# NovelAgentFlutter 协作栏与组优先交互重构分析

最后更新：2026-05-28

关联文档：

- `docs/ui-simplification-cli-alignment-plan-2026-05-28.md`
- `docs/ui-simplification-session-order-2026-05-28.md`

---

## 1. 这次问题不是“再调一下样式”

当前用户反馈集中在：

- 右下角智能体选择仍然分行，占空间
- 输入区缺少附件、深度思考、停止等能力入口
- 左侧除了大图标主切换外，还叠了一组意义不清的小图标按钮
- 找不到项目智能体组的正式入口
- “默认只有单一主智能体，用户只通过选择一个智能体组决定当前项目能用哪些智能体”这条规则没有真正生效
- 上下文预览、工具显示、运行状态都是双行块，占空间且像调试面板
- 大量 UI 被切成一个个框和分栏，视觉噪声过高

这些问题已经不只是视觉密度问题，而是 **交互主语义没有收束**。

如果继续只做局部 CSS/尺寸微调，会把当前“组选择、智能体选择、输入能力、项目动作、状态条”之间已经打架的语义继续固化。

---

## 2. 当前实现里的关键错位

## 2.1 智能体组已经存在，但真正的主入口仍然是“单个智能体下拉”

目前代码里已经有一整套项目智能体组相关链路：

- `ProjectOpeningSessionProjectionService`
- `ProjectOpeningAgentGroupBindingService`
- `ConversationOpeningPanelViewDataService`
- `OpeningSessionPanel`
- `OpeningAgentGroupPicker`

也就是说，项目级的“组选择”能力其实已经有基础。

但与此同时，右下角仍保留了：

- `ConversationModelStrip`
- `SelectorField`
- `_agentSelectorOptions()`

并且 `_agentSelectorOptions()` 直接把可见智能体列表暴露给 UI。

结果就是：

1. 用户在会话里看到的是“智能体下拉”，不是“项目智能体组”
2. 项目级组选择被降成了一个开局阶段专用卡片，而不是正式协作入口
3. “当前项目到底由哪个组控制、当前主智能体是谁”在 UI 上是模糊的

这与既定目标冲突：

> 用户始终只选择一个项目智能体组；当前实际主智能体由该组决定；只有在确有必要时才展示组内成员信息，而不是把成员选择当成一等入口。

---

## 2.2 输入区能力合同仍然是假收口

当前：

- `ConversationInputCapabilityService.resolve()` 把
  - `showOptimizeAction`
  - `showToolOptionsAction`
  - `showAttachmentEntry`
  - `showStopAction`
  全部硬编码为 `false`

这在之前清理“伪动作”时是合理的过渡做法，但现在已经暴露出新问题：

1. 用户确实需要附件入口
2. 用户确实需要深度思考入口
3. 停止动作在生成态应当存在
4. 这些能力不应该永远隐藏，而应该 **按平台、运行态、模型能力、项目上下文动态出现**

所以现在的问题不是“按钮没画出来”，而是：

**输入区缺少正式的能力投影模型。**

现状仍是“先把假按钮都关掉”，还没有演进到“把真能力按条件投影出来”。

---

## 2.3 右栏状态区仍然是三块调试条，而不是协作摘要

当前状态区由三个块组成：

- `ContextStatusBadge`
- `ConversationRuntimeStatusStrip`
- `ToolVisibilityToggle`

每一块都是：

- 图标
- 标题
- 第二行说明

因此即使信息很少，也会强制占用三行以上。

它们在可视上更像：

- 调试信息条
- 诊断面板
- 展示状态面板

而不像：

- 会话级摘要
- 可快速扫读的协作状态

问题不只是“占高”，而是 **信息组织方式仍然是后台状态风格，而不是前台协作风格**。

---

## 2.4 左栏已经有对象级大切换，却又叠加了一层小图标动作组

当前左侧已有：

- `WorkbenchActivityRail`
  - 文件
  - 项目
  - 长任务

这已经是明确的对象切换。

但在 `WorkbenchProjectPanel` 里又叠了：

- `ProjectActionGroup`
  - 新建项目
  - 打开项目
  - 项目信息
  - 刷新项目

这些动作以小图标工具条形式出现。

问题在于：

1. 它们视觉上像编辑器工具栏，而不是项目操作
2. 与左侧大按钮语义重叠
3. 会让左栏看起来像“主导航 + 子导航 + 工具栏”三层叠加

也就是：

**左栏已经做成对象面板了，却还保留了一层旧式工具条思维。**

---

## 2.5 中栏、右栏都在靠“很多盒子”组织信息

当前多个组件都使用：

- `PanelSurface`
- `ResourcePanelSection`
- `ConversationPanelBand`
- 额外边框
- 额外分栏

问题不是这些基础组件不该存在，而是：

1. 它们被过于频繁地嵌套
2. 很多块其实不是独立对象，只是同一对象内部的子信息
3. 结果是视觉上处处是框，层次却没有变清晰

典型例子：

- 项目面板里“项目动作”“当前协作基线”“项目资料与规则”都被再包一层 section
- 会话侧栏里的状态区又被拆成多个 band
- 输入区与选择区又被硬切成两个面板 section

这让界面显得“工程化很重”，但产品感很弱。

---

## 3. 哪些目标应该被正式确立

## 3.1 项目级协作选择必须组优先

后续应当正式固定为：

1. 用户对当前项目只选择一个智能体组
2. 当前会话默认主智能体由该组解析得出
3. UI 默认不暴露“单智能体切换”作为同等级主入口
4. 若需要展示组内成员，应当是说明性信息，不是平级主选择器

这意味着右下角第二个选择器不应再是“智能体”，而应当变成：

- `智能体组`

而“当前主智能体”应只作为只读状态显示，或放入组详情里。

---

## 3.2 输入区应该以“能力投影”而不是“固定按钮”建模

需要新增一个明确的输入能力投影层，至少回答：

- 当前是否允许附件
- 当前是否允许停止
- 当前是否显示深度思考开关
- 当前深度思考是否由模型支持
- 当前是否仍保留工具显示入口

而且这些判断不应散落在 widget 内，而应来自一个独立服务。

桌面端附件、模型支持的深度思考、生成中的停止，这些都应该是 **真实能力**，不是临时按钮。

---

## 3.3 右栏状态区必须收束成“单行摘要优先”

应该把：

- 上下文
- 工具显示
- 运行态

收成紧凑摘要行或 chip 行，而不是三张双行卡。

合理形态更像：

- `上下文 已载入正文与资源`
- `工具 概览`
- `运行 空闲 / 生成中`

必要时才展开详细解释。

---

## 3.4 左栏项目动作应只保留少量明确入口

更合理的策略是：

- 把“新建项目 / 打开项目”留在更上层或明显位置
- 项目面板里不再摆四个同质小图标
- 当前项目内部更多以：
  - 当前项目信息
  - 项目规则入口
  - 资产与模板入口
  - 智能体组与生态入口
  来表达

也就是说，左栏项目面板应更像“当前项目侧边说明与配置入口”，而不是迷你工具箱。

---

## 4. 为什么这轮不适合一把梭实现

如果把你刚才列的所有点放在一个会话里直接做，会同时触碰：

- 会话 view data 合同
- 智能体组绑定与默认规则
- 输入能力服务
- 右栏布局
- 左栏项目面板
- 组件共用样式与边框语言

这已经明显超出“一轮会话稳定完成”的合适范围。

更关键的是，这几条线有先后依赖：

1. 先定“组选主智能体”的合同
2. 再定输入能力如何按模型/平台/运行态投影
3. 再改右栏结构
4. 最后再做左栏和视觉减噪

否则 UI 先改了，后面合同一变，又要回头拆。

---

## 5. 建议的执行原则

后续这条线建议遵循：

1. **先合同，后 UI**
   - 先把 group-first 和 capability projection 定清楚
2. **只保留一个正式主入口**
   - 项目级协作只认“智能体组”
3. **项目级状态只读，动作级入口最小化**
   - 不在侧栏里重复堆工具按钮
4. **收边框，不收信息**
   - 不是删功能，而是让信息更轻量地组织
5. **始终注意桌面端与未来 CLI 对齐**
   - 选择逻辑、能力判定逻辑应当可复用，不写死在 Flutter widget 里

---

## 6. 下一步应该怎么拆

建议拆成一条新的实施线，至少包含：

1. `GF-01`
   - 建立 group-first 协作选择合同
2. `GF-02`
   - 建立输入能力投影合同
3. `GF-03`
   - 右栏会话/输入区紧凑化
4. `GF-04`
   - 左栏项目面板收口
5. `GF-05`
   - 全局分栏/边框减噪回归
6. `GF-06`
   - 联调、截图、Windows 打包前回归

具体 session 顺序见下一份文档。
