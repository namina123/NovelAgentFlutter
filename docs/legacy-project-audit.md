# 旧项目审计: `D:\GODOTProject\NOVELAgent`

## 目的

这份审计只做一件事: 把旧项目为什么会变重、变难改，转成新项目的硬约束。

## 结构性问题

### 1. 壳层和业务层长在一起

UI 主控既管布局，也管业务动作、会话流程、状态回填和部分交互策略。结果是:

- 窗口层变成了事实上的应用层。
- 任何新功能都倾向于继续塞进主控。
- 一处变更容易带出一串无关回归。

### 2. 状态中心过大

`app_state.gd` 同时承担:

- 当前项目
- 当前会话
- 当前模型/凭据
- 工作流运行
- 技能执行
- 持久化
- 部分宿主动作协调

这会让状态边界失真: 大部分能力都能“顺手”依赖它，于是依赖方向开始失控。

### 3. 平台能力、产品能力、功能能力没有分开

旧项目里经常是一个模块同时知道:

- UI 长什么样
- 项目文件怎么存
- 模型请求怎么发
- 原生工具怎么调
- 当前运行平台能不能做这件事

一旦做跨平台，复杂度会按乘法增长。

### 4. 仓库没有交付边界

参考资料、构建产物、外部依赖、实验代码长期与主产品同仓共生，导致:

- 认知噪音很大
- 搜索结果污染严重
- 迁移、裁剪、重构的成本偏高

### 5. 先加功能，后补架构

旧项目其实已经开始补救，像 `UI_DECOUPLING_PLAN.md` 和 `GODOT_FRONTEND_ARCHITECTURE.md` 都在做拆分，但时间点已经偏晚，拆分是在负重状态下进行的。

## 给新项目的硬约束

1. 新项目不允许出现 `main_controller` / `app_state` 级别的全能文件。
2. Flutter GUI 和 CLI 只做各自壳层，不承接共享业务规则。
3. 平台差异不通过到处写 `if (desktop/mobile)` 解决，而通过能力接口隔离。
4. 共享核心必须是纯 Dart，不依赖 Flutter UI。
5. 新仓库一开始就分 `apps/` 和 `packages/`，拒绝继续把一切堆在一个应用目录下。
6. 桌面专属能力必须显式标记为 desktop-only，不能默默泄漏进移动端路径。
7. 文件过大时优先拆职责，不再用“先跑起来再说”作为默认策略。

## 这份审计的结论

旧项目不是“功能太多”才失败，而是“功能增长时没有稳定边界”。  
新项目第一优先级不是复刻功能，而是建立让功能可以慢慢长、却不轻易发胖的边界。
