## 1. 先把你的意思梳理清楚

你现在要的，不是“拆书功能更强一点”这么简单。

你真正想要的是：

1. 一本书拆完以后，后续不能只停留在“拆书项目”里。
2. 拆书结果应该能继续进入其他正常写作类别：
   - 一般小说续写
   - 长任务续写
   - 多种长任务模式续写
3. 这些后续路线不应该藏到别的页面或别的入口里再找。
4. 拆书完成后的“后续菜单”本身就应该是完整工程菜单：
   - 一般续写
   - 长任务续写
   - 长任务不同规格 / 不同模式
   - 以及后续可能新增的其他续写路线
5. 拆书后的核心价值，不只是抽几个角色和世界观卡片。
6. 真正难点是：
   - 怎么让后续续写对齐前面所有章节
   - 怎么在超长篇、未完结、1000 章以上时仍能保持世界观、主线、人物、性格、关系、伏笔、走向不漂
7. 你要的是一种“拆书结果成为正式续写基座”的能力，而不是一个孤立的拆书工作台。

换句话说：

**拆书只是前置输入，续写才是后续主线。**

而且续写入口应该是可分流的，不应该被锁死为某一个专用模式。

## 2. 参考 MuMuAINovel 后得到的关键信号

`MuMuAINovel` 在这条线上最值得吸收的，不是页面，而是它对“拆书后继续创作”的产品语义：

### 2.1 它不是把拆书结果当静态报告

它的拆书导入不是只生成一份纪要，而是把导入结果继续变成项目里的创作事实：

- 项目基础信息
- 章节
- 大纲
- 世界观
- 职业体系
- 角色
- 组织
- 关系

也就是：

**拆书结果会被继续送入写作工程，而不是只停在分析阶段。**

### 2.2 它已经区分了“整本拆”和“尾部续写导向拆”

`MuMuAINovel` 的拆书接口里明确有：

- `extract_mode = tail | full`
- `tail_chapter_count`
- `import_mode = append | overwrite`

这说明它已经在产品上承认一件事：

**对于未完结长篇，很多时候用户真正要的不是整本重建，而是抓住前情基座，然后从尾部继续。**

这是和你的目标高度一致的。

### 2.3 它的续写不是把全书正文直接塞给模型

从它的大纲续写、章节续写上下文可以看到，它主要依赖的是分层上下文：

- 项目基础信息
- 最近若干章结构
- 角色全量信息
- 关系 / 组织 / 职业等结构化信息
- 伏笔提醒
- 相关记忆
- 上一章承接点
- 最近章节上下文

所以它的核心方法不是“上下文越多越好”，而是：

**全书信息结构化压缩 + 最近局部窗口放大。**

这也是我们必须走的方向。

## 3. 我们当前项目的现状

### 3.1 我们已经有的好东西

我们现在并不是从零开始。

已经具备的基础不少：

1. 拆书抽取结果已经是结构化的
   - `BookDeconstructionExtractionResult`
   - 已覆盖：
     - premise
     - story outline summary
     - chapter outlines
     - style profiles
     - world rule sets
     - character profiles
     - organization profiles
     - foreshadow / timeline / relationship

2. 拆书结果已经能映射成可应用计划
   - `BookDeconstructionAssetMappingService`
   - `BuildBookDeconstructionApplicationPlanUseCase`

3. 长任务本身已经有“长期约束路径”机制
   - `LongTaskModeContextPathService`
   - `LongTaskProjectFileSectionPlanService`

4. 长任务已经有不少漂移检查能力名义上的接入位
   - `long_task_world_drift_signal_service.dart`
   - `long_task_narrative_drift_signal_service.dart`
   - `long_task_entity_drift_signal_service.dart`
   - `long_task_style_drift_signal_service.dart`
   - `long_task_checkpoint_drift_signal_service.dart`

5. 长任务模式目录已经有适合“旧材料接续/抢救”的路线
   - `salvage_restructure_existing`

### 3.2 我们当前真正缺的

虽然有这些基础，但现在仍然缺一层正式中间层：

**拆书结果到续写运行之间的承接层。**

具体表现为：

1. 拆书目前更像“资产预演”
   - `BookDeconstructionController` 当前确认后主要写的是预演纪要
   - `project_import_execution_service.dart` 目前也主要是自动拆书预演纪要

2. `book_deconstruction` 仍是一个封闭策略
   - `StrategyCatalogService` 里它只支持：
     - `book_asset_extraction`
   - 还没有正式声明：
     - 拆书结果可以转入 `general_novel`
     - 或转入 `long_task_novel` 的若干模式

3. 长任务长期约束路径虽已存在，但没有“拆书续写基座”的正式事实包

4. 一般小说续写与长任务续写都还没有一个统一的“前情承接协议”

所以问题不是“没有拆书”，而是：

**拆书产物还没有成为后续写作系统的一级输入。**

## 4. 这件事真正该怎么定义

我建议把目标正式定义成：

## 4.1 拆书项目不是终点，而是基座工程

拆书项目的职责应该是：

1. 导入外部作品或片段
2. 抽取并清洗结构化前情
3. 生成可确认的续写基座
4. 允许从这个基座派生多个续写项目

也就是说：

- 拆书项目保留“分析源”
- 续写项目承担“正式创作”

这比“直接把拆书项目类型改成一般小说/长任务小说”更合理。

### 为什么不建议直接改项目类型

因为你明确说了：

> 拆完书后，后续可以选择所有其他一般类别

这意味着同一份拆书结果，后面可能要走多条路线：

- 一条普通交互式续写
- 一条灵感托管式长任务
- 一条全书共拟式长任务
- 一条旧稿抢救式长任务

如果直接把拆书项目自己改类型，会丢掉“可多路派生”的能力。

所以更合理的是：

**拆书项目 -> 生成续写基座包 -> 派生多个续写项目**

## 5. 推荐新增的核心对象：续写基座包

我建议新增一个正式概念：

`DeconstructionContinuationPackage`

它不是 UI 对象，而是领域对象。

### 5.1 它至少应该包含什么

#### A. 全书稳定事实层

这些是长期不该轻易漂移的：

- 世界规则
- 时代 / 地点 / 氛围
- 主线总前提
- 风格目标
- 主要角色卡
- 组织卡
- 关系网
- 伏笔池
- 时间线

#### B. 结构压缩层

这些是对超长篇最重要的：

- 全书总纲摘要
- 分卷 / 分阶段摘要
- 每若干章一个 arc summary
- 每章摘要与承接点
- 当前未回收线索

#### C. 尾部承接层

用于真正继续写下一章：

- 最近 N 章摘要
- 最近 M 章原文片段窗口
- 上一章结尾承接点
- 当前剧情阶段
- 当前角色状态快照
- 当前组织/势力状态快照

#### D. 覆盖范围声明

必须知道这份拆书基座到底代表什么：

- 来源书名
- 来源文档
- 是整本抽取还是尾部抽取
- 若是尾部抽取，覆盖的是最后多少章
- 哪些章节被显式纳入
- 哪些信息是推断得到，不是原文明示

这层非常重要。

否则后面续写时会误把“不完整拆书结果”当成“完整全书共识”。

## 6. 面对 1000 章以上时，不能怎么做

这里必须先明确反模式。

### 6.1 不能把前面所有章节全文硬塞进上下文

1000 章级别根本不可持续：

- token 爆炸
- 每次续写成本极高
- 召回效率很差
- 重要信息会淹没在无关文本里

### 6.2 不能只靠“最后几章 + 一个世界观摘要”

这会丢掉很多中程信息：

- 旧伏笔
- 阵营演化
- 人物成长轨迹
- 已经建立的人设边界
- 中期主线承诺

### 6.3 不能把一致性全压到 prompt 文案

这件事必须领域化。

不能继续靠：

- 一个超长 system prompt
- 临时拼接说明
- 页面上几个备注字段

去承担超长篇前情对接。

---

## 7. 面对 1000 章以上时，应该怎么做

推荐正式采用：

## 7.1 多层记忆金字塔

### 第一层：全局圣经层

只保留稳定、长期有效、必须遵守的事实：

- 世界观底线
- 风格底线
- 主要角色稳定性格
- 主线承诺
- 禁区

### 第二层：阶段 / 分卷层

每 20 到 50 章收束成一个阶段包：

- 这一阶段发生了什么
- 哪些关系变了
- 哪些伏笔被埋下/回收
- 主线向哪里推进

### 第三层：章节摘要层

每章保留：

- 简要摘要
- 承接点
- 角色出场
- 组织出场
- 情绪基调
- 未闭合动作

### 第四层：尾部原文窗口层

只保留最近少量原文片段：

- 最近 1 章到 3 章全文
- 或最近 5 章到 10 章关键片段

### 第五层：动态状态表层

每次续写前读取当前状态：

- 角色当前状态
- 势力状态
- 感情/关系变化
- 伏笔状态
- 当前主线阶段

这才是“超长篇可续写”的正道。

## 7.2 生成时走“全局稳定 + 局部放大”策略

续写时，不是一次读所有信息，而是：

1. 先装载全局圣经
2. 再装载相关分卷/阶段摘要
3. 再装载当前章节附近的近邻摘要
4. 最后装载最近原文窗口

也就是：

**远处信息摘要化，近处信息高保真。**

## 8. 我们项目里最合理的产品走法

我建议不要做“拆书后继续写”这个单按钮黑箱。

而是拆成下面这个明确流程。

## 8.1 第一步：拆书项目完成后，生成续写基座

输出：

- 结构化资产
- 续写基座包
- 覆盖范围说明

## 8.2 第二步：用户选择续写去向

至少应支持：

1. 派生为 `general_novel`
   - 适合普通对话式续写

2. 派生为 `long_task_novel`
   - 并可选择具体模式：
     - `seed_autopilot_novel`
     - `full_outline_consensus`
     - `volume_checkpoint_handoff`
     - `chapter_brief_supervised`
     - `salvage_restructure_existing`

这里要强调：

**续写模式是“派生项目”的策略，不是“拆书项目”的策略。**

### 这一步的 UI 语义要明确

这里不应做成：

- 拆书结束
- 用户再自己跳去别的入口
- 重新寻找长任务或普通续写入口

而应该做成：

**拆书后续菜单 = 完整工程菜单**

也就是拆书完成后，用户就在当前后续菜单里直接看到：

1. 一般小说续写
2. 灵感托管式长任务
3. 全书共拟式长任务
4. 分卷检查点式长任务
5. 章纲监督式长任务
6. 旧稿抢救重构式长任务

后续如果我们再扩新的工程路线，也还是加在这个后续菜单里。

所以这个菜单的职责不是“提示一下接下来可以做什么”，而是：

**正式承接拆书之后的工程分流。**

## 8.3 第三步：派生项目自动继承续写基座

派生时自动完成：

- 写入长期约束路径
- 写入续写基座索引
- 写入尾部承接窗口
- 写入项目初始说明
- 决定默认续写入口

## 8.4 第四步：续写运行时按模式取不同上下文

例如：

### 一般小说续写

偏重：

- 最近章节窗口
- 当前角色状态
- 读者可见风格一致性

### 灵感托管式长任务

偏重：

- 全局圣经
- 分阶段结构
- 低频检查点

### 全书共拟式长任务

偏重：

- 全书走向
- 分卷结构
- 结局承诺

### 旧稿抢救式长任务

偏重：

- 材料缺损识别
- 结构重建
- 再续写前重组

## 10. 对现有项目策略的建议

这里给一个非常明确的建议：

## 10.1 保留 `book_deconstruction` 作为分析型项目

它的职责不改：

- 导入外部作品
- 抽取结构化资产
- 生成续写基座

## 10.2 不建议直接把 `book_deconstruction` 和 `general_novel` / `long_task_novel` 合并

因为这会让：

- 分析源
- 续写执行
- 多路线分叉

混在一个项目语义里，后续会很难维护。

## 10.3 推荐增加“派生续写项目”

也就是：

- 一个拆书源项目
- 多个续写派生项目

这样你说的“拆完以后可以当一般小说续写，也可以当不同长任务续写”才真正成立。

## 11. 最关键的技术判断

如果只用一句话总结：

**这件事的核心不是“拆书做得更细”，而是“建立一层可被不同续写模式共享的正式续写基座”。**

真正的难点不在 UI，也不在多一个按钮，而在：

1. 如何把全书前情压缩成多层稳定事实
2. 如何把尾部最近章节高保真承接
3. 如何把这些事实以项目级、模式无关的方式供后续续写读取
4. 如何在普通续写与长任务续写之间共享这层基座，而不是各自复制一套逻辑

## 12. 当前分析结论

### 结论一

你的目标是合理的，而且和我们已有长期路线并不冲突。

### 结论二

最正确的方向不是“让拆书项目自己支持续写模式切换”，而是：

**让拆书项目产出一个可派生、可复用、可多路分叉的续写基座包。**

同时，产品入口上必须把这些分叉路线直接放进“拆书后续菜单”里，作为完整工程菜单来承接，而不是让用户再去别处寻找。

### 结论三

面对 1000 章以上未完结长篇，必须采用：

- 全局圣经
- 分卷摘要
- 章节摘要
- 尾部窗口
- 状态表

的分层承接，而不能继续依赖“全量正文”或“只看最后几章”。

### 结论四

我们当前仓库已经有不少可复用积木：

- 拆书结构化资产
- 长任务长期约束路径
- 漂移检测框架
- 多种长任务模式

真正缺的是“拆书结果 -> 续写基座 -> 派生续写项目”的中间层。

## 14. 关于“这些前置资源到底怎么生成”的批判性分析

你补充的这个问题非常关键。

现在要解决的不是“拆书后有没有入口”，而是：

**拆书后那些真正决定续写质量的前置资源，到底应该由什么机制、在什么时机、以什么交互心智生成。**

你提出的候选方案是：

1. 拆书项目创建完成
2. 用户选择一个智能体组
3. 开启分析
4. 这个智能体组按既定流程跑一个“分析长任务”

这个方案不是没道理，相反它已经碰到了几个正确方向：

- 你意识到前置资源不该全靠用户手填
- 你意识到这件事是一个受控流程，不是一句 prompt
- 你意识到智能体组可能会参与这件事，而不是固定单智能体

但如果直接照这个方案落地，我认为会有明显问题。

## 14.1 这个方案的优点

### 优点一：它承认“前置资源生成”是工程，不是备注

这是对的。

续写基座涉及：

- 世界观
- 主线总承诺
- 角色稳定性
- 关系网
- 伏笔池
- 分阶段摘要
- 尾部承接窗口

这本来就不是“拆完顺手写两段说明”能解决的。

### 优点二：它天然适合长流程和可恢复

如果前置资源生成要跑：

- 章节分段
- arc 摘要
- 人物状态汇总
- 伏笔回收状态分析
- 风格提炼

那确实很像一个可恢复任务链。

### 优点三：它和我们现有 group-first / opening / long-task 基础并不冲突

我们已有：

- starter group
- opening orchestration
- long task runtime

所以把“资源分析”做成一个正式流程，在架构上是接得住的。

---

## 14.2 这个方案的问题

### 问题一：太早要求用户选智能体组，心智负担偏高

这是我最先反对的一点。

拆书刚完成时，用户最关心的是：

- 我接下来要怎么续写
- 这个拆书结果够不够继续写
- 我应该选普通续写还是长任务续写

这时候如果先问：

> 请选择一个智能体组，然后开始分析长任务

大多数用户会不知道自己到底在决定什么。

因为这时他们真正还没决定的是：

- 我要走哪条续写路线
- 我需要多重的分析
- 我是要快速继续，还是要建立高质量长篇基座

所以：

**“先选智能体组”对于专家用户可能可用，但对于产品默认流不够友好。**

### 问题二：把它直接叫“分析长任务”容易把产品语义搞混

“长任务”在我们项目里已经有很明确的语义：

- 正式写作任务链
- 可恢复推进
- 会进检查点
- 会继续生成正文 / 修订 / 后处理

而“拆书后前置资源生成”虽然也可能很长，但它本质上不是正文写作长任务，而是：

**续写基座构建流程**

如果直接也叫长任务，用户会混淆：

- 这是在开始写了吗？
- 这是在分析吗？
- 这是在建工程还是在续正文？

所以我不建议产品层直接把它命名成“分析长任务”。

### 问题三：不同后续方案对前置资源的需求并不相同

这是决定性问题。

比如：

#### 一般续写

需要的更偏：

- 尾部承接
- 角色状态
- 近期剧情方向

#### 灵感托管式长任务

需要的更偏：

- 全局圣经
- 主线承诺
- 分阶段摘要
- 长期约束

#### 全书共拟式长任务

需要的更偏：

- 现有材料压缩
- 全书走向重建
- 分卷结构建议

#### 旧稿抢救重构式长任务

需要的更偏：

- 缺口识别
- 设定冲突
- 结构断裂点

这说明：

**前置资源生成不是一条固定流水线，而是至少要分层、分规格。**

如果强制用户一上来选智能体组并跑同一条“分析长任务”，容易浪费计算，也容易分析过度。

### 问题四：如果把分析和续写派生绑定得太死，会损失“快速进入”的体验

有些用户并不想先做一整套深分析。

他们可能只是想：

- 从最近 10 章开始续一章
- 先试试文风
- 先做一个普通续写分支

这类需求如果被强行要求：

- 选组
- 等分析长任务
- 再派生

体验会很重。

所以不能把“深度前置资源构建”做成唯一入口。

---

## 15. 最好的方案：分层生成，而不是单一路径大分析

综合易用性、可行性、工程复用，我认为最好的方案是：

## 15.1 拆书后续工程菜单里，先选“后续路线”，再决定分析规格

顺序应该是：

1. 拆书完成
2. 进入“后续工程菜单”
3. 用户先选要去哪里：
   - 一般小说续写
   - 灵感托管式长任务
   - 全书共拟式长任务
   - 分卷检查点式长任务
   - 章纲监督式长任务
   - 旧稿抢救重构式长任务
4. 系统根据路线，给出默认分析规格
5. 用户再决定：
   - 直接快速开始
   - 或先补做更完整的续写基座分析

也就是：

**先选工程去向，再按去向决定前置资源深度。**

这比“先选智能体组，再开分析长任务”更符合用户心智。

---

## 15.2 把前置资源生成分成三档

我建议正式分成：

### A. 快速承接

适合：

- 普通续写
- 先试写
- 只接最近剧情

生成内容：

- 最近章节摘要
- 尾部承接点
- 近期角色状态
- 基础世界观 / 风格提要

特点：

- 快
- 成本低
- 可马上进入写作

### B. 标准续写基座

适合：

- 大多数认真续写
- 普通续写长期使用
- 轻中度长任务

生成内容：

- 全局圣经草案
- 分阶段摘要
- 角色 / 组织 / 关系稳定卡
- 伏笔池
- 时间线
- 最近章节承接窗口

特点：

- 是默认推荐档
- 既够用，又不至于过重

### C. 深度重构基座

适合：

- 超长篇
- 结构混乱
- 要进全书共拟 / 旧稿抢救式长任务

生成内容：

- 更正式的全书走向重建
- 分卷 / 分 arc 重构
- 冲突和缺口识别
- 设定矛盾与角色漂移风险
- 长任务长期约束包

特点：

- 慢
- 重
- 但适合长期托管

这三档，比“统一分析长任务”更合理。

---

## 15.3 智能体组应该怎么参与

这里我不建议“让用户默认先选组”，而建议：

### 默认情况

系统根据：

- 当前项目类型 = `book_deconstruction`
- 当前后续路线
- 当前分析规格

自动匹配推荐 starter group / continuation group。

也就是说：

#### 快速承接

默认用轻量 generalist continuation 组。

#### 标准续写基座

默认用 deconstruction continuation generalist 组。

#### 深度重构基座

默认用更偏 long-task planning / salvage 的组。

### 高级情况

再允许用户展开“高级设置”手动换组。

这样：

- 新手不用先理解组
- 老手仍能干预
- 也符合我们已有的 group-first 运行路线

所以我对你的方案的修正是：

**不是“用户先选组再分析”，而是“系统先按路线推荐组，用户可选覆盖”。**

---

## 15.4 运行形态应该怎么定义

这里我建议产品层不要直接叫“分析长任务”，而是明确成：

`续写基座构建`

底层实现可以复用长任务 runtime 的很多能力：

- 可恢复
- 分阶段
- 可观察
- 可中断
- 可回看

但在产品语义上，它应该被单独定义为：

**基座构建流程**

而不是正文长任务本身。

这样能避免把两个概念混在一起：

1. 续写前资源构建
2. 正式正文长任务推进

---

## 15.5 生成完成后再派生正式续写项目

我认为最好的闭环是：

1. 拆书完成
2. 用户在后续工程菜单中选择路线
3. 系统按路线决定默认分析规格与默认组
4. 运行一次“续写基座构建”
5. 构建完成后生成：
   - 续写基座包
   - 覆盖范围说明
   - 推荐长期约束
6. 再派生正式续写项目：
   - 普通续写项目
   - 某种长任务续写项目

这样一来：

- 拆书项目仍是分析源
- 续写项目才是执行面
- 多路分叉天然成立

---

## 16. 为什么我认为这是最好的方案

### 从易用性看

它比“先选组再跑分析长任务”更自然。

用户先选“我要怎么继续”，比先选“谁来分析”更符合直觉。

### 从可行性看

它高度复用我们现有基础：

- starter group
- opening projection
- long-task runtime
- 拆书结构化资产
- 长任务长期约束路径

### 从扩展性看

它不会把拆书后续绑死在一个流程里。

以后新增：

- 新续写模式
- 新分析规格
- 新 continuation group

都可以平行接入。

### 从产品语义看

它能把三件事分清楚：

1. 拆书分析源
2. 续写基座构建
3. 正式续写执行

这比把一切都叫“长任务”要清楚得多。

---

## 17. 最终建议

如果只给一句最终建议：

**不要直接做成“拆书完成 -> 用户选智能体组 -> 开一个分析长任务”。**

更好的方案是：

1. 拆书完成后进入“后续工程菜单”
2. 用户先选择后续路线
3. 系统按路线自动推荐：
   - 分析规格
   - continuation 智能体组
4. 用户可在高级设置里覆盖组与规格
5. 启动一个正式但语义独立的：
   - `续写基座构建流程`
6. 基座构建完成后，再派生正式续写项目

这个方案在：

- 易用性
- 可行性
- 架构复用
- 超长篇可持续性

上，综合来看都优于“先选组再直接开分析长任务”的原始版本。

---

## 18. 关于“项目类型到底在什么时候选”的再分析

你这次补充的想法是：

1. 用户在创建项目时就先选好类型
2. 选完类型后，才真正开始拆书

这个思路和前面我写的“拆完后再选后续路线”并不一样。

前者更像：

**先确定我要做什么项目，再让拆书为这个项目服务**

后者更像：

**先把书拆清楚，再决定后面走哪条工程路线**

这两种不是谁绝对对谁绝对错，而是各有收益和代价。

## 18.1 方案 A：拆完后再选后续路线

也就是前面那版思路：

- 先做拆书分析
- 拆完后进入后续工程菜单
- 再选择一般续写 / 长任务续写 / 不同规格长任务

### 好处

1. 用户在没有看到拆书结果前，不必过早做重大决策
2. 同一份拆书结果天然可以分叉出多种续写项目
3. 对“我先看看这本书到底拆成什么样”更友好

### 问题

1. 对目标很明确的用户来说，流程偏绕
2. 会让“拆书”看起来像一个相对独立的前置工程
3. 如果用户本来就是为了某个固定目标而来，比如：
   - 我就是要做长任务续写
   - 我就是要做普通续写
   那先拆后选会显得多走一步

## 18.2 方案 B：创建项目时先选目标方向，再开始拆书

也就是你现在提出的方向：

- 创建项目时就选：
  - 普通续写优先
  - 长任务续写优先
  - 或某种更具体的后续路线偏好
- 然后拆书流程按这个目标方向去生成前置资源

### 好处

1. 用户目标明确时，路径更直接
2. 拆书过程可以从一开始就按目标工程优化：
   - 普通续写偏最近章节承接
   - 长任务续写偏长期约束和阶段结构
3. 用户心智更统一：
   - “我现在就在创建一个续写项目”
   - 而不是“我先做一个拆书项目，后面再说”

### 问题

1. 如果把这个“方向”直接做成最终项目类型，会削弱“一份拆书结果服务多条路线”的天然能力
2. 用户如果选错方向，可能会拿到不够合适的默认分析结果
3. 容易让拆书逻辑和续写项目类型过度耦合
4. 对产品结构不利的一点是：
   - 拆书分析源
   - 续写执行面
   会被混进一个项目里

这会让后面很难表达：

- 这份信息是原书事实
- 这份信息是续写推断
- 这份信息是某个续写路线专属加工结果

---

## 19. 批判性结论：两种纯方案都不够好

如果只站一边，都会丢东西。

### 只用“拆完再选”

会损失：

- 目标明确用户的效率
- 按目标类型定制拆书分析的能力

### 只用“创建时先选类型”

会损失：

- 拆书结果的一次分析、多路复用
- 后续灵活分叉
- 源事实与派生事实的边界清晰度

所以我不建议纯选其中之一。

---

## 20. 我认为最好的方案：双层选择，主次分明

最稳的方案不是二选一，而是：

## 20.1 创建项目时先选“主目标方向”

但这里选的不是最终唯一类型，而是：

**本次拆书的主目标路线**

比如：

1. 普通续写优先
2. 长任务续写优先
3. 暂时只拆书分析

这样做的意义是：

- 系统能从一开始知道默认要偏向哪类分析
- 但又不把后续彻底锁死

也就是说：

创建时选的是：

**默认导向**

不是：

**永久唯一去向**

## 20.2 拆书流程按“主目标方向”定制

例如：

### 如果创建时选“普通续写优先”

则拆书更偏重：

- 最近章节窗口
- 尾部承接点
- 近期角色状态
- 基础风格与世界观提要

### 如果创建时选“长任务续写优先”

则拆书更偏重：

- 全局圣经
- 分卷 / 分阶段摘要
- 主线承诺
- 角色稳定卡
- 长期约束包

### 如果创建时选“先拆书分析”

则拆书偏中性：

- 尽量保留源事实
- 尽量少做路线专属加工

## 20.3 拆书完成后，仍然保留“后续工程菜单”

这是关键。

即便创建时已经选了主目标方向，拆书完成后仍应保留完整后续菜单：

- 一般续写
- 各种长任务续写
- 其他未来路线

但系统会把创建时的主目标路线：

- 放在默认首位
- 作为推荐路线
- 自动选好默认分析规格和默认 continuation group

这样就兼顾了两边：

1. 创建时有方向
2. 拆完后仍可分叉

## 20.4 这里最容易做错的一点：不要把“方向”直接做成“最终项目类型”

这是这轮分析里我认为必须额外说死的一点。

如果用户在创建时表达的是：

- 普通续写优先
- 长任务续写优先
- 先拆书分析

那么系统真正拿到的，应该是：

**拆书承接工程的默认导向**

而不是：

**已经创建好了最终的普通续写项目或长任务续写项目**

也就是说，产品上要区分两层：

### 第一层：源工程类型

它仍然应该是：

- `book_deconstruction`

或者未来如果要重命名，也应该是“拆书承接源工程”这类语义。

这层负责：

- 导入原书
- 拆书分析
- 构建续写基座
- 保留源事实
- 保留多路派生能力

### 第二层：后续目标方向

它只是创建时记录的默认导向，例如：

- `general_continuation_preferred`
- `long_task_continuation_preferred`
- `analysis_only_preferred`

这层负责影响：

- 默认分析规格
- 默认 continuation group
- 默认后续菜单排序
- 默认推荐的派生路线

### 第三层：真正派生出来的执行项目

等拆书和基座构建完成后，才正式派生：

- `general_novel`
- `long_task_novel`
- 或后续新增的其他执行型项目

这一刀如果不切开，后面实现时就很容易出现几个问题：

1. 拆书源事实和续写推断事实混在同一个项目里
2. 用户想从同一份拆书结果派生两条路线时，会被项目类型锁死
3. “创建时先选方向”会被错误实现成“创建时先建最终项目”，从而失去拆书源工程的独立价值

所以更准确的说法不是：

**创建项目时先选最终类型**

而是：

**创建拆书承接工程时，先记录一个主目标方向。**

---

## 21. 为什么这是更好的辩证方案

### 对目标明确的用户

他们会觉得顺：

- 创建时就选好“我要做长任务续写”
- 后面拆书不是瞎拆，而是按长任务续写准备

### 对目标还不明确的用户

他们也不会被锁死：

- 先选“先拆书分析”或一个默认导向
- 拆完后仍能在后续工程菜单重新分流

### 对架构

它避免了两个极端：

1. 不是完全后置，导致拆书缺乏目标导向
2. 也不是完全前置锁死，导致拆书失去复用性
3. 同时还保住了“源工程”和“执行工程”的边界，不至于把项目类型语义做乱

### 对超长篇

它还有一个额外好处：

对于 1000 章级别作品，不同目标路线确实应该决定不同的基座构建优先级。

所以让项目创建阶段表达“主目标方向”，是有真实技术收益的，不只是 UI 选择。

---

## 22. 最终建议再收束一次

如果用一句更准确的话来说，我现在的最终建议不是：

- “必须拆完后再选”

也不是：

- “必须创建时先选死”

而是：

**创建拆书承接工程时先选“主目标方向 / 默认导向”，拆书过程按这个导向准备资源；拆书完成后，再通过完整的后续工程菜单保留重新分流与多路派生能力。**

换成产品动作就是：

1. 创建项目
2. 选择：
   - 普通续写优先
   - 长任务续写优先
   - 先拆书分析
3. 开始拆书
4. 拆书基于该导向构建默认前置资源
5. 拆书完成后，进入完整后续工程菜单
6. 默认高亮创建时所选路线，但不禁止用户改走别的路线

这比单纯的前置或后置，都更稳。

再收束成一句实现层面的判断：

- 创建时确定的是 `主目标方向`
- 拆书期间运行的是 `续写基座构建`
- 真正落地的 `项目类型` 应该在派生执行项目时才最终确定

---

## 23. 继续吸收 MuMuAINovel 后，我认为还能补进我们框架的东西

这轮继续往参考项目里深挖后，我认为真正值得吸收的不是某几个接口名，而是下面几类框架判断。

### 23.1 拆书承接要显式分成“预览 / 确认 / 构建 / 派生”

MuMu 的拆书导入链有一个很实用的节奏：

1. 创建任务
2. 先拿到预览
3. 用户确认应用
4. 应用后再继续补生成世界观、职业、角色、组织等信息

这说明：

**拆书承接不该被做成一次性黑箱。**

对我们更合适的翻译是：

1. 先生成拆书预览与覆盖范围说明
2. 用户确认这份材料是否足以承接续写
3. 再进入正式的 `续写基座构建`
4. 构建完成后，再派生正式执行项目

### 23.2 续写上下文必须是正式 contract，不是散装 prompt 拼接

MuMu 在章节生成侧已经有比较明确的上下文合同：

- `chapter_outline`
- `continuation_point`
- `previous_chapter_summary`
- `foreshadow_reminders`
- `relevant_memories`
- `characters_info`
- `all_chapters_brief`
- `recent_plot`
- `memory_context`

更重要的是，它把 1-1 和 1-N 模式分成不同的 context builder。

这个思路很值得吸收。

对我们来说，后续不应该让：

- 一般续写
- 长任务续写
- 拆书续写承接

各自维护一套 prompt 拼装逻辑。

更合理的是把它收束成正式合同层，例如：

1. `ContinuationGlobalContext`
2. `ContinuationRecentContext`
3. `ContinuationStateSnapshot`
4. `ContinuationPromptMaterial`

### 23.3 角色 / 组织 / 关系 / 伏笔要从“分析资产”升级成“运行事实”

MuMu 的角色、组织、关系、伏笔、记忆，并不只是展示资料，而是后续生成和分析时会被重新读回去的运行事实。

这对我们是个重要提醒。

我们当前的拆书结构化资产已经不错，但如果它们只停在：

- preview markdown
- 资产列表
- analysis 文档

那它们还没有真正进入续写运行时。

所以 continuation package 不应只是打包 markdown，还应包含：

1. 稳定实体索引
2. 可滚动状态表
3. 运行时读取映射

### 23.4 “分析后回写”应该是长期机制，而不是一次性导入行为

MuMu 不只是导入时提取结构，后面章节分析还会继续：

- 更新剧情分析
- 更新故事记忆
- 更新伏笔状态
- 清理旧分析结果
- 重建相关向量记忆

这说明：

**续写一致性不是导入一次就永久解决，而是要在后续生成过程中持续回写。**

对我们来说，这意味着 continuation package 不能只是初始报告，而应该支持：

- 增量更新
- 漂移检测后回写
- 派生分支各自继续演化

### 23.5 伏笔最好有稳定引用，而不只是文本匹配

MuMu 在伏笔上有两个层次：

1. 理想状态下用 `reference_foreshadow_id` 做回收追踪
2. 实在没有时才用内容匹配做兜底

这个思路非常值得吸收。

所以我们后续的伏笔不应只是自由文本列表，而应该至少有：

- stable id
- plant stage / chapter range
- expected resolve stage
- current resolve state
- related entities

### 23.6 上下文读取可以按模式分型，但底层材料应共享

MuMu 的 `OneToOneContextBuilder / OneToManyContextBuilder` 提醒我们：

**不同运行模式确实需要不同读取器。**

但这不应变成：

- 每种模式各自维护一套独立事实层

更合理的是：

1. 共享底层 continuation package
2. 根据模式切换不同 context profile

### 23.7 失败步骤可重试，这对“续写基座构建”也很重要

MuMu 的拆书导入允许：

- 世界观生成失败
- 职业生成失败
- 角色/组织生成失败

被单独记录并重试，而不是整条链直接报废。

这对我们的 `续写基座构建流程` 很有价值。

因为这条链未来也会包含很多阶段：

1. 章节拆分
2. 多层摘要
3. 全局圣经抽取
4. 实体归一
5. 伏笔链整理
6. 长任务约束包生成

所以更合理的设计是：

- continuation package 允许“部分完成”
- 每个阶段有独立状态
- 用户可以重跑失败步骤

### 23.8 不适合直接照搬的部分

为了避免越吸收越跑偏，也把不该照搬的点写清楚：

1. 不要把拆书导入后的结果直接揉进单一写作项目
2. 不要把上下文策略紧耦合在 API 层
3. 不要把章节级记忆系统直接等同于拆书续写基座
4. 不要过早引入过细、过重的单体后端数据模型

### 23.9 这轮吸收后，我认为我们的框架至少应明确成四层

1. 拆书源层
2. 续写基座层
3. 模式化读取层
4. 执行与回写层

如果这四层不分开，后面很容易再次退化成：

- 拆书只是预览报告
- 续写只是拼 prompt
- 长任务只是另一套平行事实

## 24. 多世界 / 快穿 / 分区域覆盖：必须打破“一个角色一张全局卡就够了”的假设

你这次补的这个点非常关键。

如果我们继续默认：

- 一个角色只有一张全局角色卡
- 一个世界观只有一份全局规则
- 一段关系只有一种稳定状态

那么一旦遇到：

- 快穿
- 多世界并行
- 多副本
- 梦境 / 幻境 / 回档线
- 同一人物在不同世界身份不同
- 同一组织只在某个区域或卷段成立

整个 continuation package 就会开始失真。

所以这里必须明确：

**全局事实层仍然需要，但它上面必须允许存在“区域性 / 阶段性 / 世界线局部覆盖层”。**

### 24.1 为什么这个问题会很快把简单角色卡做坏

以快穿或多世界为例，同一个“主角”可能同时具备：

#### 全局稳定身份

- 核心人格底色
- 穿越机制
- 主线目标
- 跨世界记忆保留规则

#### 世界 A 局部身份

- 身份：侯府庶女
- 关系：王府联姻对象
- 能力边界：不会修仙
- 当前任务：活过宫斗线

#### 世界 B 局部身份

- 身份：星际军校候补生
- 关系：军校同期竞争者
- 能力边界：可驾驶机甲
- 当前任务：洗脱嫌疑

这三层如果都被揉进一张 `CharacterProfile`，结果通常会变成：

- 信息互相污染
- 模型拿错世界的人设
- 关系对象串场
- 能力系统穿模
- prompt 中出现互相矛盾的设定

所以这里不是“补几个字段”能解决的，而是：

**实体事实必须分层，并且带作用域。**

### 24.2 参考项目有没有类似解决方案

我这轮继续查了参考项目，结论是：

#### 有一些“局部状态”意识

它已经在这些地方摸到问题边缘：

1. `character_states`
2. `organization_states`
3. `plot_stage`
4. `story_direction`
5. `phaseLabel / stageId / stageLabel`
6. `relatedTimelineIds`

这说明它承认：

- 角色状态会变
- 组织状态会变
- 不同章节 / 阶段读取的上下文不一样
- 时间线和阶段标签可以帮助限定状态

#### 但没有正式解决“多世界局部覆盖”

我没有看到它有一套明确的：

- world / arc / route / universe scope
- 角色局部覆盖卡
- 世界线分支覆盖
- 同名角色跨世界身份分离
- 同一关系在不同作用域下的并存状态

也就是说，参考项目目前更像：

**有阶段级状态更新能力，但仍主要建立在单一主世界、单一角色主卡的思维上。**

这对普通长篇够用，对快穿 / 多世界并不够。

### 24.3 参考项目真正能给我们的启发

虽然它没有完整答案，但它给了两个很重要的启发：

1. 局部变化不该直接覆盖全局主卡
2. 阶段 / 时间线标签是未来作用域系统的前身

我们自己仓库里也已经有：

- `CharacterStageStateRecord`
- `stageId / stageLabel`
- `TimelineRecord.phaseLabel`
- `relatedTimelineIds`

这意味着我们不是从零开始。

但现在这些更像：

- 阶段说明
- 时间线关联

还不是真正的：

- 作用域覆盖系统

### 24.4 我们应该如何重新定义“角色卡”

后续不能再把角色理解成“单张卡片”，而应该拆成三层：

#### 第一层：角色主档案

例如：

- `CharacterCanonicalProfile`

只放跨作用域稳定的东西，例如：

- 稳定 id
- 核心人格底色
- 跨世界真实身份
- 主线动机
- 不会轻易改变的底层约束

#### 第二层：作用域身份覆盖

例如：

- `CharacterScopeOverlay`

用于描述角色在某个世界 / 分卷 / 副本 / 路线中的局部设定：

- 当前名字 / 马甲
- 当前身份 / 阵营 / 职业
- 当前能力边界
- 当前关系网络
- 当前公开人设
- 当前世界的禁忌与规则约束

#### 第三层：阶段状态记录

例如：

- `CharacterStageStateRecord`

用于描述在某个作用域内部，随着章节推进产生的动态变化：

- 当前状态
- 当前情绪 / 伤势 / 立场
- 当前已知信息
- 当前任务进度
- 关联时间线

也就是说：

**主档案回答“这个人本质是谁”，作用域覆盖回答“这个人此时此地以什么身份存在”，阶段状态回答“这个身份现在发展到哪一步了”。**

### 24.5 世界观也必须允许局部覆盖

这个问题不只发生在角色上，也发生在世界规则上。

例如：

#### 全局规则

- 存在多世界穿梭机制
- 主角能保留部分跨世界记忆
- 每次进入新世界会获得局部身份

#### 世界 A 规则

- 古代宫廷世界，无超凡力量
- 社会规则由礼法和皇权主导

#### 世界 B 规则

- 机甲文明，技术伦理和军权主导

#### 幻境 / 副本规则

- 时间流速异常
- 死亡不等于真正死亡

所以世界观也应拆成：

1. `WorldCanonicalRules`
2. `WorldScopeOverlay`
3. `LocalSceneOrDungeonOverride`

### 24.6 关系、组织、伏笔同样需要作用域

这个问题不是只靠角色和世界观拆层就能解决。

#### 关系

同两个人在不同世界可以是：

- 仇敌
- 师徒
- 恋人
- 不相识

所以关系不能只有一份全局记录。

#### 组织

某个组织可能：

- 只存在于某一个世界
- 只在卷一成立，卷二瓦解
- 只对某个身份线有效

#### 伏笔

某条伏笔可能：

- 是全局主线伏笔
- 是世界 A 专属伏笔
- 是副本 B 的局部伏笔

因此：

- 关系记录要带 scope
- 组织档案要带 scope
- 伏笔记录也要带 scope

### 24.7 continuation package 还需要一个正式“作用域系统”

前面文档里我们已经有：

- 全局圣经层
- 分卷 / 分阶段摘要层
- 章节摘要层
- 尾部窗口层

现在还要再补一个正交维度：

**作用域层**

我建议正式引入类似：

- `ContinuationScope`

它至少要支持几类 scope：

1. `global`
2. `world`
3. `arc`
4. `volume`
5. `route`
6. `instance` / `dungeon`
7. `chapter_window`

并且要支持：

- 父子关系
- 覆盖优先级
- 激活条件

例如：

- 全局主角卡
  - 世界 A 覆盖
    - 世界 A 第三阶段状态
  - 世界 B 覆盖
    - 世界 B 副本 2 状态

### 24.8 运行时读取策略也要改

后续续写时，不应该再简单地：

- 读全局角色卡
- 读最近章节

而应该变成：

1. 先确认当前 active scope
2. 读取该 scope 的世界规则覆盖
3. 读取该 scope 的角色身份覆盖
4. 读取该 scope 内的阶段状态
5. 回退补全全局稳定事实
6. 再读取最近章节窗口

也就是：

**先定位当前在哪个世界 / 路线 / 副本，再决定哪些角色卡和规则是真正生效的。**

### 24.9 我们当前仓库里哪些东西可以复用，哪些还不够

#### 可以复用的

1. `CharacterStageStateRecord`
2. `TimelineRecord`
3. `relatedTimelineIds`
4. `phaseLabel / stageId / stageLabel`
5. 已有的结构化资产：
   - `CharacterProfile`
   - `WorldRuleSet`
   - `RelationshipRecord`
   - `ForeshadowRecord`

这些已经说明我们项目里有：

- 主档案
- 阶段记录
- 时间线关联

#### 还不够的

现在缺的是：

1. 正式 scope 实体
2. 作用域覆盖档案
3. 覆盖优先级与回退规则
4. 当前 active scope 的运行时解析
5. 拆书阶段自动识别“哪些信息是全局，哪些是局部”

也就是说，我们已经有“状态记录零件”，但还没有“作用域骨架”。

### 24.10 拆书阶段要特别新增的识别任务

如果未来支持拆书承接快穿 / 多世界作品，拆书阶段不能只抽：

- 角色
- 世界观
- 关系
- 时间线

还要额外抽：

1. 世界 / 副本 / 路线切换点
2. 哪些角色是跨世界同一实体
3. 哪些名字只是局部身份
4. 哪些关系只在局部生效
5. 哪些规则是全局规则，哪些只在某世界有效
6. 哪些伏笔是全局主线伏笔，哪些是局部任务伏笔

也就是拆书结果里要允许出现：

- `scope map`
- `entity alias mapping by scope`
- `scope-local relationship set`
- `scope-local rule set`

### 24.11 产品层怎么避免把用户搞晕

虽然底层要支持 scope，但产品层不应该一上来就把“作用域系统”三个字砸给用户。

更合理的是在 UI 上用用户能理解的词：

- 世界
- 卷 / 篇章
- 路线
- 副本
- 当前承接线

然后系统内部再映射成统一 scope 模型。

这样：

- 普通小说用户几乎感知不到复杂度
- 快穿 / 多世界用户才会看到更细的作用域管理

### 24.12 这轮补充后的新结论

到这里，前面的 continuation package 结论还要再往前推进一步：

**它不只是“全局圣经 + 摘要 + 状态表”，还必须是“全局事实 + 作用域覆盖 + 阶段状态”的组合。**

参考项目目前没有把这件事完整解决，它更多只走到了：

- 局部状态更新
- 阶段标签
- 时间线关联

但这已经足够说明方向：

**局部变化必须独立成层，不能继续粗暴覆盖全局主卡。**

所以如果后续我们真的要把拆书承接做成适用于：

- 快穿
- 多世界
- 大地图换区
- 分卷换身份
- 支线 / route 分叉

的正式框架，那么“作用域覆盖系统”不再是锦上添花，而是基础设施。

## 25. 还要再上提一层：这不只是“多世界支持”，而是“特殊剧情连续性机制”支持

你这次补得很对，而且我认为这比前一轮“多世界 / 快穿”还更底层。

快穿其实只是一个例子。

真正的问题不是：

- 要不要支持快穿
- 要不要支持多世界

而是：

**我们的系统能不能正确理解“某些剧情机制会改变事实的连续方式”。**

这类机制包括但不限于：

- 快穿
- 多世界并行
- 死亡回归
- 读档 / 恢复存档
- 时间回溯
- 回档线
- 梦境线 / 幻境线
- 模拟副本 / 试炼副本
- 伪身份覆盖
- 支线 / route 分叉
- 平行结局线
- 记忆保留但世界重置
- 世界不重置但人物认知重置

所以如果我们把框架写成：

- “支持快穿”
- “支持多世界”

这种按题材名枚举的方式，迟早会越补越碎。

更正确的做法是把它统一抽象成：

**连续性机制（continuity mechanics）**

## 25.1 为什么“作用域”还不够

上一轮我已经把 scope 补出来了，但现在要明确：

**scope 很重要，但 scope 只解决“哪里生效”，还不解决“怎么连续”。**

例如：

### 快穿

重点问题是：

- 当前在哪个世界
- 同一角色在该世界以什么身份存在

这主要是 scope 问题。

### 死亡回归

重点问题却变成：

- 哪些事实会回滚
- 哪些记忆不会回滚
- 谁知道“上一轮”发生过什么
- 回归后哪些关系应该恢复到旧状态，哪些应该保留痕迹

这已经不是单纯 scope 能解决的。

### 读档 / 恢复存档

重点问题是：

- 哪些资产回到旧快照
- 哪些元事实保留
- 当前正文分支是否要替换、分叉还是并存

这更像是 continuity transition 问题。

所以：

**scope 是事实作用域；continuity mechanics 是事实如何跨作用域、跨阶段、跨回滚点延续或重置。**

这两个必须分开。

## 25.2 我认为应该正式引入“连续性合同层”

如果前面已经有：

- `ContinuationScope`

那么这里还需要再补一层，例如：

- `ContinuationMechanic`
- `ContinuityTransitionPolicy`
- `ContinuityFrame`

名称后面可以再定，但语义上至少要有这样一层。

它的职责不是描述“这是哪种题材”，而是描述：

**当前作品里，事实的保留、重置、分叉、合并、显隐规则是什么。**

## 25.3 特殊剧情机制真正需要建模的，不是题材名，而是这几种维度

我建议把这类问题统一拆成下面几个维度。

### 第一维：身份连续性

问题是：

- 当前角色是否还是“同一实体”
- 是否只是换了局部身份
- 名字变了是不是同一个人
- 某角色在不同线里是不是同一 canonical entity

这对应：

- `entity identity continuity`

### 第二维：记忆连续性

问题是：

- 主角是否记得上一轮
- 配角是否记得
- 世界是否记得
- 只有读者知道，角色不知道，算不算运行时事实

这对应：

- `memory carry-over policy`

### 第三维：状态连续性

问题是：

- 角色状态是否保留
- 伤势、装备、情绪、关系进度是否回滚
- 组织势力、社会局势是否回滚

这对应：

- `state persistence / reset policy`

### 第四维：因果连续性

问题是：

- 上一轮做过的事对这一轮是否仍有影响
- 某个失败结局是否只是废线，还是会留下因果痕迹
- 回档后伏笔是否需要重新埋，还是保留“已发生过”的元信息

这对应：

- `causal continuity policy`

### 第五维：分支连续性

问题是：

- 新剧情是覆盖旧线
- 从旧线分叉
- 还是回到某个快照继续同线改写

这对应：

- `branch / overwrite / fork policy`

### 第六维：显隐连续性

问题是：

- 哪些事实对角色可见
- 哪些事实只对系统可见
- 哪些事实只对读者视角成立

这对应：

- `knowledge visibility policy`

### 第七维：回收连续性

问题是：

- 伏笔在回档后是否仍算“已埋”
- 关系变化在新线是否要重新建立
- 任务线索在副本结束后是继承还是清空

这对应：

- `artifact carry-forward policy`

这七个维度一旦建出来，快穿、死亡回归、读档、多世界这些都只是不同参数组合，而不再是需要单独发明一套框架的题材名。

## 25.4 用几个例子看，为什么这套抽象更稳

### 例子一：快穿

它通常表现为：

- 身份连续性：全局同一主角，局部身份变化
- 记忆连续性：主角保留，局部角色不保留
- 状态连续性：多数局部状态按世界切换重置
- 因果连续性：主线任务累计保留，局部支线不保留
- 分支连续性：一个世界结束后进入下一个 scope

### 例子二：死亡回归

它通常表现为：

- 身份连续性：同一主角
- 记忆连续性：主角保留，其他角色大多不保留
- 状态连续性：世界回滚，主角某些内部状态保留
- 因果连续性：外部事实重置，但主角认知构成元因果
- 分支连续性：在同一世界 scope 内多轮 replay

### 例子三：恢复存档

它通常表现为：

- 身份连续性：同一批实体
- 记忆连续性：取决于机制设定，可能全回滚，可能主角保留
- 状态连续性：回到某个快照
- 因果连续性：快照之后的线要么废弃，要么形成分叉
- 分支连续性：覆盖或派生分支

### 例子四：普通长篇小说

它的参数其实也只是：

- 身份连续性：稳定
- 记忆连续性：正常连续
- 状态连续性：正常连续
- 因果连续性：正常累计
- 分支连续性：单线

这恰恰说明：

**一般项目不是例外，相反它只是特殊剧情机制框架下的默认参数集。**

所以这套设计不是“为了少数题材加复杂度”，而是给所有项目一个统一底座。

## 25.5 这对一般项目同样有意义

这里必须特别说清楚，不然容易误会成：

“这是为了快穿这类少见题材，给系统加很多负担。”

其实不是。

即使是最普通的项目，也仍然会遇到这些低配版问题：

- 角色前后身份变化
- 世界规则在某卷后扩展
- 主线 / 支线分离
- 梦境、回忆、幻觉章节
- 章节级回退重写
- 某段剧情作废后改写

也就是说，普通项目只是：

- 默认单世界
- 默认单主线
- 默认不回档
- 默认事实连续

而不是根本没有 continuity 规则。

所以正确的架构姿势应该是：

- 一般项目走默认值
- 特殊项目覆盖默认值

而不是：

- 一般项目走一套系统
- 特殊题材再额外造一套平行系统

## 25.6 continuation package 需要新增的，不只是 scope，还有“连续性策略”

到这里，continuation package 至少应该包含两类不同但相关的东西：

### A. 事实结构

例如：

- canonical facts
- scope overlays
- stage states
- timelines
- foreshadows

### B. 连续性策略

例如：

- 当前项目默认 continuity mode
- 哪些实体跨 scope 保持同一 identity
- 哪些状态进入新 frame 后重置
- 哪些记忆可跨 frame 保留
- 遇到回档时采用覆盖、分叉还是快照恢复

没有 B，A 很快会在特殊剧情里失效。

## 25.7 运行时真正需要解析的，应该是“当前连续性帧”

前面我们谈的是 active scope，但现在还要再补一个概念：

- `active continuity frame`

因为一个 frame 不只告诉系统：

- 现在在哪个世界 / 副本 / 路线

还要告诉系统：

- 当前是正常推进、回归后重跑、读档恢复、平行支线，还是梦境线
- 这条线与父线是什么关系
- 当前该继承哪些事实，屏蔽哪些事实

也就是说，续写时真正应该先解析的是：

1. 当前 active continuity frame
2. 该 frame 对应的 active scope 链
3. 该 frame 的 continuity transition policy
4. 再据此拼运行时上下文

## 25.8 这套能力不能绑定在拆书阶段，它应该是一般项目与拆书项目共享的底层能力

这里必须再明确纠正一次：

**连续性机制系统不是拆书项目专属能力。**

更准确的关系应该是：

1. 一般项目创建时，也应允许声明或逐步形成自己的连续性机制
2. 拆书项目只是多了一条“从既有作品中反向提取 continuity hints”的输入路径
3. 两者后续都应该落到同一套 runtime continuity 底座

也就是说：

- 一般项目：从创作规划、开局对话、后续运行中逐步建立 continuity facts
- 拆书项目：从既有文本中反向抽取 continuity facts

但最后服务的都不是“拆书子系统”，而是：

**整个写作工程共享的连续性底座。**

### 对一般项目，这意味着什么

即使用户不是拆书，而是直接新建一个普通项目，系统也应能支持：

- 单线默认连续
- 章节改写后的旧线处理
- 梦境 / 幻觉等局部异常段
- 分支路线
- 设定扩容后的规则继承
- 死亡回归 / 回档 / 存档恢复这类特殊剧情机制

所以这里不该理解成：

- “拆书时额外分析一下特殊机制”

而应该理解成：

- “写作系统本身就要有 continuity layer，拆书只是其中一种填充方式”

### 拆书阶段额外要做的，只是“提取”

如果未来要支持从现有作品拆书承接这些特殊机制，那么拆书阶段除了抽 scope 外，还应尽量识别：

1. 是否存在明显回档 / 回归节点
2. 记忆保留规则是否在文本中可见
3. 是否存在同一角色多身份但同实体
4. 是否存在读者知道、角色不知道的循环信息
5. 某些支线是否已废弃但仍影响主角认知
6. 某些伏笔是否需要跨轮次、跨世界累计

也就是说，拆书结果除了 `scope map`，还应尽量产生：

- `continuity hints`
- `reset / carry-over hints`
- `entity identity mapping hints`
- `branch interpretation hints`

它们一开始可以只是推断性较强的 hints，不一定一上来就要求 100% 结构化确定。

### 对架构的最终落点

所以更准确的架构表述应该是：

1. `ContinuityLayer` 是所有写作项目共享的基础设施
2. `BookDeconstruction` 只是它的一个高密度输入来源
3. `GeneralNovel / LongTaskNovel / DeconstructionDerivedProject` 都读取同一套 continuity runtime contract

## 25.9 产品层怎么安排才不让用户崩溃

底层很复杂，但产品层不能让用户一进来就面对：

- continuity policy
- branch carry-over
- causal reset mode

这些词。

更合理的是：

### 默认情况

系统默认为：

- 单线连续
- 正常状态累积
- 无特殊回滚

### 检测到明显特殊机制时

再用用户懂的话呈现：

- 有跨世界承接
- 有回归 / 回档机制
- 有多路线分支
- 有局部身份覆盖
- 有跨线记忆保留

### 高级设置

再允许用户细调：

- 记忆保留
- 状态回滚
- 分支覆盖/并存
- 伏笔是否跨线继承

这样就能做到：

- 一般用户不被吓到
- 特殊剧情用户又有足够控制力

## 25.10 这轮深挖后的最终修正

所以我现在会把前一轮的结论再修正得更准确一点：

不是：

**我们只需要一个“作用域覆盖系统”。**

而是：

**我们需要“作用域覆盖系统 + 连续性机制系统”。**

前者回答：

- 事实在哪一层、哪一域生效

后者回答：

- 这些事实如何保留、重置、分叉、继承、显隐

只有这两层同时存在，我们的 agent 才能真正稳妥地写：

- 普通长篇
- 快穿
- 多世界
- 死亡回归
- 读档重开
- 梦境/幻境线
- 路线分支

而且更重要的是，这套设计对普通项目也同样成立，因为普通项目只是它的默认、最简单配置。

如果再用一句更不容易误解的话收束：

**拆书项目需要这套能力，但并不拥有这套能力；这套能力本来就应该属于整个写作系统。**
