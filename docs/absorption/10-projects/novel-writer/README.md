# novel-writer 吸收档案

## 1. 项目定位

- 来源项目：`references/novel-writer-main`
- 主要类型：以 CLI / 斜杠命令为入口的“规格驱动小说创作方法论与项目骨架”
- 许可证：`MIT`
- 我们参考它的原因：
  - 它不强调 GUI，而强调“项目如何被 AI 助手理解和推进”
  - 它把小说创作拆成一套很明确的方法论、命令集、模板集、跟踪文件和专家角色
  - 它和我们当前“策略优先、core 共用、agent/skill/模板资产化”的方向天然接近

## 2. 总判断

`novel-writer` 最值得我们吸收的，不是某个具体工具实现，而是它把“小说创作流程”做成了：

- 一套方法论
- 一套命令协议
- 一套项目骨架
- 一套规范文件
- 一套追踪文件
- 一组专家角色

它和前几份参考项目的气质不同：

- `AIxiezuo` 更像最小小说生成骨架
- `Writingway` 更像桌面写作工作台
- `Ai-Novel` 更像工程化资产平台
- `novel-writer` 更像“策略与规范驱动的创作操作系统”

所以它对 NovelAgent 最大的价值在于：

- 强化策略层
- 强化项目内标准资产模板
- 强化长任务前置规范
- 强化 agent / skill / workflow 的标准入口设计

## 3. 可吸收精髓

### 3.1 七步方法论非常适合映射到我们的策略层

它的核心方法论是：

1. `/constitution`
2. `/specify`
3. `/clarify`
4. `/plan`
5. `/tasks`
6. `/write`
7. `/analyze`

这套流程的价值，不是名字本身，而是它明确区分了：

- 价值观层
- 需求层
- 决策层
- 设计层
- 执行层
- 验证层

这和我们现在已经在强调的：

- `project_strategy`
- `mode_strategy`
- `workflow_strategy`

非常契合。

NovelAgent 不需要照抄这七步，但非常值得吸收它的分层思路：

- “开局引导”不是直接写正文
- “长任务规划”不是直接执行任务
- “修订与分析”不是生成顺手附带

这特别适合进入：

- 一般小说项目的引导链
- 长任务模式 1 的开局链
- 长任务模式 2 的全书共识链

### 3.2 Constitution 非常适合成为我们的正式资产

它把 `/constitution` 放在第一步，而且给了很完整的模板：

- 核心价值观
- 质量底线
- 风格原则
- 内容原则
- 读者契约
- 修订流程

这个东西和我们现在已有的“风格”“长期约束”“去 AI”“模式引导结果”之间，其实差一点就能接起来。

我认为它最值得吸收的地方是：

1. 创作原则不应只是对话里的一段约束
2. 这些原则应该有稳定文件位置
3. 它们应参与后续任务、分析、重写、检查

对 NovelAgent，最自然的落点是：

- `project constitution` 作为项目级共享资产
- 可以是 `spec/constitution.md`、`AGENT.md` 扩展块，或我们自己的标准文档
- 在 core 中作为正式上下文来源，不暴露传输层原始 prompt

这会直接增强：

- 长任务模式的长期一致性
- 风格守恒
- 分析与重写依据

### 3.3 它的模板不只是“模板”，而是“项目标准文件骨架”

它的 `templates/` 下不是只有 prompt，而是一整套项目骨架：

- `writing-constitution-template.md`
- `story-template.md`
- `outline-template.md`
- `knowledge/*`
- `tracking/*`
- `commands/*`

这点特别重要。

也就是说，它不是简单让 AI 帮写，而是先给项目建立：

- 故事模板
- 大纲模板
- 世界设定模板
- 人物档案模板
- 追踪模板
- 命令模板

这非常适合我们吸收为：

- 新建项目骨架模板
- 项目类型模板
- 长任务模式模板
- 资产初始文件模板

比起随手新建一堆空白目录，这套思路更“有骨架”。

### 3.4 Tracking 文件体系很值得吸收

它单独做了：

- `plot-tracker.json`
- `timeline.json`
- `relationships.json`
- `character-state.json`
- `validation-rules.json`

这说明它非常明确地把“写作后的维护对象”单独拆出来了。

这一点和我们的方向高度一致，只是它仍偏 JSON 文件表达。

可吸收的核心思想是：

1. 情节追踪是正式资产
2. 时间线不是临时备注
3. 关系网应有专门文件
4. 角色状态应可被验证
5. 验证规则也是项目资产

对 NovelAgent，我们应进一步升级成：

- Markdown 可读层
- SQLite 索引层
- 统一资产服务

但“这些对象本身必须存在”这一点，值得完整吸收。

### 3.5 它把 `/write` 命令做成了“执行包”而不是一句写作提示

`templates/commands/write.md` 很值得看。

它在执行写作前，明确规定 AI 要先查询：

- constitution
- specification
- creative plan
- tasks
- tracking
- knowledge
- 前文
- 风格参考
- 反 AI 规范

这个思路极其适合我们。

也就是说，一个真正的“写作动作”不是：

> 用户点了生成 -> 发一句 prompt

而应该是：

> 根据当前任务类型，装配一份正式执行包

这和我们现在已经有的这些东西是直接接得上的：

- task execution plan
- context assembler
- long task transaction
- mode guidance assets
- project file context sections

它给我们的启发是：

- 每类任务应有明确的上下文查询顺序
- 执行前提醒和验证应成为规则，而不是 UI 文案
- 模式、风格、追踪、前文都应有优先级

### 3.6 它把“分析/检查/修复”也做成了标准工作流

它不仅有 `/analyze`，还有：

- `/checklist`
- `/track`
- `/timeline`
- `/relations`

尤其 `track` 的说明很值得注意：

- 可以做完整追踪报告
- 可以做深度一致性检查
- 甚至可以有 `--fix`

这对我们很有启发：

1. review / analysis / validation 不是附加功能
2. 它们应是项目内正式动作
3. 分析结果应能继续驱动修复任务

这和我们现在已有的：

- review report
- revision follow-up
- checkpoint review
- repair task

是高度可融合的。

### 3.7 Experts 目录很像“专家策略包”

它单独做了：

- `experts/core/plot.md`
- `experts/core/style.md`
- `experts/core/character.md`
- `experts/core/world.md`

这很像一种轻量的“专长角色”体系。

对我们来说，这特别适合转译成：

- 内置 agent profile
- 内置 skill package
- 专家策略模板

也就是说，它不是一定要变成“多个会话专家面板”，但非常适合变成：

- 可选专家智能体
- 可选分析视角
- 可选 prompt 片段

这对一般协作和长任务都很有价值。

### 3.8 它把项目骨架和 AI 平台适配分开，方向很对

它支持多个 AI 平台，但真正稳定的不是平台壳，而是项目本身的文件结构与命令语义。

这对我们的启发是：

- GUI / CLI 都只是入口
- 项目内资产、策略、模板、追踪结构才是核心

这和我们一直坚持的：

- core 优先
- GUI / CLI 最大复用

是一致的。

### 3.9 “反 AI 味 / 自然表达规则”这类项目内规范很值得吸收，但要更结构化

它在 `write.md` 中已经开始塞大量“去 AI 味”规则，比如：

- 段落结构
- 黑名单表达
- 具象化检查
- 抽象表达替换

虽然这些内容现在还比较“写在命令里”，但其核心价值很高：

1. 风格与自然表达规范应成为正式资产
2. 写作前、写作后、分析时都应复用这些规则

对 NovelAgent，我建议不要把这类规则只留在命令模板中，而应拆成：

- 风格资产
- 自然表达规则资产
- 去 AI 约束资产
- 分析检查规则资产

这样 GUI / CLI / 长任务都能共用。

### 3.10 它很适合作为“标准项目初始化器”的参考

`novel-writer` 最终给人的感觉是：

它很会“搭一个让 AI 接手更稳定的项目目录”。

这对我们很关键，因为我们现在也在不断明确：

- 新建项目后默认有哪些目录
- 中文只是映射显示，物理目录应稳定
- 项目骨架要能支撑后续智能体和工具工作

它能帮我们继续想清楚：

- 项目级标准目录
- 项目级标准资产文件
- 命令/模板/规则与项目的关系

## 4. 对 NovelAgent 的架构落点

### `core`

最适合进入 `core` 的吸收点：

- 创作方法论的分层映射
- 任务级上下文查询顺序规则
- constitution / specification / tracking 这类资产在执行链中的优先级
- 分析 -> 修复 -> 回看 的共享流程
- 专家策略描述

### `adapters`

- 项目模板初始化器
- 项目骨架写入器
- 标准追踪文件仓储
- 标准资产模板导入器

### `app`

- 新建项目时的项目骨架选择
- 项目级 constitution / specification / outline / tracking 编辑入口
- 专家模式选择器
- 分析/检查/修复工作流入口

### `ui`

- 项目初始化向导
- 标准模板浏览与编辑页
- 追踪面板
- 宪法/规格/大纲/任务分解面板
- 专家面板或专家选择入口

## 5. 可服务的策略

### `project_strategy`

强相关：

- 一般小说项目
- 长篇项目

中相关：

- 拆书项目
- 短文集项目

原因：

- 它主要提供的是项目骨架和规范，不局限于某一种创作体量

### `mode_strategy`

强相关：

- `seed_autopilot_novel`
- `full_outline_consensus`

中高相关：

- 一般协作模式
- 灵感模式进入正式规划后的阶段

它特别适合“先规范后执行”的模式，而不是“一上来直接写”的模式。

### `workflow_strategy`

最适合服务：

- 项目开局引导
- 规格生成
- 章节规划
- 任务分解
- 章节写作执行包装配
- 分析检查
- 修复与回看

## 6. 与现有设计的融合点

### 6.1 与我们的策略优先文档高度契合

它是目前几份参考里，和我们 `docs/strategy-first-predesign.md` 最接近的一份。

它能帮助我们把“策略模式”再落实一层：

- 不是只说 strategy
- 而是让每个策略拥有：
  - 前置资产
  - 标准文件
  - 执行流程
  - 检查流程

### 6.2 与我们的 agent / skill 标准化直接相关

它的 command / expert / memory / template 体系，对我们非常像：

- skill
- agent
- template
- project asset

所以它特别适合帮助我们进一步收紧：

- 通用核心字段
- NovelAgent 扩展字段
- 项目内标准文件协议

### 6.3 与我们的长任务模式特别能融合

它最大的价值之一，是它能帮我们把长任务模式前几步做得更稳：

- 先定宪法
- 再定规格
- 再澄清
- 再规划
- 再分任务
- 再执行

这和你前面一直要求的“不要一上来就糊成一坨，让模式职责清楚”非常一致。

### 6.4 与我们的双存储设计融合

它是文件先行的，而我们是 `Markdown + SQLite` 双轨。

所以最自然的融合方式是：

- 吸收它的标准文件骨架
- 用 SQLite 给这些文件建索引和运行支撑

这样既保留人可读性，也保留运行效率。

## 7. 不应吸收的部分

### 7.1 它的斜杠命令格式本身

不需要追求兼容它的命令前缀系统。

我们吸收的是：

- 命令语义
- 流程拆分
- 文件结构

而不是复制它的 CLI 交互形态。

### 7.2 大量命令内嵌长提示词文本

这种做法对“命令模板仓库”很自然，但对我们来说，如果直接照搬，会让：

- skill
- agent
- prompt
- strategy

之间边界重新糊掉。

我们应把其中的价值拆到更细的资产里。

### 7.3 过度文件化而缺少运行层抽象

它很强于文件骨架，但弱于正式运行时。

这意味着：

- 它适合指导我们的策略和模板层
- 不适合直接指导我们的 runtime 设计

## 8. 后续实施候选

### 近期可做

1. 正式定义项目级 constitution 资产
2. 把 specification / outline / tracking 标准模板纳入项目初始化
3. 给模式开局和项目开局接入标准骨架生成
4. 把“执行前上下文查询顺序”做成 core 规则，而不是散落在 prompt 文本里
5. 把专家策略拆到内置 agent / skill / template 体系

### 中期可做

1. 做项目级追踪面板
2. 做“分析 -> 修复 -> 回看”标准流水线
3. 做可复用的项目模板市场 / 包

### 暂缓观察

1. 直接兼容它的多 AI 平台命令格式
2. 将长篇写作全部寄托在超长命令模板文本上

## 9. 当前结论

`novel-writer` 对我们的价值，是把“小说 Agent 应该如何有章法地工作”说得非常清楚。

它提醒我们：

- 项目不只是目录，更是规范集合
- 创作不只是生成，更是先立标准、再做决策、再执行、再验证
- tracking、constitution、outline、experts 这些都应成为正式资产

如果 `Writingway` 提醒我们“工作台要像工作台”，  
那 `novel-writer` 提醒我们的就是“策略和项目规范要像策略和项目规范”，不能只是散乱功能的集合。
