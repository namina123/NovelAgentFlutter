# book-os 吸收档案

## 1. 项目定位

- 来源项目：`references/book-os-main`
- 主要类型：面向 AI 写作工具的“分层上下文 + 指令工作流 + 全局标准库”体系
- 许可证：`MIT`
- 我们参考它的原因：
  - 它不是传统 GUI 应用，而是把“如何让 AI 稳定参与小说创作”整理成了一套可安装、可复用的工作系统
  - 它对“全局标准、项目标准、稿件标准”三层上下文的拆分非常清晰
  - 它把命令入口、工作流指令、专用 agent、写作标准文档明确分层，特别适合我们当前强调的策略模式与 core 共用方向

## 2. 总判断

`book-os` 和前几份参考项目有一点明显不同：

- `AIxiezuo` 更像早期生成器骨架
- `Writingway` 更像桌面工作台
- `novel-writer` 更像方法论与规范骨架
- `book-os` 更像“把 AI 写作协作流程产品化后的上下文操作系统”

它最值得 NovelAgent 吸收的，不是某个命令文本，也不是它对 Claude / Cursor 的宿主接法，而是这几条更底层的思想：

- 把上下文分成全局标准层、项目层、稿件层
- 把长工作流拆成命令层、执行指令层、专职 agent 层
- 用 lite 文档为上下文预算服务
- 用条件读取和条件跳过，减少无意义重复上下文
- 把“写作、分析、连续性检查、版本管理”都视为正式工作流，而不是聊天附带功能

所以它对 NovelAgent 最大的价值，在于补强：

- 上下文装配规则
- 资产层的全局/项目/稿件分域
- 工作流节点的职责切分
- 内置专家 agent 的角色边界
- 长任务执行中的版本/校验/复盘链

## 3. 可吸收精髓

### 3.1 三层上下文模型非常适合成为我们的长期基座

它在 README 里直接把上下文拆成三层：

1. `Standards`
2. `Novel`
3. `Manuscripts`

这不是普通目录约定，而是一种很强的运行思想：

- 第一层回答“你一贯怎么写”
- 第二层回答“这本书是什么、为什么写、遵守什么”
- 第三层回答“当前这次具体写什么”

这个拆法和我们现在正在做的很多事是可以严丝合缝接上的：

- 全局风格/写作原则
- 项目 constitution / guidance / style center
- 当前长任务 / 章节 / 任务 / 追踪资产

对 NovelAgent 来说，这特别适合沉成一套正式合同：

- `global asset scope`
- `project asset scope`
- `manuscript/task asset scope`

也就是说，后面不管是 GUI 还是 CLI，都不应该把“所有上下文来源”揉成一锅，而应先分域，再由策略决定取哪些域、取多少、以什么优先级取。

### 3.2 Command / Instruction / Agent 三层拆法很值得吸收

它的结构不是简单几个命令文件，而是明确分了三层：

- `commands/*.md`
- `instructions/core/*.md`
- `claude-code/agents/*.md`

其中：

- `commands` 更像用户入口和宿主桥接层
- `instructions` 是正式工作流规则层
- `agents` 是专职子角色定义

这对我们特别重要，因为它说明真正稳定的系统不能把这三件事混在一起：

1. 用户如何触发
2. 工作流到底怎么走
3. 哪些子能力负责哪个步骤

NovelAgent 完全值得吸收这条分法，并映射到我们自己的架构：

- `app/ui`：入口和交互呈现
- `core workflow`：正式流程编排
- `agent/skill assets`：专长角色和策略包

这会直接帮助我们避免把流程细节继续堆进某个大控制器或某个巨型提示词文件里。

### 3.3 “Lite 文档”是非常实用的上下文预算策略

`book-os` 明确区分了：

- `premise.md` 和 `premise-lite.md`
- `story-outline.md` 和 `story-outline-lite.md`

而且这些 lite 文件不是装饰，它们就是为了“efficient AI context usage”存在的。

这点很值得我们完整吸收。

因为它说明：

1. 不是每次都该读完整资产
2. 资产需要有“完整视图”和“压缩视图”
3. 压缩视图本身应是正式资产，而不是临时摘要字符串

这和我们现在已有的：

- summary
- context budgeter
- generation record
- session history

正好可以接起来。

对 NovelAgent 更好的做法是：

- 核心资产保留 Markdown 完整版
- 为可高频注入的资产生成 lite / summary 版本
- SQLite 只负责索引、检索和状态，不替代用户可读文档

### 3.4 条件读取和“如果已在上下文中则跳过”的思想很成熟

它在 `standards/writing-style.md`、`narrative-techniques.md`、`instructions/core/*.md` 里大量使用了：

- 如果某段规则已经在当前上下文中，就跳过
- 只有当前任务真的需要某类规则时，才读取对应标准
- 描写、体裁等规则按任务类型按需引入

这对我们很有启发。

因为这不是简单的“省 token”，而是更进一步的运行纪律：

- 上下文拼装应有去重
- 上下文拼装应有条件门控
- 上下文拼装应有任务相关性判断

这非常适合继续增强我们的 core：

- `context section dedup`
- `conditional asset injection`
- `task-sensitive section selection`

后面不管是一般项目、长任务模式，还是拆书、灵感模式，这套规则都能复用。

### 3.5 它的 plan -> outline -> write -> analyze 是很清楚的一条写作闭环

当前公开的几条主命令是：

- `plan-novel`
- `create-outline`
- `write-scenes`
- `analyze-manuscript`

虽然数量不多，但闭环很清晰：

1. 新建项目并建立项目层资产
2. 将故事拆成结构化大纲和任务
3. 按任务写场景/章节
4. 对既有稿件做分析并补建资产

这条闭环对我们有两个很强的启发：

1. 一般小说项目与长任务模式，实际上都需要“起步、结构化、执行、分析”四大段
2. 旧稿导入分析不应只是工具，而应是正式的模式入口

这和你前面一直强调的“项目类型与模式是平行策略，不是某个模式附属按钮”是完全一致的。

### 3.6 分析既服务新项目，也服务既有稿件接管

`analyze-manuscript.md` 的重点不只是“分析文本”，而是：

- 先理解现有稿件状态
- 再反推出项目文档
- 再把老稿件纳入标准工作流

这一点特别值得我们吸收。

因为它意味着分析模式不是单纯出一个 review 报告，而是可以承担：

- 项目迁入
- 老稿项目接管
- 资产初始化
- 写作风格侦测
- 当前阶段定位

对 NovelAgent，这可以直接映射成一个正式策略：

- `existing_project_adoption_strategy`

这会服务：

- 打开已有项目时的初始化
- 导入旧工程
- 旧稿自动补建 constitution / style / timeline / tracking

### 3.7 写作流程里显式加入版本管理与备份，非常适合进入我们的运行基座

`write-scenes.md` 里不是写完就完了，它在中间和末尾显式调用了：

- manuscript version management
- backup
- progress update
- version checkpoint

并且专门定义了一个 `writing-workflow` agent 负责这条链。

这说明它把“稿件保护”和“执行留痕”看成写作过程本身的一部分，而不是事后补丁。

这和我们当前已经有的：

- execution record
- checkpoint review
- review report
- revision resolution

很容易融合。

可吸收的核心思想是：

1. 每次执行后应有结构化留痕
2. 重要节点应有回退点
3. 进度统计和状态更新不应依赖用户手工维护

### 3.8 专职 agent 的边界感很适合我们的内置 agent/skill 设计

它内置的 agent 包括：

- `writing-workflow`
- `prose-reviewer`
- `continuity-checker`
- `date-checker`
- `context-researcher`
- `manuscript-creator`

这些 agent 的价值不在于名字，而在于它清楚地把职责拆开了：

- 有的只负责搜集上下文
- 有的只负责创建文档
- 有的只负责连续性检查
- 有的只负责版本/备份流程

这正是我们项目一直在强调的：

- 单一职责
- 工具与策略解耦
- 核心逻辑可复用

对 NovelAgent，这很适合进入两层：

- 内置 agent profile
- 内置 skill / workflow step 包

同时也提醒我们：

- 不要让“主智能体”承担过多隐式职责
- 子智能体或子步骤应有可识别、可替换、可裁剪的边界

### 3.9 Standards 目录非常像“全局写作标准中心”

它单独维护：

- `writing-style.md`
- `narrative-techniques.md`
- `genre-guides/*`

这和我们当前已经准备做的：

- 风格中心
- 智能体默认写作偏好
- 项目 constitution 约束

是可以很好拼接的。

重要的启发不是这些标准文件本身，而是它承认了一件事：

- 有些规则不是某一本书专属
- 有些规则应当被多个项目复用
- 有些规则要按体裁、任务、场景按需注入

因此我们也应正式保留一层：

- `global writing standards`

它可以是用户级资产，而不是某个项目内部文件。

### 3.10 它很适合我们第一种长任务模式的“全权托管写作”骨架

你前面已经明确提出一种长任务模式：

- 人类只提供灵感、走向、世界观等
- 后续大量写作推进交由智能体

`book-os` 恰好很适合作为这个模式的参考骨架，因为它天然强调：

- 先计划
- 再结构化
- 再按任务写
- 再回看与分析
- 写的同时维护稿件状态

也就是说，它不像某些项目那样更偏“陪聊式创作”，而更偏“带执行纪律的写作代理”。

这对我们第一种长任务模式的策略层非常有帮助。

## 4. 对 NovelAgent 的架构落点

### `core`

- 新增或补强“多域上下文模型”：
  - 全局标准域
  - 项目域
  - 稿件/任务域
- 强化上下文装配器的：
  - 条件注入
  - 已读去重
  - lite 资产优先
- 将“分析旧稿并补建资产”建成正式 use case / strategy
- 将版本检查点、执行留痕、进度更新继续统一到 workflow runtime
- 为 agent/skill 引入更明确的“专职角色包”边界

### `adapters`

- 用户级标准资产读写 adapter
- lite/full 双视图资产生成与索引 adapter
- 已有稿件扫描与分析 adapter
- 项目 adoption / import 初始化 adapter
- 版本与备份落盘 adapter

### `app`

- 项目创建时区分：
  - 新建小说项目
  - 接管已有稿件项目
- 长任务模式入口明确：
  - 计划阶段
  - 大纲阶段
  - 章节执行阶段
  - 分析与修订阶段
- 让设置与会话装配能读取用户级全局标准

### `ui`

- 新建项目引导中展示“创作标准”“项目风格”“稿件结构”的区别
- 资产面板中区分：
  - 全局标准
  - 项目资产
  - 稿件资产
- 在会话或任务详情里展示“本轮实际注入了哪些上下文域”
- 为 lite/full 资产提供明确但不打扰的切换与说明

## 5. 可服务的策略

### `project_strategy`

- 一般小说项目
- 既有稿件接管项目
- 拆书/分析型项目

### `mode_strategy`

- 长任务模式 1：人类给灵感，智能体持续推进
- 长任务模式 2：先共识全书走向，再按计划推进
- 一般协作模式下的“分析现有项目”“补建资产”子模式

### `workflow_strategy`

- 项目初始化工作流
- 大纲生成工作流
- 章节生成工作流
- 旧稿分析接管工作流
- 连续性检查与修订工作流
- 版本检查点与回滚工作流

## 6. 与现有设计的融合点

### 6.1 与资产层

它最自然的融合点，是把我们现在已有但还没完全产品化的几条线重新归整：

- 风格中心
- constitution / guidance
- 角色卡 / 伏笔 / 时间线 / 关系网
- 章节任务 / 执行记录 / 复盘记录

`book-os` 提醒我们，这些资产不仅要存在，还要先分域，再决定如何注入。

### 6.2 与会话层

我们已经在做会话策略和上下文策略，这个项目能进一步帮助我们明确：

- 会话不是直接读一切
- 先按任务类型选域
- 再在域内选 lite/full
- 再去重、裁剪、排序

这会让 GUI 与 CLI 共用的核心更稳。

### 6.3 与工作流层

它的 `command -> instruction -> agent` 结构，很适合映射成我们自己的：

- `entry use case`
- `workflow orchestration`
- `step-specific services`

这样后面新增模式时，不至于把流程判断到处散落。

### 6.4 与工具层

虽然它本身主要是文档驱动，不是工具系统驱动，但它对我们有一个重要提醒：

- 有些动作本质上不是“给模型一个工具”
- 而是“运行时框架自己要做的步骤”

比如：

- 读取必要文件
- 选择 lite/full 上下文
- 更新进度
- 建立备份点

这些更像 runtime 责任，而不是暴露给模型的普通工具。

### 6.5 与运行调度层

它很适合作为我们长任务调度器的一组行为参考：

- 开局先建项目层资产
- 写作前做上下文选择和环境检查
- 执行后做回写、计数、备份、复盘

这一点和我们已经有的 runtime / checkpoint / review / revision 体系能相互补强。

### 6.6 与导入导出层

它对“分析既有稿件并纳入系统”的重视，说明导入层不应只停留在：

- 导入一堆文件

而应该进一步支持：

- 扫描
- 识别
- 补建项目资产
- 建立初始任务与状态

## 7. 不应吸收的部分

- 不吸收它对 `Claude Code`、`Cursor` 的宿主写法：
  - 这些是外部宿主耦合层，不适合成为我们的内部标准
- 不吸收具体命令名和命令文案：
  - 我们需要策略入口，不需要复刻斜杠命令表面形式
- 不吸收它把全局安装目录写死为 `~/.novel-os/` 的做法：
  - 我们已有跨平台项目根与用户目录策略，尤其移动端不能照搬
- 不吸收它文档里与具体宿主工具强绑定的执行描述：
  - 我们必须保持 GUI/CLI 共核，而不是绑定某一宿主交互习惯
- 不吸收任何可构成实现级转译的具体大段工作流文本：
  - 这里依旧只吸收思路、边界与能力切分

## 8. 后续实施候选

### 近期可做

- 在 core 里补强“全局域 / 项目域 / 稿件域”上下文分域模型
- 为高频资产正式加入 lite/full 双视图
- 把“已有稿件接管”整理成独立 project strategy
- 将当前上下文策略补上“已读去重”和“任务按需注入”规则

### 中期可做

- 内置一组更清晰的专家 agent / skill profile：
  - 连续性检查
  - 风格校验
  - 项目分析接管
  - 版本与复盘辅助
- 在 GUI 中展示实际注入的上下文域和资产来源
- 让长任务执行记录更明确地区分：
  - 计划阶段
  - 大纲阶段
  - 正文阶段
  - 分析阶段

### 暂缓观察

- 是否需要面向用户暴露“全局标准中心”的完整编辑体验
- 是否需要把 environment check 之类的弱宿主步骤产品化
- 是否需要引入更细粒度的“多专职 agent 并行协作”界面表达
