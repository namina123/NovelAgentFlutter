# AIxiezuo 吸收档案

## 1. 项目定位

- 来源项目：`references/AIxiezuo-main`
- 主要类型：`Python + Flask + LangChain` 的早期本地小说生成工具
- 许可证：`MIT`
- 我们参考它的原因：
  - 它代表了一类很典型的“小说生成器”思路：模板驱动 + 状态 JSON + 章节正文文件 + 会话记忆
  - 虽然形态较早，但它把“章节状态”“世界设定”“模板组”“多小说隔离”“前文正文参与生成”这些核心要素都落成了具体文件结构
  - 它对我们很有价值，因为它能提醒我们哪些“看似朴素但非常实用”的能力，必须在新项目里有更正规、可扩展的实现

## 2. 总判断

`AIxiezuo` 不像 `Ai-Novel` 那样偏工程化平台，也不像 `MuMuAINovel` 那样偏完整产品闭环。

它更像一个早期但方向明确的小说 Agent 原型，强项在于：

- 明确把“正文”和“状态”分开
- 明确把“世界设定”和“章节推进”分开
- 明确把“模板”从代码里抽出来
- 明确支持“多小说项目隔离”
- 明确意识到“只靠聊天记忆不够，必须读前面章节正文”

所以它最值得我们吸收的，不是 UI，也不是 LangChain 包装，而是这些基础理念：

- 文件级项目隔离
- 模板组三件套
- 状态文件与正文文件并存
- 前文正文参与生成
- 会话记忆压缩
- 多版本草稿/版本对比雏形

## 3. 可吸收精髓

### 3.1 小说项目的最小可用骨架非常清楚

它的目录组织非常直白：

- `data/`：状态和世界设定
- `xiaoshuo/`：章节正文
- `templates/`：模板组
- `prompts/`：默认提示词
- `versions/`：章节多版本
- `memory/`：会话消息与压缩摘要

这个结构对我们最大的启发是：

一个小说项目的可用性，不需要一开始就有巨量复杂对象，但一定要有几类分开的持久层：

1. 正文层
2. 状态层
3. 设定层
4. 模板层
5. 会话层
6. 版本层

这和我们现在正在做的 `Markdown + SQLite` 双兼容其实是同方向的。

对 NovelAgent 的可吸收做法是：

- 保留用户可见、可浏览的文档/目录结构
- 同时用结构化索引层承接状态、运行和检索
- 不把所有东西都塞进一类“项目文件”

### 3.2 模板组三件套非常值得吸收

它把模板拆成了三种文件：

- `writer_role`
- `writing_rules`
- `update_state_rules`

看起来朴素，但这个拆法很有价值，因为它至少区分了三件事：

1. 角色定位
2. 写作行为规则
3. 状态更新规则

这对我们的启发是：

- “负责写正文的约束”和“负责更新资产的约束”不应该混在一起
- 不同任务应该有不同模板入口
- 模板不应该只有一个大 system prompt

我们不必照搬这三个名字，但可以吸收它的基本分法，落成更正规的模板层：

- `role blocks`
- `writing policy blocks`
- `asset update policy blocks`
- `task prompt presets`

它特别适合服务：

- 一般小说项目
- 长任务模式 1 的正文阶段
- 长任务模式 2 的正文与修订阶段
- 未来的状态更新 / 角色卡更新 / 世界设定补全

### 3.3 “章节状态 JSON”是非常早但非常有用的资产化意识

它的 `ChapterState` 结构虽然简单，但方向是对的：

- 主角
- 物品
- 关系
- 当前剧情摘要

这说明它已经意识到：

- 正文不是唯一事实来源
- 章节推进会改变角色状态
- 角色状态要在下一章继续被引用

我们不应该照搬它的字段，但应该吸收这个意识，并把它升级成我们的资产层语言：

- 角色资产
- 身份映射
- 关系资产
- 当前阶段剧情摘要
- 局部章节状态投影

它的价值在于，它证明了“哪怕是很轻的结构化状态，也比完全依赖聊天历史强很多”。

### 3.4 世界设定单独存档是必须保留的

它把 `world_bible` 单独存成 JSON，这一点很重要。

因为它天然区分了：

- 稳定设定
- 剧情推进状态

对于 NovelAgent，这个边界必须保留，而且应进一步升级：

- 世界规则
- 职业/等级体系
- 地点
- 势力
- 物品与法则

这些都不该只作为一大段文本附在系统提示词里。

也就是说，`AIxiezuo` 的世界书虽然还很早期，但已经指向我们现在的“设定资产中心”。

### 3.5 “读取前面章节正文”这件事必须保留

这是这个项目最实用、也最值得我们直接吸收的点之一。

它明确加入了：

- `use_previous_chapters`
- `previous_chapters_count`

而且不是只读记忆摘要，而是直接读前面的章节正文文件。

这说明它已经发现一个非常真实的问题：

- 只靠会话记忆，正文细节容易漂
- 状态 JSON 不足以替代真实前文
- 正文之间的措辞、节奏、行为连续性需要直接读取文件

这个点对我们特别重要。

NovelAgent 应吸收成更正式的策略：

- “状态/设定/记忆”不是“正文窗口”的替代品
- 正文窗口是独立上下文来源
- 读取多少章、读摘要还是读正文、读尾部还是读整章，应该是上下文策略的一部分

这尤其适用于：

- 一般小说项目的续写
- 长任务模式 1 的章节连续生成
- 长任务模式 2 的按大纲稳定写作

### 3.6 多小说隔离的思路很朴素，但非常实用

它通过 `novel_id` 做了项目隔离：

- 状态文件前缀隔离
- 世界设定文件前缀隔离
- 正文文件前缀隔离
- 版本文件前缀隔离

这虽然是早期做法，但对我们有两个重要提醒：

1. 项目隔离必须是物理隔离，不只是 UI 里的切换
2. 会话、正文、状态、设定、版本都要跟项目绑定

在我们这里，这个思想应该进化成：

- 项目根目录隔离
- 项目内结构固定
- 项目索引与运行记录绑定
- 资产、工具、长任务、会话全部跟项目作用域绑定

### 3.7 会话记忆分片和压缩，是很值得继续吸收的

它在 `main.py` 里做了：

- `MemoryChunkManager`
- `MemoryIndexManager`
- `MemoryCompressor`
- `MemoryManager`

即便实现还比较早期，但它抓住了两个本质问题：

1. 历史不能无限增长
2. 历史需要分片和压缩，否则会拖垮上下文

而且它不是只说“压缩一下”，而是做了：

- chunk
- summary
- index
- recent messages
- range load

对我们来说，这非常值得吸收为更正规的 core 能力：

- 会话窗口策略
- 会话分段记录
- 历史压缩摘要
- 可回放原文与压缩文并存

这部分适合同时服务：

- 普通协作会话
- 长任务运行记录
- CLI 会话

### 3.8 状态更新与正文生成是两条链，但彼此联动

它有单独的 `update_state()`，会基于：

- 旧状态
- 本章正文

再生成新状态。

这个思路很值得保留，因为它天然就是：

- 正文生成链
- 资产更新链

二者分开，但有明确依赖关系。

对于 NovelAgent，我们应当把它吸收成更广义的“派生资产更新链”：

- 正文生成后
- 角色状态可更新
- 世界设定可补全
- 伏笔可登记
- 关系可更新

这样就不只是“更新角色 JSON”，而是统一进入共享派生资产链。

### 3.9 多版本章节是非常朴素但很有用的能力

它有 `versions/` 目录和章节版本文件，这说明它已经意识到：

- 一次生成不是最终稿
- 同一章可能有多个候选版本
- 版本应该可保留、可比较

这对我们当前工作台很有启发：

- 草稿不应该只有一个
- 章节应支持候选版本
- 版本不只是临时文本，而是可记录的资产

对 NovelAgent，适合升级成：

- 草稿分支
- 版本对比
- 接受/退回/重试
- 重写来源链

### 3.10 细纲文件独立存在，也很有价值

它在 `xiaoshuo/zhangjiexigang/{novel_id}/{chapter}.txt` 里存章节细纲，并提供读取接口。

这意味着它天然区分了：

- 章纲
- 正文
- 状态

这和我们的项目结构目标是一致的。

虽然它的命名方式不必照搬，但“章纲是一级资产，不是聊天消息里的临时内容”这一点必须吸收。

## 4. 对 NovelAgent 的架构落点

### `core`

最适合进入 `core` 的吸收点：

- 模板组拆分原则
- 正文 / 状态 / 设定 / 章纲分离原则
- 前文章节读取策略
- 会话分片与压缩窗口策略
- 正文生成后派生状态更新的合同
- 草稿/版本资产模型

### `adapters`

- `Markdown + SQLite` 双轨存储实现
- 项目目录与命名映射
- 文件级正文读取器
- 会话 chunk / summary 仓储
- 版本文件读写

### `app`

- 模板管理状态
- 项目隔离与项目切换
- 版本列表与版本对比
- 设定编辑入口
- 章纲读取与套用流程

### `ui`

- 模板编辑器
- 设定版本浏览与编辑面板
- 章节版本列表
- 章纲导入/读取入口
- 会话摘要/历史查看入口

## 5. 可服务的策略

### `project_strategy`

强相关：

- 一般小说项目
- 长篇项目

中相关：

- 短文集项目

较弱相关：

- 拆书项目

原因很简单：  
它本质上是一套“持续写小说”的最小骨架，对标准小说项目最有帮助。

### `mode_strategy`

强相关：

- `seed_autopilot_novel`
- `full_outline_consensus`
- 一般协作续写模式

中相关：

- 灵感后进入正文阶段的模式

它对“前期采集灵感”帮助有限，但对“进入持续写作后如何稳住上下文”帮助很大。

### `workflow_strategy`

最适合服务：

- 单章续写
- 多章连续写作
- 状态更新
- 章纲到正文
- 草稿版本保存与比较
- 会话摘要压缩

## 6. 与现有设计的融合点

### 6.1 与我们的双存储设计融合

它特别适合补强 `docs/storage-dual-compatibility-design.md` 里的“可读文件层”。

也就是说，我们可以吸收它的这些表达形态：

- 正文以文档存在
- 状态有结构化文件投影
- 世界设定有独立文件投影
- 章纲独立成文件

然后由 SQLite 去承担：

- 索引
- 查询
- 最近版本
- 运行记录

### 6.2 与我们的长任务设计融合

它虽然没有完整长任务系统，但它给长任务很重要的两个提醒：

1. 正文连续性不能只靠长期记忆，要直接读前文
2. 状态更新要和正文推进联动

这两个点都可以直接增强我们已有的长任务模式。

### 6.3 与我们的模板 / Prompt 体系融合

它的三件套模板可以直接作为一个早期范式，帮助我们进一步稳住：

- 角色类模板
- 写作类模板
- 资产更新类模板

后续完全可以让它们映射到我们的：

- Prompt preset
- Prompt block
- task-specific template asset

## 7. 不应吸收的部分

### 7.1 早期 LangChain 封装方式

不建议吸收：

- 把 provider 兼容寄托给 LangChain 类型分发
- 在业务主文件中直连具体模型 SDK

原因：

- 我们已经有自己的 provider 合同和兼容层方向
- 继续沿这种方式走会把传输层和业务层重新揉在一起

### 7.2 单文件承载太多职责

`main.py` 很典型地把：

- 模型配置
- 模型调用
- 状态管理
- 记忆管理
- 正文生成
- 状态更新

揉在了一个文件里。

这个结构绝对不能吸收。

我们只能吸收它的职责划分意识，不能吸收它的落地形式。

### 7.3 过于轻量的状态 schema

它的状态 JSON 是有用的，但过于简化。

我们不能停留在：

- 主角
- 物品
- 关系
- 当前剧情摘要

而应把它升级成更完整的资产层。

### 7.4 Web 端的原始交互形态

它的前端更多是功能演示，不适合直接参考我们的 UI 方案。

我们只吸收“要有哪些入口”，不吸收“界面该长什么样”。

## 8. 后续实施候选

### 近期可做

1. 把“前文章节正文读取策略”继续正式化
2. 把章纲资产与正文资产的边界继续拉清
3. 把草稿版本记录和版本对比继续推进
4. 把状态更新链纳入共享资产派生链
5. 把会话压缩窗口与章节上下文窗口的策略明确分开

### 中期可做

1. 做模板组管理的真正 GUI 入口
2. 做设定版本浏览与比较
3. 做项目内章纲目录和正文目录联动

### 暂缓观察

1. 继续沿它的旧式 LangChain 业务封装走
2. 继续用松散 JSON 直接代表全部资产层

## 9. 当前结论

`AIxiezuo` 的价值不在“先进”，而在“抓住了小说生成工具最早也最真实的几个硬需求”：

- 模板要能换
- 小说要能隔离
- 状态要能存
- 世界设定要独立
- 前文章节要能读
- 会话历史要能压
- 草稿版本要能留

这些点如果新项目做丢了，再漂亮的架构也会虚。

所以它很适合作为我们的“基础写作骨架参考源”，尤其适合回填到：

- 正文上下文策略
- 模板层
- 章纲/正文/状态/设定分层
- 会话压缩与项目隔离
