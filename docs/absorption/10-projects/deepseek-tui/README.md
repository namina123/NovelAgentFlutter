# DeepSeek-TUI 吸收档案

## 1. 项目定位

- 来源项目：`references/DeepSeek-TUI-main`
- 主要类型：终端原生的本地 Agent runtime / TUI / 工具编排系统
- 许可证：`MIT`
- 我们参考它的原因：
  - 它不是小说产品，但它在“本地 agent 怎样稳定运行”这件事上做得非常完整
  - 它把工具执行、审批、记忆、任务、线程、子智能体、MCP、运行时 API 拆得很清楚
  - 它对我们最大的价值，不在 UI 风格，而在共享 core runtime 的设计经验

## 2. 总判断

`DeepSeek-TUI` 和前面几份参考项目的气质完全不同。

前几份更偏：

- 小说创作方法论
- 写作资产组织
- 工作台交互
- 写作流程策略

而 `DeepSeek-TUI` 更偏：

- agent runtime
- 工具表面设计
- 会话寿命管理
- 持久任务与恢复
- 本地 API 集成

所以它对 NovelAgent 最值得吸收的，不是“终端长什么样”，而是“我们的 GUI / CLI 共用底座该怎样更稳”。

它最有价值的几条经验是：

- 把模式与审批拆开
- 把工具做成结构化表面，而不是全靠 shell
- 把线程 / 回合 / 事件 / 任务做成可持久恢复的数据模型
- 把大型输出、子智能体结果、长分析结果从主上下文中搬出去
- 把用户级记忆与项目级指令严格区分
- 把本地 runtime API 当作正式集成面，而不是附属调试功能

对 NovelAgent 来说，这一份参考主要服务的是：

- core 运行层
- 工具调度层
- 会话与上下文层
- GUI / CLI / 未来移动端宿主的统一后端接口

## 3. 可吸收精髓

### 3.1 模式与审批是两层，不应揉成一个开关

它明确区分了：

- `Plan / Agent / YOLO` 这种“交互模式”
- `suggest / auto / never` 这种“审批模式”

这个区分非常重要。

因为它说明：

1. 用户当前想做什么，与
2. 工具该被多严格地拦截，

其实不是同一个维度。

这对 NovelAgent 的启发很直接：

- “一般协作模式 / 长任务模式 / 分析模式”是策略层
- “允许哪些工具、是否自动执行、是否要求确认”是权限/审批层

我们不该把“策略类型”和“安全策略”写死在一起。

这特别适合沉到 core 合同里，变成：

- `interaction_mode`
- `approval_policy`
- `tool_execution_policy`

### 3.2 工具表面必须是结构化的，不能让 shell 吃掉一切

`docs/TOOL_SURFACE.md` 的设计立场非常清楚：

- 专用结构化工具优先
- 只有专用工具不合适时才落回 shell
- 不保留“并不比 shell 更好”的重复工具

这点对我们很有用。

因为它能约束我们后面继续扩工具时，不至于越做越乱。

对 NovelAgent 来说，这意味着：

1. 文件、目录、搜索、计划、任务、回放、恢复这类高频动作，尽量走结构化工具
2. 真正平台差异大、长尾型、宿主相关的动作，再走 shell / 宿主 adapter
3. 工具名和工具职责要稳定，不要同义别名乱飞

这会直接提升：

- 智能体选工具的稳定性
- OpenAI / Anthropic / Gemini 等兼容层下的工具调用成功率
- 工具结果的可回放与可解释性

### 3.3 持久线程 / 回合 / 事件时间线，非常适合我们统一 GUI 和 CLI

它把 runtime 数据模型做成了：

- `Thread`
- `Turn`
- `Item lifecycle`
- `Event stream`

而不是只有一堆临时聊天消息。

这特别值得我们吸收。

因为我们自己的 NovelAgent 现在虽然已经有：

- session
- history
- execution record
- long task record

但还可以继续向更统一的数据模型收束。

最值得吸收的思想是：

1. GUI 看的是线程与事件时间线
2. CLI 看的也应是同一条线程与事件时间线
3. 任务、工具、回放、打断、恢复都应附着在这条时间线之上

这能帮助我们后续继续做好：

- 长任务运行回放
- 出错后重试
- 工具证据展示
- 断点恢复

### 3.4 大型输出必须外置，主上下文只留决策级摘要

它专门做了：

- `retrieve_tool_result`
- `handle_read`
- `var_handle`

核心思想非常好：

- 工具输出可能很大
- 子智能体结果可能很大
- 长日志可能很大
- 但父会话不需要一次吞完整内容

这对我们是一个非常直接的提醒。

NovelAgent 后面应继续强化：

- 工具结果摘要
- 结果句柄 / 结果引用
- 按片段读取
- 主会话只保留“决策所需摘要”

这和你之前一直强调的“不要让上下文被无意义内容拖垮”完全同向。

它特别适合服务：

- 长任务日志
- 审稿报告
- 工具回放
- 大型资产分析
- 探针测试结果留存

### 3.5 子智能体应是持久会话，不只是一次性调用

`DeepSeek-TUI` 的子智能体表面非常克制：

- `agent_open`
- `agent_eval`
- `agent_close`

而且它强调的是：

- 独立上下文
- 独立生命周期
- 可并发运行
- 完成后回传摘要和证据

这一点非常适合我们。

因为我们的 NovelAgent 本来就不是单一问答器，后面无论是：

- 写作
- 审稿
- 连续性检查
- 风格检查
- 伏笔回收检查

都可能需要多智能体协作。

从它这里最值得吸收的不是“并发很多个”本身，而是：

1. 子智能体要有角色类型
2. 子智能体要有清晰输出合同
3. 父会话拿摘要和证据，不是把子会话完整转录回来

这会帮助我们把多智能体保持在可控范围内。

### 3.6 用户记忆和项目指令必须分层

`docs/MEMORY.md` 里区分得非常明确：

- 用户记忆：跨项目、跨会话的持久偏好
- 项目指令：仓库/项目级规范

这对我们特别关键。

因为 NovelAgent 现在既有：

- 项目级 `agent.md`
- 项目资产
- 智能体设置
- 用户设置
- 未来还会有风格偏好和长期习惯

这几层如果不分清楚，很容易互相污染。

它给我们的清晰结论是：

1. 用户级偏好要独立存储
2. 项目级规范要跟项目走
3. 长任务状态不要写进用户记忆
4. 短期会话状态不要冒充长期记忆

这套边界非常值得写进我们自己的基石文档与 core 合同里。

### 3.7 会话寿命管理是第一等公民，不是后补优化

它对长会话退化这件事非常坦诚，也给出了明确策略：

- 早用子智能体
- 批量读搜索
- 积极压缩
- 大分析放到 RLM / 外部上下文
- 主会话保持精简

这点对我们太重要了。

因为 NovelAgent 的长任务天然就是长会话高风险区。

它最值得吸收的不是具体阈值，而是这套操作纪律：

1. 主线程只保留协调和决策
2. 大体量分析丢到专用环境
3. 每轮都要考虑上下文预算
4. 长任务要随时可压缩、可接力、可恢复

这能继续增强我们已经在做的：

- context budgeter
- session history
- relay / handoff
- checkpoint review

### 3.8 Runtime API 非常值得我们视作正式宿主接口

它把 `serve --http` 和 `doctor --json` 做成了明确的本地集成面。

这件事的价值很大：

- UI 不一定总要直接嵌进 runtime
- 也可以通过本地服务协议来接
- 自动化、外部 supervisor、未来其他宿主都能接同一套 contract

这对 NovelAgent 是很大的启发。

即便我们当前 Flutter GUI 和 CLI 仍共用 Dart core，也值得继续保留一个抽象方向：

- 能否逐步形成本地 runtime contract
- 让 GUI / CLI / 探针 / 自动化脚本走同一个可观测接口

不用照搬它的 HTTP 设计，但“要有稳定集成面”这点非常值得吸收。

### 3.9 MCP 与外部工具接入，应走同一审批与可观测框架

它对 MCP 的处理很成熟：

- 工具命名统一
- 配置路径明确
- 管理入口清晰
- 仍走同一审批体系
- 明确哪些操作需要重启才能进入模型可见工具池

这对我们也非常有价值。

因为后续 NovelAgent 无论是：

- 引第三方工具
- 接本地扩展
- 接移动端受限宿主能力

都需要一个清楚的外部能力接入层。

值得吸收的核心思想是：

1. 外部工具不是特殊公民
2. 一样需要权限、诊断、状态、可见性
3. 外部工具的配置改动与运行时可见性要分清楚

### 3.10 配置分层非常清楚：全局、项目覆盖、环境变量

`docs/CONFIGURATION.md` 里把：

- 全局配置
- 项目 overlay
- 环境变量覆盖

边界划得很清楚。

这正好契合我们已经在推进的方向：

- 桌面端默认目录可配置
- 移动端默认目录受宿主约束
- 项目设置要能覆盖用户设置
- CLI 侧依赖同目录配置

它最值得我们吸收的是分层覆盖思想，而不是它具体的 TOML 形态。

对 NovelAgent 最合适的落点是：

- 用户级设置
- 项目级设置
- 会话/运行级临时覆盖

而且每层都要有明确的优先级和可解释性。

### 3.11 回滚与恢复必须是正式能力

它把：

- fork
- backtrack
- restore
- side-git snapshot

分成几种不同的恢复路径，而不是一个“撤销”按钮包打天下。

这特别值得我们吸收它的概念区分：

1. 会话分叉
2. 工作区文件恢复
3. 长任务从检查点继续
4. 会话历史回退

这些其实不是同一种事。

NovelAgent 后面如果把这几个动作分清楚，用户体验会稳很多，也更不容易误操作。

## 4. 对 NovelAgent 的架构落点

### `core`

- 继续明确：
  - `interaction_mode`
  - `approval_policy`
  - `tool_execution_policy`
- 收束共享 runtime 数据模型：
  - thread
  - turn
  - item/event timeline
  - durable task
- 补强大型输出句柄化与摘要化读取
- 继续规范子智能体合同、角色类型、结果摘要格式
- 明确用户记忆 / 项目指令 / 会话状态 / 长任务状态的边界
- 进一步强化上下文寿命管理与压缩纪律

### `adapters`

- 本地任务持久化 adapter
- 工具结果 spill / artifact adapter
- 本地 runtime contract adapter
- 外部工具 / MCP 风格接入 adapter
- 用户级设置与项目级覆盖 adapter

### `app`

- GUI 与 CLI 共用相同任务、线程、恢复、重试入口
- 让探针、自动化测试、后台执行也走统一 runtime 合同
- 将项目设置、用户设置、临时运行设置做清晰分层

### `ui`

- 更清楚地区分模式切换与审批/权限切换
- 会话里只显示精炼工具摘要，详细内容按需展开
- 长任务页显示线程、回合、事件、检查点和工具证据
- 重试、恢复、继续、回滚这些入口要按动作类型分清楚

## 5. 可服务的策略

### `project_strategy`

- 一般小说项目
- 长任务小说项目
- 导入/接管已有项目

### `mode_strategy`

- 一般协作模式
- 长任务模式 1
- 长任务模式 2
- 分析 / 审稿 / 修订模式

### `workflow_strategy`

- 长任务调度
- 多智能体协作
- 工具执行与证据回放
- 出错重试与恢复
- 任务持久化与断点续跑

## 6. 与现有设计的融合点

### 6.1 与资产层

它对我们最大的提醒是：

- 资产正文、资产摘要、工具证据、运行记录不要混成一种对象

这会帮助我们把：

- Markdown 资产
- SQLite 索引
- 工具产物
- 运行日志

继续分开。

### 6.2 与会话层

它非常适合继续补强我们当前的：

- session history
- context assembler
- user-visible relay
- compact / handoff

特别是“主会话精简、外部结果句柄化”这一点。

### 6.3 与工作流层

持久任务、事件时间线、子智能体角色、恢复路径这些能力，很适合直接增强我们的 workflow runtime。

### 6.4 与工具层

它几乎整份都在提醒我们：

- 工具要结构化
- 工具结果要可摘要
- 工具结果要可重取
- 外部工具也要走同一框架

这与我们当前继续迁移工具链的方向是高度一致的。

### 6.5 与运行调度层

它最适合补强的就是这一层。

尤其是：

- durable task
- retry / resume
- background work
- subagent orchestration
- event replay

这些都直接关系到 NovelAgent 真正“能长时间稳定可用”。

### 6.6 与导入导出层

它的运行 API 与本地 contract 思想提醒我们：

- 导出不只是文件导出
- 也可以有运行状态、线程摘要、任务证据的导出或重建入口

这对我们后面做项目级备份与迁移也有帮助。

## 7. 不应吸收的部分

- 不吸收它的终端键位、终端渲染和 ratatui 具体实现：
  - 这些是终端宿主特性，不适合搬到 Flutter
- 不吸收它 DeepSeek 专属的模型默认、推理档位和提供商优先级：
  - 我们需要更通用的多提供商抽象
- 不吸收它面向编程代理的部分专用工具表面：
  - NovelAgent 主要还是小说项目，不需要把编程向工具表面全量照搬
- 不吸收它的远程运维、腾讯云、飞书桥接等宿主耦合方案：
  - 这些超出当前 NovelAgent 核心目标
- 不吸收任何具体实现文本、提示词正文、Rust crate 结构：
  - 我们继续只吸收思想、边界、能力分解

## 8. 后续实施候选

### 近期可做

- 收束共享 runtime 的 thread / turn / event 模型
- 强化工具结果摘要、句柄化和按需重取
- 明确用户记忆、项目规范、会话状态、长任务状态的分层
- 把模式与审批策略从 UI 行为中进一步抽离到 core

### 中期可做

- 为 GUI / CLI / 探针统一一套本地 runtime contract
- 继续规范子智能体角色与输出合同
- 把恢复、重试、回滚、分叉做成清晰的动作体系
- 让长任务回放和工具证据视图真正建立在统一事件时间线上

### 暂缓观察

- 是否需要显式引入类似 RLM 的专用大上下文分析执行面
- 是否需要单独暴露本地 HTTP runtime API
- 是否需要支持更通用的插件 / MCP 市场形态
