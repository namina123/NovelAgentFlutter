# MuMuAINovel 可吸收策略整理

## 目的

本文只整理 `references/MuMuAINovel-main` 中值得被 `NovelAgentFlutter` 吸收的产品策略、数据表达与交互做法。

这里的结论遵守我们当前项目的长期约束：

- 只吸收理念、能力拆分、数据形态、交互经验
- 不照搬它的 React/FastAPI/SaaS 架构
- 继续坚持 GUI 与 CLI 共用 core
- 继续坚持单一职责、接口边界、低耦合、本地优先

## 总判断

`MuMuAINovel` 更适合作为“功能完备度与产品思路参考”，不适合作为“实现模板”。

它的优势主要在三类：

1. 把写作能力做成了结构化资产，而不是一次性 prompt
2. 把很多复杂流程拆成了“分析 -> 建议 -> 执行 -> 回看”的闭环
3. 把若干高价值写作对象做成了独立管理中心，比如伏笔、风格、关系、导入导出

它不适合直接搬来的部分也很明显：

- 账号、登录、云端工坊、后台管理
- Web SaaS 式页面组织
- 服务端数据库先行的状态设计

所以我们应该“吸收能力模型”，而不是“复制页面和后端”。

## 可以重点吸收的部分

### 1. 灵感模式

可吸收。

值得吸收的不是它当前页面形式，而是它把“发散、细化、快速生成、保留上下文”做成了一条独立工作流。对我们来说，这类能力很适合做成项目内的创意会话模式，而不是普通聊天的附庸。

建议落点：

- `core`：灵感会话策略、候选项生成契约、细化规则
- `app`：灵感流程状态、步骤切换、会话暂存
- `ui`：更轻的对话式灵感面板或引导式创建入口

### 2. 自定义写作风格

可重点吸收。

这里最有价值的是把“风格”当作独立资产管理，而不是塞进智能体系统提示词。风格应当可复用、可继承、可导入导出、可设为项目默认值。

建议落点：

- `core`：风格实体、风格叠加规则、默认风格解析
- `adapters`：风格持久化、导入导出
- `ui`：风格列表、编辑器、项目默认风格入口

### 3. 数据导入导出

必须吸收。

`MuMuAINovel` 的导入导出思路是对的：导出不只是备份，而是可迁移、可共享、可校验的数据包。我们应该把项目、角色、组织、风格、模板等资产都纳入统一的 bundle 体系。

建议落点：

- `core`：bundle 元数据、版本号、校验、冲突合并策略
- `adapters`：zip/目录导入导出、文件读写
- `app`：导入预检、冲突预览、覆盖策略
- `ui`：项目导出、角色卡导出、生态包导入入口

### 4. Prompt 调整界面

可吸收，但要重构表达。

我们不该把 prompt 调整做成一堆裸文本拼接，而应做成“模板层、变量层、策略层”三层。可视化编辑有价值，但它应该服务于我们的 `AGENT.md`、`SKILL.md`、模板资产体系，而不是另起一套孤立的文本库。

建议落点：

- `core`：prompt 模板实体、变量槽位、覆盖规则
- `app`：模板应用、恢复默认、对比变更
- `ui`：模板编辑页、预览页、差异查看

### 5. 章节字数限制

可直接吸收。

这是很实用的生成策略输入，应当成为任务参数的一部分，而不是藏在提示词里。它还可以继续扩展为章节目标长度、最小长度、上限提醒等。

建议落点：

- `core`：生成参数对象、字数目标约束
- `ui`：章节任务、长任务、重写任务中的统一输入项

### 6. 思维链与章节关系图谱

可吸收思路，不吸收“暴露原始思维链”的表达。

真正值得吸收的是结构化图谱视图：章节关系、冲突、伏笔回收、人物连接、势力结构，而不是把模型原始推理全量展示给用户。我们应当展示“分析结果对象”与“关系结构”，不要展示传输层原文。

建议落点：

- `core`：章节分析结果、关系边、节点语义模型
- `app`：图谱视图模型、过滤器
- `ui`：图谱页、章节分析侧栏、关系检视器

### 7. 根据分析一键重写

必须吸收。

这是“分析 -> 执行”闭环里价值极高的一段。最关键的是把“分析结论”和“重写请求”拆开，让用户能选择是整章重写、局部重写，还是只提炼建议。

建议落点：

- `core`：重写计划、局部重写范围、建议到任务的转换器
- `adapters`：模型执行
- `ui`：分析结果旁的重写动作、局部片段重写入口

### 8. 职业等级体系

可吸收，而且很适合我们的项目定位。

但不能写死为某一题材。它应当成为项目级可配置设定体系的一部分，用统一 schema 表达“职业/境界/组织级别/能力阶梯”等概念。

建议落点：

- `core`： progression schema、等级项、规则引用
- `adapters`：项目内持久化
- `ui`：体系编辑器、引用面板

### 9. 角色/组织卡片导入导出

强烈建议吸收。

这和我们本地资产化方向高度一致。角色、组织、地点、物品等卡片本身就该成为可迁移资产，可以跨项目复用，也能用于新建项目的快速预填。

建议落点：

- `core`：卡片标准结构、验证规则、引用关系
- `adapters`：单卡与卡组导入导出
- `ui`：资产浏览、导入、导出、复制到项目

### 10. 伏笔管理

这是最值得吸收的一批能力之一。

从参考项目里可以吸收到的重点包括：

- 伏笔是独立对象，不是散落在正文里的备注
- 伏笔应有明确状态，如已埋下、待回收、部分回收、已回收、弃用
- 伏笔应能和章节、人物、事件建立关联
- 分析结果应能反哺伏笔状态更新

建议落点：

- `core`：伏笔实体、状态机、关联规则、上下文选择策略
- `app`：伏笔同步服务、章节分析回填
- `ui`：伏笔中心、时间线、待回收提醒

### 11. 提示词工坊

可吸收本地版，暂不吸收社区版。

我们当前不该优先做云端平台、审核、评分社区，但可以做本地的 prompt pack / template pack 机制。也就是说，吸收“可分享模板包”的思路，不吸收“在线工坊平台”的完整产品。

建议落点：

- `core`：模板包元数据、依赖关系、版本信息
- `adapters`：本地包导入导出、索引
- `ui`：本地工坊页、模板包浏览与启用

### 12. 拆书功能

强烈建议吸收。

拆书真正有价值的不是“上传一本书”，而是把外部文本拆成结构化资产：世界观、角色、势力、剧情线、写法特征、章节骨架。它应当是“导入 -> 预览 -> 结构化提取 -> 应用”的分阶段流程。

建议落点：

- `core`：拆书任务、结构化提取结果、应用计划
- `adapters`：txt/epub/doc 等解析
- `app`：多阶段任务编排、失败重试
- `ui`：导入预览、结果确认、应用范围选择

## 暂不建议直接吸收的部分

### 1. Linux DO 自动创建账号 / OAuth

当前不建议吸收。

这属于 SaaS 化能力，与我们现阶段的本地优先桌面端/移动端目标并不一致。最多只作为未来云协作版本的远期参考。

### 2. 社区驱动平台能力

比如：

- 在线模板工坊
- 用户评分评论
- 后台审核
- 云端账号资产同步

这些都不适合作为现在的主线任务。它们会把我们带回旧项目那种重量级方向。

## 我们能吸收的共性策略

### 1. 把高频写作对象都做成资产

包括：

- 风格
- 伏笔
- 角色/组织卡
- 章节分析结果
- 模板包
- 拆书结果

这样它们才真正可复用、可导出、可图形化、可策略化。

### 2. 把复杂流程拆成阶段

最值得学的是：

- 先分析
- 再生成建议
- 再让用户决定是否执行
- 最后保留记录与回放

这比把所有工作都压成一次模型调用更稳。

### 3. 展示结构化结果，而不是暴露底层传输细节

用户真正需要看到的是：

- 哪些伏笔没回收
- 这一章逻辑链怎样
- 哪个建议可一键重写
- 哪个角色关系发生变化

而不是原始调试信息、冗长中间提示词、未加工的响应体。

### 4. 导入导出要从一开始就版本化

这是避免以后生态资产混乱的关键。项目包、卡片包、风格包、模板包都应该有清晰的版本头和兼容策略。

## 对我们当前架构的落位建议

### 应进入 core 的

- 灵感模式策略
- 风格实体与叠加规则
- 导入导出 schema 与验证
- prompt 模板模型
- 字数目标与生成参数
- 章节分析与关系图数据模型
- 一键重写计划
- 职业等级体系 schema
- 角色/组织/地点等卡片标准结构
- 伏笔状态与同步规则
- 拆书任务结构与应用计划

### 应进入 adapters 的

- 本地文件包导入导出
- zip/目录读写
- 外部文档解析
- 模型执行适配
- 本地 SQLite / 项目文件持久化

### 应进入 app 的

- 多阶段用例编排
- 页面间状态同步
- 导入预检结果转换
- 分析结果到 UI 视图模型的组装

### 应进入 ui 的

- 灵感工作台
- 风格编辑器
- 伏笔中心
- 图谱页
- 模板调整页
- 拆书导入向导
- 重写确认与结果回放界面

## 建议的吸收优先级

### 第一优先级

- 伏笔管理
- 风格资产化
- 分析后一键重写
- 资产导入导出

原因：这些能力最能提升“持续创作”的可用性，而且都能沉淀成 GUI/CLI 共用 core。

### 第二优先级

- 灵感模式
- 章节分析与关系图谱
- 职业等级体系
- 角色/组织卡跨项目复用

原因：这批能力能明显提升项目组织与过程反馈，但要建立在基础资产结构稳定之后。

### 第三优先级

- 本地 prompt 工坊
- 拆书完整链路

原因：它们很有价值，但工作量更大，且会依赖前两级能力的稳定数据结构。

## 对当前项目最有价值的直接结论

如果只提炼一句话，就是：

`MuMuAINovel` 最值得我们吸收的不是“页面”，而是“把写作流程中的关键对象做成结构化资产，再把分析、执行、导入导出串成闭环”。`

这和我们当前正在推进的解耦式 Flutter/Dart 架构是相容的，而且能明显减少未来再次走向“逻辑全堆在宿主层”的风险。
