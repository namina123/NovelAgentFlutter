## 1. 本轮最终要解决什么

这几轮讨论，表面上是在谈“知识卡够不够”“要不要 SQLite”“哈利波特同人怎么复用”“科技发展依据怎么沉淀”，但本质上是在谈一个更大的问题：

```text
本项目到底需要一个什么样的“参考 / 证据 / 资料 / 风格 / 原作提取 / 复用”基座，
才能同时服务普通写作、长任务、拆书、拆书续写、解书、总结、评书、未来同人和跨作品引用，
又不把项目做成一团过重、过耦合、用户难懂的系统。
```

最终结论已经很清楚：

1. 当前的 `knowledge card / design element / research note / reference work record` 不应废弃。
2. 但它们也不应被误认为未来完整的大框架。
3. 我们需要的不是“把知识卡继续做大”，而是：
   - 在应用级建立一个更强、更可复用、更可追溯的参考证据基座。
   - 在项目级保留一层轻量、可编辑、可投影、可激活的工作知识能力层。
4. 这两层必须分离。
5. 两层之间只能通过可追溯的派生、挂载、提取、提升来沟通，不能互相糊成一个仓。

因此，本轮的正式架构判断可以概括为一句话：

```text
知识卡体系保留，但降位为项目工作知识能力层；
新的“大框架”单独成为应用级参考证据基座；
两者通过单向派生、挂载和证据链接协作，而不是互相吞并。
```

## 2. 为什么现有知识卡体系不够，但又不能推翻

### 2.1 现有体系为什么不够

从当前代码看，项目信息对象已经有不错的开放性：

1. `ProjectKnowledgeCard`
   - 有 `card_namespace`
   - 有 `card_type`
   - 有 `content_payload`
   - 有 `source_refs / evidence_refs / scope_refs`
   - 有 `activation_policy / usage_policy`
   - 有 `confidence / lifecycle_status`

2. `DesignElementCard`
   - 有开放 `design_payload`
   - 有 `source_refs / evidence_refs / linked_refs`
   - 有 `uncertainty`
   - 很适合承载“命名巧思、象征系统、结构提示、主题手法”

3. `ResearchNote`
   - 已经把 `usable_facts` 和 `creative_suggestions` 分开
   - 已经比很多项目更接近“研究中间层”

4. `ReferenceWorkRecord`
   - 已经在表达“这个外部作品和当前项目是什么关系”
   - 已经在表达“允许怎么用、需要不要确认”

这些对象已经明显不是“一个简陋的 knowledge.md 文件”。

但它们仍然不够承接未来的大框架，原因也很明确：

1. 它们是项目作用域对象，不是应用级可复用对象。
2. 它们的仓储模型是“当前项目里保存一份结构化资料”，不是“全局可复用、可版本化、可分享、可导入导出的资料包”。
3. 它们更适合“本项目此时此刻要用什么”，不适合承载“一个完整原作 / 一个完整神话系统 / 一个完整历史时期 / 一个完整科技演进依据库 / 一套写作风格画像”。
4. 它们没有天然承载 package catalog、版本分支、挂载关系、跨项目复用策略、升级冲突策略。
5. 它们没有解决“同一份原作总结以后反复用于多个项目”“同一份科技发展依据复用于不同世界观项目”“同一风格画像跨项目复用”的问题。

所以，不够是事实。

### 2.2 现有体系为什么不能推翻

虽然不够，但也不能推翻。原因同样很强：

1. 它们已经和当前项目工作流接上了。
2. 它们已经天然适合作为项目运行时的轻量工作知识层。
3. 它们已经有 source/evidence/usage/activation 这些关键字段。
4. 它们已经是“结构化事实源”，而不是纯 prompt 幻觉。
5. 它们当前以 JSON 和投影文件存储，简单、可读、易于调试，适合作为项目层。

因此正确做法不是：

```text
知识卡不够 -> 停掉重做
```

而是：

```text
知识卡不够 -> 重新定位其职责边界
```

也就是：

1. 保留。
2. 不再拔高。
3. 不让它扛应用级复用基座。
4. 让它成为“大框架投射到项目里的工作能力层”。

## 3. 最终分层：我们真正需要的是三层，而不是一层万能仓

### 3.1 总体分层

最终推荐的正式分层如下：

```text
Layer A: 应用级参考证据基座
Layer B: 项目级挂载与可见性层
Layer C: 项目级工作知识能力层
```

### 3.2 Layer A：应用级参考证据基座

这是用户口中的“大框架”。

它的职责不是直接给模型灌 prompt，而是做下面这些事情：

1. 保存可复用的资料包。
2. 保存这些资料包里的结构化内容、来源、证据、版本、许可边界。
3. 为多个项目提供统一挂载入口。
4. 为智能体提供“发现、检索、摘要、精读、导出、投影、提取”的能力。
5. 为未来分享、导入、导出、市场化扩展、社区复用留出空间。

它不是：

1. 某一种项目类型。
2. 某个项目的私有知识目录。
3. 普通用户必须直接理解的数据库界面。
4. 直接暴露给所有智能体任意读取的无限 prompt 仓。

### 3.3 Layer B：项目级挂载与可见性层

这一层负责回答：

1. 当前项目挂了哪些应用级资料包。
2. 当前项目默认能看哪些资料包。
3. 当前项目的智能体在什么权限下可以发现更多资料包。
4. 当前项目是否允许从全局目录里升级检索范围。
5. 当前项目引用的是哪一个版本快照。
6. 当前项目对哪些资料包只是读权限，哪些可以衍生生成项目知识卡。

这一层非常关键，因为它决定了：

1. 不让每个项目默认背上全世界资料。
2. 不让智能体一上来就把整个应用级基座当上下文吃掉。
3. 不让用户被大量技术选项淹没。
4. 不让“应用级可复用资料”和“项目级当前工作集”混在一起。

### 3.4 Layer C：项目级工作知识能力层

这层就是当前的：

1. `ProjectKnowledgeCard`
2. `DesignElementCard`
3. `ResearchNote`
4. `ReferenceWorkRecord`
5. 以及后续围绕它们的 activation、projection、review、linking

这层的职责是：

1. 承接项目当前真正在用的知识。
2. 承接项目运行中新增的研究结果、设计元素、边界记录。
3. 承接从应用级资料包投影/提取出来的“小块、够用、可激活”的工作知识。
4. 支撑普通写作、长任务、拆书、解书的上下文注入。
5. 保持轻量、可编辑、可读、可调试。

这层不承担：

1. 全局资料库。
2. 跨项目原始真源。
3. 复杂版本树。
4. 完整原作包体。

### 3.5 三层之间的关系

这三层关系必须是清晰单向的：

```text
应用级参考证据基座
    -> 通过挂载/检索/提取/摘要
项目级工作知识能力层

项目级运行中产生的新知识
    -> 默认只留在项目层
    -> 只有显式提升时，才升级为应用级可复用资料包
```

也就是说：

1. 项目层可以从应用层派生。
2. 应用层不能被项目层悄悄反写污染。
3. 升级为全局资料必须经过显式 promotion。
4. 任何 promotion 都必须保留来源、证据、版本和审计轨迹。

这点非常重要。

如果这里不守住，未来一定会出现：

1. 项目里随手总结的东西污染全局。
2. 一个劣质 research note 变成全局真相。
3. 风格总结和事实总结混在一起。
4. 用户不知道自己修改的是项目局部还是全局资产。

### 3.6 三层的正式命名

这轮之后，不建议继续在正式文档、代码设计或产品讨论里长期使用“大框架”这个讨论期代号。

它可以继续作为口头代称，但不应再承担正式命名职责。

推荐把三层正式命名为：

1. 应用级：
   - 代码/架构名：`ReferenceEvidenceSubstrate`
   - 中文正式名：`参考证据基座`
   - 用户可见名：`参考资产库`

2. 项目级挂载与可见性层：
   - 代码/架构名：`ProjectReferenceAttachmentLayer`
   - 中文正式名：`项目参考挂载层`
   - 用户可见名：`项目资料挂载`

3. 项目级工作知识能力层：
   - 代码/架构名：`ProjectInformationCapabilityLayer`
   - 中文正式名：`项目知识能力层`
   - 用户可见名：`项目资料`

这里要强调三点：

1. `ReferenceEvidenceSubstrate` 适合代码、文档、合同和实现讨论。
2. `参考资产库` 更适合作为 GUI 文案，因为用户更容易理解。
3. `ProjectInformationCapabilityLayer` 保留“能力层”这个判断，能防止它再次被误读成“全局知识库”。

如果后续为了目录名和 import 路径需要更短缩写，可以收敛成：

1. `reference_substrate`
2. `project_reference_attachments`
3. `project_information`

但这只是实现层缩写，不改变上面的正式命名。

## 4. 对“每个大框架条目都单独 SQLite”的正式评估

用户这轮提出了一个很有直觉吸引力的想法：

```text
大框架中的每个条目应当单一 sqlite，这样才是真的可分开复用。
```

这个想法不该被直接否定，因为它抓住了一个真实目标：

```text
逻辑上必须可拆、可独立复用、可独立分享、可独立挂载。
```

但从真正的大型项目落地角度看，“每个条目物理上一库一 SQLite 文件”并不是最优默认方案。

### 4.1 这个想法抓住的正确部分

它抓住了三件很重要的事：

1. 每个条目不应绑死在一个大杂烩仓里。
2. 每个条目未来可能被单独导出、分享、挂载、版本化。
3. 如果无法独立寻址、独立迁移、独立复用，那它就不是真正的模块化资料资产。

这些判断都对。

### 4.2 物理上一条目一 SQLite 的问题

但如果把这个目标直接翻译成“每一个条目都是一个 SQLite 文件”，会带来很多现实问题：

1. 目录和文件数膨胀。
2. catalog、索引、跨包检索、全文检索、版本比较都会变重。
3. 事务管理复杂。
4. 批量升级、迁移、校验、备份会变得很碎。
5. 权限和可见性策略会变成“遍历一堆小库”的维护灾难。
6. 很多条目其实是一个 package 内部的多个 record，不值得每条物理拆库。
7. 对后续移动端、桌面端、容器端同步和缓存都不友好。

更直白一点：

```text
逻辑独立 ≠ 物理上一条目一数据库文件
```

### 4.3 更合理的结论

更稳的正式结论应当是：

1. 每个资料包、条目、版本必须逻辑独立、可独立寻址。
2. 但默认物理承载不建议“一条目一 SQLite 文件”。
3. 更合适的是：
   - 应用级维护一个共享 SQLite 基座作为主 catalog 和主索引。
   - 包、条目、版本、来源、证据、挂载关系都在这个主基座内有独立 identity。
   - 需要导出、分享、归档时，再打包成独立 bundle。

也就是说，正式推荐：

```text
共享 SQLite 主基座
  + 逻辑独立的 package / entry / version
  + 可导出可导入的 bundle
```

而不是：

```text
海量分散 SQLite 小文件
```

### 4.4 那么“独立复用”怎么保证

要保证独立复用，不靠“每条一个 SQLite”，而靠下面这些能力：

1. `package_id`
2. `package_version_id`
3. `entry_id`
4. `entry_namespace`
5. `entry_kind`
6. `export_bundle`
7. `import_bundle`
8. `mount_binding`
9. `promotion_record`
10. `dependency_record`

只要这些 identity 和 contract 在，条目就是可独立复用的。

### 4.5 最终结论

所以，这一条我会明确修正为：

```text
不是“每个条目都单独一个 SQLite 文件”，
而是“每个条目都必须是 SQLite 基座里独立可寻址、可版本化、可导出复用的逻辑单元”。
```

这比“一条一库”更适合真正的项目。

### 4.6 可分发如何正式保证：分发单元不是数据库实例，而是 bundle 合同

这轮还需要补上一条非常关键的正式结论：

```text
可分发性不应依赖“每个条目一个独立 SQLite 文件”，
而应依赖“包级分发合同”。
```

也就是说，我们需要明确区分四件事：

1. 运行时治理单元：
   - 共享 SQLite 主基座

2. 逻辑复用单元：
   - `entry`

3. 逻辑聚合单元：
   - `package`

4. 分发单元：
   - `bundle`

这四者不能混为一谈。

推荐的正式关系是：

```text
Entry 是逻辑可复用单元
Package 是逻辑聚合单元
Bundle 是导入导出与分享单元
SQLite 主库是运行时治理单元
```

#### 推荐的 bundle 合同

至少应包含：

1. `manifest.json`
   - `bundle_id`
   - `package_id`
   - `package_version_id`
   - `bundle_schema_version`
   - `display_name`
   - `package_kind`
   - `created_at`
   - `created_by`
   - `source_summary`
   - `license_summary`
   - `dependency_summary`
   - `integrity_hashes`

2. `payload/`
   - 可为 `payload.sqlite`
   - 或按后续权衡支持 `payload.jsonl`
   - 或混合结构化附件

3. `attachments/`
   - 原始导入资料
   - 提取中间产物
   - 样本片段
   - 只读投影资源

4. `projections/`
   - 面向人阅读的 Markdown 摘要
   - 风格画像摘要
   - 边界说明页

5. `integrity/`
   - 完整性校验信息
   - 哪怕早期不做强签名，也应先保留结构位

#### 为什么 bundle 合同更好

因为它同时解决了：

1. 独立导出。
2. 独立导入。
3. 独立分享。
4. 跨机器迁移。
5. 应用级 catalog 重建。
6. 人工归档和审计。

而不需要把运行时架构做成“海量小 SQLite 文件”的维护灾难。

#### 一个重要补充

包不一定很大。

如果以后确实存在“只想分享一个极小条目”的场景，也完全可以让一个 bundle 只包含一个 entry。

因此：

```text
支持极小粒度分发
≠
默认把运行时物理结构碎成一条一库
```

## 5. 我们真正要承载的不是单一知识，而是几类完全不同的资料资产

如果不先把“资料类型”分清，后面一定会又回到一个巨大的知识仓。

### 5.1 `ReferenceWorkPackage`

适合承载：

1. 原作提取包。
2. 同人参考包。
3. 作品世界观提取包。
4. 角色体系提取包。
5. 时间线提取包。
6. 情节结构提取包。
7. 写作侧重点和叙事方式提取包。

典型例子：

1. 《哈利波特》原作参考包。
2. 某本快穿原作的多世界结构提取包。
3. 某套轻小说系列的角色与时间线提取包。

注意：

1. 这里的重点不是只提“剧情梗概”。
2. 还要提角色特点、关系变化、叙事节奏、篇章重心、风格手法、常用意象、细节习惯、伏笔方式。
3. 但这些内容不能裸放成一大段 prompt 文本，而应有结构。

### 5.2 `DomainEvidencePackage`

适合承载客观领域依据：

1. 历史时期资料。
2. 科技发展依据。
3. 神话体系资料。
4. 宗教民俗资料。
5. 星象、八卦、古典象征资料。
6. 真实制度、地理、工艺、军事、生活方式资料。

典型例子：

1. 明代日常制度与社会组织包。
2. 近代盐业与冶金发展基础包。
3. 北欧神话人物与象征关系包。
4. 原始社会到青铜社会基础技术演进包。

这类包特别适合你提到的“穿越古代发展科技”“穿越异世界用科学立足”。

### 5.3 `StyleTechniqueProfile`

这类东西必须单列，不应硬塞进知识卡。

它适合承载：

1. 某作者文风画像。
2. 某作品叙事技法画像。
3. 常用描写路径。
4. 情绪控制方式。
5. 对话习惯。
6. 节奏推进习惯。
7. 意象、隐喻、镜头感、视角调度习惯。

这类内容和客观事实不同：

1. 它不是真假二元。
2. 它更像分析结论、风格画像、策略建议。
3. 它需要置信度、证据样本、适用范围。

所以不能把它混进纯事实库。

### 5.4 `ProcessDependencyPackage`

这类包承载“过程型参考”而非静态设定。

适合承载：

1. 科技演进依赖链。
2. 魔法体系发展依赖链。
3. 宗教/政治/军事扩张依赖链。
4. 产业组织和制度演进链。
5. 某种流派固定演化逻辑的参考。

例如：

1. “从原始社会到蒸汽化”的关键节点包。
2. “修仙世界炼器工业化”的依赖链包。
3. “魔法文明和科学文明碰撞时可出现的制度断点”参考包。

### 5.5 `ProjectDivergenceSnapshot`

这一类很重要，因为项目一旦挂了全局参考包，后续很可能会偏离。

例如：

1. 这是哈利波特同人，但我们让角色命运提前拐了。
2. 这是明代穿越，但我们的架空点从第二卷开始越来越强。
3. 这是北欧神话命名体系借用，但后续故事只取意象，不再严格遵循原典。

这些偏离不能直接回写原始资料包。

因此需要项目级的：

1. 偏离声明。
2. 替换规则。
3. 作废规则。
4. 优先级覆盖。

### 5.6 `MicroReferenceShard`

这类东西就是你举的“中文网络热梗”那种零散知识。

它们的特点是：

1. 粒度小。
2. 生命周期短。
3. 可能有时效性。
4. 不值得建成完整大包。
5. 但对项目可能很有用。

这类不应该强迫走重型提取流。

因此需要一个轻量包型：

1. 可短期收录。
2. 可标时效。
3. 可快速失效。
4. 可不进入长期挂载。

## 6. 对当前四类信息对象的正式重新定位

### 6.1 `ProjectKnowledgeCard`

正式定位：

```text
项目工作事实卡
```

适合放：

1. 当前项目稳定角色事实。
2. 当前项目稳定世界事实。
3. 当前项目确认后的规则事实。
4. 从更大资料包中提炼出来、当前项目真正要消费的知识。

不适合放：

1. 一整本原作的完整提取。
2. 一整套神话体系的完整材料。
3. 风格画像全文。
4. 重型版本树。

### 6.2 `DesignElementCard`

正式定位：

```text
项目设计元素卡
```

适合放：

1. 命名暗线。
2. 象征系统。
3. 结构巧思。
4. 情节回环。
5. 主题影射。
6. 角色设定中的隐性表达方式。

它是项目层非常好的承接点，但不应该反过来成为“所有设计资产的全局仓”。

### 6.3 `ResearchNote`

正式定位：

```text
研究中间层与证据草稿层
```

适合放：

1. 某次联网搜集结论。
2. 某次导入资料摘要。
3. 某次资料提取结果。
4. 一些尚未提升为稳定知识卡的中间证据。

它应该继续保留“usable facts”和“creative suggestions”的分离。

这是一个很正确的设计，不应回退。

### 6.4 `ReferenceWorkRecord`

正式定位：

```text
项目边界与引用关系记录
```

适合放：

1. 项目和外部作品是什么关系。
2. 允许怎么借用。
3. 需要不要用户确认。
4. 有哪些使用风险。
5. 当前项目挂载了哪个参考作品包。

它不是完整原作包体本身。

### 6.5 这四类对象合起来是什么

它们合起来最合理的统一命名不是“大知识库”，而是：

```text
项目工作知识能力层
```

或者更具体一点：

```text
Project Information Capability Layer
```

这里“能力层”这个说法很重要，因为它强调：

1. 它服务项目当前执行。
2. 它是项目运行时上下文能力的一部分。
3. 它不是应用全局资料仓本身。

## 7. 数据承载：SQLite 应放在哪些层，哪些层不应急着重做

### 7.1 正式判断

SQLite 是对的，但要放对位置。

最合理的放法不是“把现在全部项目知识 JSON 立刻抹掉改 SQLite”，而是：

1. 应用级参考证据基座优先 SQLite。
2. 项目级挂载与可见性映射优先 SQLite。
3. 项目级工作知识能力层暂时可以保留现有 JSON 事实源加投影，不必硬切。

### 7.2 为什么应用级优先 SQLite

应用级基座天然需要：

1. 关系映射。
2. 来源链。
3. 证据链。
4. package catalog。
5. package version。
6. mount visibility。
7. dependency。
8. promotion。
9. 审计事件。
10. 多条件查询。

这些都是 SQLite 的强项。

### 7.3 为什么项目挂载映射优先 SQLite

项目挂载层需要：

1. 某项目挂了哪些包。
2. 哪些是默认可见。
3. 哪些只可发现摘要。
4. 哪些允许升级检索。
5. 用的是哪个版本快照。
6. 是否有项目偏离覆盖。

这类 mapping 很适合结构化表，而不适合纯 Markdown。

### 7.4 为什么项目工作知识层可以暂时不重做

当前项目层的 JSON 模型有几个现实优点：

1. 结构已经跑通。
2. 易调试。
3. 易人工检查。
4. 当前适配器已经稳定。
5. 作为项目级工作集，数据量不会像全局参考基座那样夸张。

所以短中期最好的路线是：

1. 不推翻项目层。
2. 不在这一步制造大迁移。
3. 先把应用级基座和挂载层设计对。
4. 项目层以后如果要迁 SQLite，再以“实现替换”而不是“语义重写”的方式做。

### 7.5 形式上对用户暴露什么

即使底层是 SQLite，用户看到的也不应是数据库。

用户看到的应该是：

1. 可读摘要。
2. 包说明。
3. 提取结果页。
4. 风格画像页。
5. 边界页。
6. 证据页。
7. 项目已挂载资料列表。
8. 项目当前正在激活的知识卡和设计元素。

也就是说：

```text
SQLite 是底座，不是 UI 形态。
```

### 7.6 ORM 与原生 SQL 的正式取舍

这轮还需要把 SQLite 的实现策略说清楚，否则后面很容易在实现时又绕回“要不要先上 ORM”。

正式建议是：

```text
先用 SQLite 驱动架构，不用 ORM 驱动架构。
```

更具体一点：

1. `core`
   - 只定义仓储合同、查询合同、bundle contract、mount contract
   - 不暴露 ORM 语义

2. `adapters`
   - 承担 SQLite 具体实现
   - 承担迁移、查询、索引、事务、导入导出

3. 查询层
   - 优先原生 SQL
   - 允许轻量 mapper / row translator
   - 避免把复杂关系查询藏进重型 ORM 魔法

不推荐当前阶段先把 ORM 作为核心前提，原因如下：

1. 这套数据不是普通表单 CRUD。
2. 有很多版本、挂载、来源、证据、依赖、冲突、promotion 查询。
3. 很多关键查询用显式 SQL 比 ORM 更清楚、更可审计。
4. 如果 ORM 太早进入 core，后面容易把架构反过来做成“迎合 ORM 的模型”。

这不意味着未来永远不能引入 ORM。

更准确的判断是：

1. 当前阶段：
   - 原生 SQL + 轻量封装最稳

2. 后续若 GUI 出现大量复杂响应式浏览需求，且已证明 ORM 真能降低 adapter 复杂度：
   - 可以在 adapter 内部评估引入

3. 即使未来引入 ORM：
   - 也不应让 core contracts 依赖 ORM 术语

最终结论：

```text
SQLite 是主数据底座；
SQL 是当前首选表达；
ORM 最多是未来 adapter 内部的可选实现技术，而不是先验架构中心。
```

## 8. 生成方式：大框架不应被建成“某种特殊项目类型”

### 8.1 不推荐方案

不推荐把“大框架”定义成一个新的项目类型，例如：

1. “知识库项目”
2. “原作提取项目”
3. “资料数据库项目”

然后强迫所有复用都通过这种项目来完成。

原因：

1. 它会让应用级资产和项目级工作流边界重新混淆。
2. 它会让用户误以为“资料资产也必须像小说项目一样操作”。
3. 它会让全局可复用内容被项目生命周期绑架。

### 8.2 更合理的生成方式

更合理的是双轨：

1. 重型资产通过显式构建流程生成。
2. 轻量项目资料通过项目工作流自然生成。

也就是：

#### A. 重型构建流

用于：

1. 原作完整提取。
2. 历史/科技/神话体系包构建。
3. 风格画像构建。
4. 大型资料包整理。

这种流程应是显式的、可审核的、可版本化的。

#### B. 项目内自然生成流

用于：

1. 写作过程中顺手生成 research note。
2. 写作过程中顺手生成 knowledge card。
3. 拆书过程中顺手生成 design element。
4. 解书过程中顺手生成总结性知识。

这种流程默认只落项目层。

#### C. 项目到应用的提升流

当项目里出现了“真的值得复用”的资产时，才显式提升为应用级包。

例如：

1. 某次同人原作提取做得很好。
2. 某套科技演进依据整理得很好。
3. 某种写法风格画像已经足够稳定。

这时应走：

```text
project artifact -> review -> promote -> reusable package
```

而不是自动上升。

### 8.3 为什么这样更稳

因为这避免了两个极端：

1. 一切都靠人工提前建大库，太重。
2. 一切都靠项目运行时临场猜，太散。

这也是更接近大型项目的做法。

## 9. 用户暴露、权限与可见性：必须做轻量默认，允许高级可达

### 9.1 先明确一条基线

正常用户不应在创建项目时就被问：

1. 你要挂哪些资料包。
2. 你要不要开放全局目录可见性。
3. 你要不要允许升级检索。
4. 你要不要启用 style technique package。

那样心智负担太高。

### 9.2 默认策略

默认应由智能体和项目演化流程来推荐：

1. 这个项目可能需要历史资料。
2. 这个项目可能需要某原作参考包。
3. 这个项目可能需要某科技演进包。
4. 这个项目看起来完全原创，不需要额外挂载。

然后用户只需要看到低心智的确认结果：

1. 已附加资料。
2. 推荐资料。
3. 当前没有额外资料。

### 9.3 高级可达策略

同时必须给高级用户一个设置入口，允许他们：

1. 浏览应用级资料包目录。
2. 手动挂载某个资料包到当前项目。
3. 调整当前项目允许访问的资料包范围。
4. 查看当前项目引用的是哪一版快照。
5. 分叉资料包。
6. 导入外部资料包。
7. 导出自己整理的资料包。

### 9.4 权限模型

最合理的权限模型应至少区分：

1. 普通用户项目运行权限。
2. 高级用户资料管理权限。
3. 智能体默认运行权限。
4. 智能体升级检索权限。
5. 应用级管理权限。

### 9.5 对智能体的可见性层级

智能体看到的内容不应该是“全开”或“全关”，而应有层级：

1. `attached_read`
   - 只能读项目已挂载资料包。

2. `catalog_discoverable`
   - 可以看全局目录摘要，但不能直接展开全文。

3. `escalated_inspect`
   - 当项目当前挂载不够时，可请求升级查看候选包更多摘要或部分细节。

4. `admin_override`
   - 只在明确高权限场景下使用。

### 9.6 为什么不能让智能体默认随便看全库

因为那会造成：

1. 上下文膨胀。
2. 错误引用。
3. 引用边界失控。
4. 无意义资料噪音。
5. 用户难以理解“为什么模型突然知道这么多东西”。

所以“智能体能用工具看到更大范围”和“智能体默认什么都看见”是两回事。

## 10. 用户可编辑性：哪些能改，哪些不该直接改

### 10.1 项目层对象应可编辑

项目级工作知识能力层里的内容应该较容易编辑：

1. `ProjectKnowledgeCard`
2. `DesignElementCard`
3. `ResearchNote`
4. `ReferenceWorkRecord`

原因：

1. 这是当前项目的工作集。
2. 用户经常需要改、补、删。
3. 智能体也可能提出修订。

### 10.2 应用级资料包默认不应自由原地编辑

应用级资料包更适合：

1. 只读。
2. 复制。
3. 分叉。
4. 派生新版本。
5. 做新的提取/修订版本。

不推荐普通用户直接原地改全局真源。

否则会产生：

1. 多项目被同步污染。
2. 历史不可追踪。
3. 用户不知道改动影响范围。

### 10.3 生命周期模型

应用级资料包最好有明确生命周期：

1. `candidate`
2. `reviewed`
3. `accepted`
4. `active`
5. `deprecated`
6. `archived`

项目层对象也可以有轻量生命周期，但不需要同等重型。

### 10.4 为什么这符合项目现实

因为我们本质上要同时服务两类场景：

1. 当前项目快节奏创作。
2. 长期可复用资料资产治理。

这两类场景如果用同一编辑策略，一定会互相伤害。

## 11. 错误处理：这套系统必须从设计上预留完整故障面

用户这轮特别提醒要考虑错误处理，这一点非常对。

如果只设计“理想路径”，这种系统会非常脆。

### 11.1 缺包

场景：

1. 项目挂载记录里引用了一个已不存在的资料包。
2. 导入路径损坏。

系统行为：

1. 项目标记该挂载为 `missing`.
2. 不阻塞整个项目打开。
3. 提示可替换、移除或重定位。
4. 保留原挂载记录，避免悄悄丢失语义。

### 11.2 版本不匹配

场景：

1. 项目挂的是某包旧版本。
2. 应用级目录里已有新版本。

系统行为：

1. 默认继续用旧版本快照。
2. 提示“可升级”而不是偷偷升级。
3. 升级前展示差异摘要。

### 11.3 项目偏离与上游冲突

场景：

1. 项目挂了某参考包。
2. 项目里已经生成了偏离声明。
3. 智能体后续又从上游包里读到旧规则。

系统行为：

1. 项目偏离覆盖优先于上游挂载内容。
2. activation 层必须看得见偏离规则。
3. 不允许上游内容无条件压回项目当前真相。

### 11.4 来源链断裂

场景：

1. 某知识卡引用了已失效 research note。
2. 某 style profile 的样本链接丢失。

系统行为：

1. 标记 evidence degraded。
2. 保留内容，但降低信任级别。
3. 对需要严格依据的任务发出风险提示。

### 11.5 权限不足

场景：

1. 智能体想看更多全局包。
2. 当前项目只允许 attached_read。

系统行为：

1. 返回权限不足而不是静默失败。
2. 可登记升级请求。
3. 不允许模型在无权限时“假装已经看过”。

### 11.6 多包冲突

场景：

1. 项目同时挂了两个历史包，结论冲突。
2. 项目挂了原作包和改编版包，人物设定冲突。

系统行为：

1. 记录冲突。
2. 要么要求指定优先级。
3. 要么要求项目声明偏向哪一侧。
4. 不允许 activation 静默混合。

### 11.7 提取失败

场景：

1. 原作导入失败。
2. 风格提取只完成一半。
3. 科技资料整理失败。

系统行为：

1. 落中间状态。
2. 标记 partial。
3. 保留已成功部分。
4. 不伪装成完整资料包。

### 11.8 Promotion 失败

场景：

1. 项目层某资产要提升为应用级包，但证据不全。
2. 包字段校验失败。

系统行为：

1. 提升失败。
2. 保留项目层原对象。
3. 返回缺失项。
4. 不做半成功污染。

### 11.9 SQLite 损坏或索引损坏

场景：

1. 应用级 catalog 数据损坏。
2. 局部索引损坏。

系统行为：

1. 可只读降级。
2. 可从 bundle 或投影重建部分索引。
3. 项目层工作知识尽可能不受牵连。

### 11.10 联网研究失败或来源不足

场景：

1. 搜索没有拿到可靠来源。
2. 只有低质量来源。
3. 当前网络权限未开放。

系统行为：

1. 生成 research request / pending / failed 状态。
2. 明确区分“没研究到”和“已确认”。
3. 不把猜测写成事实。

## 12. 这套架构如何覆盖写作、拆书、解书，而不是只服务小说写作

这一点必须明确，因为你已经指出，未来不只是写作。

### 12.1 普通写作项目

用法：

1. 智能体按需收集资料。
2. 资料进入 research note。
3. 必要信息提升为 knowledge card / design element。
4. 项目只激活当前需要的部分。

### 12.2 长任务写作项目

用法：

1. 长任务不应每章都盲查资料。
2. 应优先消费项目层工作知识。
3. 当出现新的信息缺口时，触发资料请求。
4. 新资料进入项目层，再被后续章节激活。

### 12.3 拆书项目

用法：

1. 从原作中提取角色、时间线、风格、情节重心、命名巧思、象征系统。
2. 这些结果先成为结构化中间层。
3. 再决定哪些沉淀为项目层、哪些提升为应用级包。
4. 当原作明显借用外部神话/历史/科学体系时，才请求外部研究补充。

### 12.4 拆书续写项目

用法：

1. 项目挂载原作提取包。
2. 项目级工作知识只保留当前续写最需要的部分。
3. 项目偏离记录负责声明“从哪里开始分歧”。

### 12.5 解书 / 总结 / 评书 / 小说解说

用法：

1. 原作提取包或项目层知识可直接支撑分析任务。
2. 风格画像和设计元素比纯剧情摘要更关键。
3. 输出的解读结果既可成为项目产物，也可反哺更强的参考包。

### 12.6 未来同人

用法：

1. 挂原作参考包。
2. 挂必要的客观背景包。
3. 项目级偏离和边界记录决定“遵循原作到什么程度”。
4. 不需要重新提取整套原作。

---

## 13. “哈利波特同人”和“科技发展依据”这两类例子给出的真正设计要求

### 13.1 哈利波特同人例子说明了什么

它说明：

1. 单纯剧情摘要不够。
2. 角色个性、语气、关系动态、叙事节奏、世界规则、关键细节、命名风格都要提出来。
3. 风格与事实不能混成一类。
4. 同一套原作提取结果应可被多个项目复用。
5. 同一原作提取结果应可分享给别人。

所以它逼出了：

1. `ReferenceWorkPackage`
2. `StyleTechniqueProfile`
3. 项目挂载层
4. 项目偏离层

### 13.2 科技发展例子说明了什么

它说明：

1. 客观依据不是一坨“百科知识”。
2. 需要区分：
   - 初始社会常态
   - 可行技术路径
   - 制度阻力
   - 资源门槛
   - 人群组织方式
3. 同一份科技依据可能在多个项目里复用。
4. 但项目对严谨性的需求不同。

所以它逼出了：

1. `DomainEvidencePackage`
2. `ProcessDependencyPackage`
3. 项目严谨度/风格容忍度策略
4. 信息收集不是永远越多越好，而要看项目当前目标

### 13.3 这两类例子共同说明的东西

它们共同说明：

1. 我们不是只缺一个“知识库”。
2. 我们缺的是一个“可复用参考资产系统”。
3. 这个系统里至少要分事实、设计、风格、过程、边界。

## 14. “零散知识”和“大包”必须并存，不然系统会过重

不是所有知识都值得建成完整包。

### 14.1 为什么必须保留轻量路径

因为现实中会有很多内容是：

1. 一次性需要。
2. 时效短。
3. 只影响少量章节。
4. 不值得长期治理。

例如：

1. 网络热梗。
2. 某个冷门符号解释。
3. 某种短期流行表达。
4. 某个具体物件的简单资料。

### 14.2 轻量路径应该怎么落

推荐：

1. 先作为 `ResearchNote` 或 `MicroReferenceShard`。
2. 默认不提升为重型包。
3. 可带失效时间和可信度。
4. 对项目可见，但不一定进入全局长期目录。

这样可以避免：

1. 系统过度官僚化。
2. 用户查一个小问题就被迫建大包。

## 15. 这套架构和当前知识卡体系的关系：不是耦合，而是投影和派生

用户上一轮明确提出：

```text
知识卡不应和大框架耦合；
知识卡只是项目级提取知识的结果；
它的来源可能来自大框架、网络、导入资料或用户输入。
```

这个判断是对的，而且应该作为正式原则固定下来。

### 15.1 正式原则

```text
大框架不直接等于知识卡。
知识卡也不回写大框架。
知识卡是项目工作知识结果层。
```

### 15.2 从大框架到知识卡的几种路径

1. 摘要投影。
2. 条目提取。
3. 按项目任务筛选。
4. 按当前章节窗口裁剪。
5. 由智能体请求“把该包中与当前任务相关部分转为项目工作知识”。

### 15.3 从项目知识到大框架的路径

只有一种正式路径：

```text
显式提升
```

也就是 review 后 promotion，而不是自动同步。

## 16. 是否应该让用户直接看见“大框架”

### 16.1 不建议默认全暴露

原因：

1. 心智负担大。
2. 用户不一定知道哪些包该挂。
3. 用户大多数时间只关心项目当前能不能用。

### 16.2 也不建议完全不可见

原因：

1. 用户有时需要复用、分享、手动挂载。
2. 高级用户确实需要治理这些资料资产。
3. 完全不可见会让系统像黑箱。

### 16.3 最合理的平衡

推荐：

1. 默认不把“大框架管理器”放在主工作流前台。
2. 提供专门的资料资产入口。
3. 项目页只展示：
   - 已挂载资料
   - 推荐资料
   - 当前激活的项目知识
4. 高级设置或资料管理页展示更完整的全局资产视图。

这比较像：

1. 引擎里的资源系统。
2. 游戏的 DLC / MOD 资产管理。
3. 但我们不能真的把它做成游戏式花哨中心。

它更应该是：

```text
平时安静存在，需要时可达。
```

---

## 17. 对“像 DLC / MOD 一样”的类比的正式取舍

这个类比有帮助，但不能完全照搬。

### 17.1 有帮助的部分

它帮助我们看到：

1. 可复用资产不应和单个项目绑死。
2. 项目可以挂不同资产组合。
3. 资产可以独立导入、导出、分享。
4. 用户不必每次重建。

### 17.2 不能照搬的部分

因为小说项目和游戏内容不同：

1. 资料包会进入智能体推理链，而不是只做静态资源。
2. 同一资料包可能部分适用、部分不适用。
3. 需要证据、来源、风格、偏离控制。

所以最终应吸收的是：

```text
资产复用与挂载的思想
```

### 17.3 这个类比帮助我们校正的一个正式判断

经过这轮补充，可以把类比进一步校正为：

1. `ReferenceEvidenceSubstrate`
   - 更像引擎级资源系统

2. `bundle`
   - 更像可分享资产包

3. `ProjectReferenceAttachmentLayer`
   - 更像项目装配关系

4. `ProjectInformationCapabilityLayer`
   - 更像运行时正在消费的工作集

这样比单纯说“大框架像 DLC/MOD”更精确，也更不容易在后续实现中把产品做跑偏。

而不是把它产品外形做成 MOD 管理器。

## 18. 这套设计和信息收集纪律的关系

前几轮我们已经收口了一个很重要的结论：

```text
信息收集不是表达限制，也不是单纯某个智能体的人设习惯；
它是平台级证据纪律 + 工具使用准则 + 智能体专业风格三层协作。
```

这次的大框架设计正好把这个判断进一步坐实了。

### 18.1 为什么不是表达限制

因为表达限制解决的是：

1. 文风。
2. 去 AI。
3. 句式倾向。
4. 文本输出样貌。

而大框架解决的是：

1. 资料从哪里来。
2. 是否已验证。
3. 可复用资产怎么挂。
4. 当前项目到底看什么。
5. 什么时候需要研究。

这两者不是一回事。

### 18.2 为什么又和执行纪律有关

因为运行时会出现 gate：

1. 当前需要资料但没有资料。
2. 当前资料不够严谨。
3. 当前引用边界冲突。
4. 当前只允许读已挂载包。

所以它最终会接入更上层的：

```text
runtime policy / execution discipline
```

但它本身不应该被塞进 expression constraints。

### 18.3 推荐的总框架

更中性的上层概念应是：

1. `length discipline`
2. `expression discipline`
3. `evidence discipline`
4. `delivery discipline`
5. `recovery discipline`

其中这次讨论出来的内容，主要落在：

```text
evidence discipline
```

## 19. 多项目类型共享这一层，是必须的

这套东西如果只给长任务用，就错了。

如果只给拆书用，也错了。

它必须同时支持：

1. 普通写作。
2. 长任务写作。
3. 拆书。
4. 拆书续写。
5. 解书。
6. 总结。
7. 小说解说。
8. 未来同人。
9. 未来跨作品引用。

因为这一层处理的是：

1. 资料。
2. 证据。
3. 风格。
4. 外部作品边界。
5. 过程依赖。

这些本来就是横切能力。

## 20. 对当前仓库现实的衔接建议：别重写，别硬迁，先加骨架

这是这轮非常重要的一点。

### 20.1 当前哪些东西可以保留

可以直接保留：

1. `.novel_agent/information/*` 作为项目工作知识事实源。
2. `knowledge/` 作为投影和兼容可读目录，而不是正式事实源。
3. 现有 `ProjectKnowledgeCard / DesignElementCard / ResearchNote / ReferenceWorkRecord` 合同。
4. 现有 project information repositories 与 path service。

### 20.2 当前哪些东西不能再继续吸收新职责

不能继续扩写为新信息中心的：

1. `knowledge/`
2. `ProjectWorkflowRuntimeService`
3. `ProjectContextActivationService`
4. gateway 一次性 tool executor

### 20.3 下一阶段最值得做的不是

不是：

1. 立刻把所有项目层 JSON 换成 SQLite。
2. 立刻做一个庞大的资料管理 GUI。
3. 立刻实现所有包类型。
4. 立刻做社区分享。

### 20.4 下一阶段最值得做的是

而是：

1. 明确应用级参考证据基座 contracts。
2. 明确项目挂载与可见性 contracts。
3. 明确项目层从应用层派生的桥。
4. 明确 promotion 合同。
5. 让当前项目层继续稳定服务真实工作流。

## 21. 从大型项目角度，这套架构还要防什么坑

### 21.1 防“又一个全能中心”

不要做一个：

1. `KnowledgeManager`
2. `ReferenceCenter`
3. `InformationHub`

然后把提取、检索、挂载、投影、权限、升级、审计全塞进去。

那会立刻重演之前的大文件问题。

### 21.2 防“所有东西都当事实”

必须持续区分：

1. 事实。
2. 研究结论。
3. 设计建议。
4. 风格画像。
5. 偏离声明。

### 21.3 防“项目层与应用层双向混写”

这一点已经反复强调，必须作为硬原则写死：

```text
默认单向派生，显式提升。
```

### 21.4 防“用户被迫理解内部治理模型”

正常用户应看到：

1. 当前项目资料够不够。
2. 是否建议补资料。
3. 当前挂了哪些资料。

而不是看到一堆 schema 和 state machine。

### 21.5 防“智能体无限制吞资料”

需要把资料访问做成工具化、策略化、权限化，而不是默认 prompt 全灌。

### 21.6 还没有被充分展开、但实现前必须纳入的边界

为了避免下一轮进入目标模式后又因为遗漏边界而返工，这里补充几类目前还没有被充分展开、但必须纳入正式实现范围的点。

#### 1. schema migration 与版本升级策略

应用级基座一旦采用 SQLite，就必须从第一版开始认真对待：

1. schema version
2. migration ordering
3. downgrade policy
4. bundle import compatibility
5. corrupted migration recovery

否则前面讨论的 versioning 都会只停留在语义层。

#### 2. 全文检索与字段索引策略

虽然我们强调不能把整个库一股脑灌进 prompt，但系统仍然需要高质量检索。

后续必须明确：

1. 哪些字段走精确索引。
2. 哪些字段走全文检索。
3. 风格画像、设计元素、原作细节、研究摘要是否需要不同检索策略。
4. 检索结果如何排序，避免“资料存在但命中不到”。

#### 3. 大文本与附件治理

有些资料包不会只有结构化表，还会有：

1. 原作片段样本
2. 导入原文
3. 风格样章
4. 大段历史资料

这要求我们明确：

1. 什么放 SQLite。
2. 什么放附件。
3. SQLite 内只保元信息还是保切片索引。
4. projection 如何从结构化层和附件层共同生成。

#### 4. license / provenance / sharing boundary

只要系统允许导入、提取、分享，就必须认真处理：

1. 原文是否可打包分享。
2. 只分享提取结果还是连原始附件一起分享。
3. `license_summary` 是否强制存在。
4. 某些 bundle 是否只能本机可用、不能导出。

这不是开源协议问题，而是资料资产治理本身的边界。

#### 5. 并发、锁与长任务运行时一致性

长任务、普通任务、拆书、资料导入以后可能同时运行。

必须考虑：

1. SQLite 写锁争用。
2. mount 变更时任务是否要刷新视图。
3. project information 激活时如何感知应用级挂载更新。
4. bundle import / promotion 与运行中任务如何协调。

#### 6. 缓存与投影重建

既然用户看到的是 projection 而不是数据库，就必须明确：

1. projection 是同步写还是异步重建。
2. projection 丢失时能否重建。
3. projection 和事实源不一致时谁为准。
4. GUI 浏览器是读 projection 还是读结构化查询结果。

#### 7. 安全与可信来源分级

未来只要联网研究和外部 bundle 并存，就必须留出：

1. 来源可信度等级
2. bundle 信任等级
3. 未校验导入物的隔离状态
4. 高风险来源对项目激活的限制策略

否则“可分享”和“可直接用”会被混成一件事。

#### 8. 删除与级联策略

后续必须定义：

1. 删除应用级包时，已挂载项目如何表现。
2. 删除 bundle 导入记录时，是否影响已派生项目知识。
3. 删除项目知识卡时，是否保留其来源链接审计。
4. 删除全局资料是否允许跨项目级联清理。

如果这里不预先设边界，用户体验和数据安全都会很差。

### 21.7 一个重要的总体提醒

上面这些边界不意味着现在就要一次性把每个高级功能都做满。

它们的意义是：

1. 现在的 contract 和层级命名必须为这些问题留口。
2. 下一轮目标模式实现时，不能只把“能存进去”当成完成。
3. 必须至少把迁移、索引、分发、权限、投影、并发、删除策略这些硬边界设计进架构。

## 22. 最终敲定：本轮正式结论

这一节把前几轮最终敲定的东西收成可直接复用的结论。

### 22.1 关于知识卡体系

1. 保留。
2. 不停掉。
3. 重新定位为项目工作知识能力层。
4. 不再误当未来完整大框架。

### 22.2 关于大框架

1. 单独存在。
2. 正式命名为 `ReferenceEvidenceSubstrate`。
3. 中文正式名为“参考证据基座”。
4. 用户可见名可采用“参考资产库”。
5. 服务所有项目类型。
6. 不是某个特殊项目类型。

### 22.3 关于知识卡和大框架的关系

1. 分离。
2. 单向派生。
3. 显式提升。
4. 保留 source/evidence traceability。

### 22.4 关于 SQLite

1. 应用级基座优先 SQLite。
2. 项目挂载映射优先 SQLite。
3. 项目工作知识层短中期可保留 JSON 事实源。
4. 不采用“每个条目一个 SQLite 文件”的默认方案。
5. 采用“共享 SQLite 基座 + 逻辑独立 package/entry/version + bundle 导入导出”的方案。
6. 可分发性依赖 bundle contract，而不是依赖运行时物理拆库。
7. 当前实现策略优先原生 SQL + 轻量 mapper，不以 ORM 为先验中心。

### 22.5 关于用户暴露

1. 默认低心智。
2. 高级可达。
3. 项目层可编辑。
4. 应用级包默认只读、可分叉。

### 22.6 关于可见性和权限

1. 项目级决定默认能看哪些资料包。
2. 智能体默认只看项目挂载集。
3. 必要时可请求升级检索。
4. 不允许无权限自由读取全局资料。

### 22.7 关于资料类型

至少区分：

1. `ReferenceWorkPackage`
2. `DomainEvidencePackage`
3. `StyleTechniqueProfile`
4. `ProcessDependencyPackage`
5. `ProjectDivergenceSnapshot`
6. `MicroReferenceShard`

### 22.8 关于错误处理

必须从设计层覆盖：

1. 缺包。
2. 版本冲突。
3. 项目偏离覆盖。
4. 来源断裂。
5. 权限不足。
6. 多包冲突。
7. 提取失败。
8. promotion 失败。
9. SQLite 损坏。
10. 联网研究失败。

### 22.9 关于与当前系统的衔接

1. 当前项目层实现可继续用。
2. 不应大迁移。
3. 不应新增新的全能中心。
4. 先补 contracts、bridge、visibility、promotion。

## 23. 我对前几轮说法做出的必要修正

为了避免未来沿着旧说法长歪，这里明确记录我这次主动修正的几条点。

### 23.1 修正一：不接受“每个条目物理单独 SQLite”

保留其“独立复用”目标，但修正实现方向为：

```text
逻辑独立 + 共享 SQLite 基座 + bundle 化导入导出
```

### 23.2 修正二：不把大框架做成一个项目类型

它应是应用级资产系统，不是项目类型。

### 23.3 修正三：不把风格当知识卡附属品

风格画像应单列，不应混进纯事实层。

### 23.4 修正四：不把大框架和知识卡耦合成一个系统

它们之间只有派生和提升，不做双向糊写。

### 23.5 修正五：不把所有资料都做成重型包

必须保留轻量零散知识路径。

## 24. 这一轮之后，什么算真正做对了

等后续实现时，若出现下列状态，才算真正做对：

1. 用户能在不增加太多心智负担的情况下，让项目自然用到合适资料。
2. 同一份原作提取、科技依据、神话体系可以跨项目复用。
3. 项目只消费当前需要的工作知识，而不是背整个资料仓。
4. 智能体不会因为“知道一点点”就假装知道全部。
5. 项目偏离和上游参考能清晰并存。
6. 风格、事实、设计、边界、研究不会再混成一锅。
7. 当前 JSON 项目层还能继续稳定跑，不被大框架重构拖死。
8. 应用级资产系统即使以后扩到写作之外，仍然通用。

---

## 25. 本文结论的最终一句话版本

```text
我们不是要把知识卡做大，而是要在应用级补一个可复用、可版本化、可挂载、可审计的参考证据基座；
项目现有知识卡体系保留为工作知识能力层；
两者通过挂载、提取、派生、提升连接；
SQLite 用在应用级基座和挂载映射上，而不是粗暴地“一条一库”；
这样才能同时服务写作、长任务、拆书、解书和未来同人，而不把项目做乱。
```
