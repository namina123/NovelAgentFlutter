# 任务保活、目标模式与写作策略层补充分析 2026-06-08

## 目的

这份文档专门收口最近几轮已经讨论出来、但还没有被正式落进 `docs/important/` 的分析结论。

它不是在重复已有的：

1. `docs/important/long-task-stability-supervisor-review-synthesis-2026-06-06.md`
2. `docs/important/expression-constraint-agent-review-architecture-analysis-2026-06-06.md`
3. `docs/important/harry-potter-reference-audit-and-watchdog-analysis-2026-06-08.md`

而是补上这些新近判断：

1. `watchdog` 的生命周期应如何定义。
2. 任务级保活与应用级保活不是一回事，应怎样分层。
3. `pause / resume / stop / continue` 应由谁负责、以什么状态表达。
4. “目标模式”本质上是什么，它与真正长任务是什么关系。
5. 是否需要引入写作策略层，以及它应如何与调度层解耦。
6. 在不把系统做得过重的前提下，我们下一阶段应守住哪些原则。
7. `watchdog` 与“连续性冲突 / 作者失忆 / 设定回退”之间的职责边界。
8. 参考提取产物目前为何仍偏向 `json + markdown projection`，以及这与原本 `sqlite` 分发目标之间的落差。
9. 为什么“没写成 sqlite”目前更像挂载层存储目标问题，而不是单纯缺少某个 toolcall。
10. 提取相关工具为何应偏向提取智能体组特有，以及它们应如何按暴露策略开放。

这份文档的定位，是防止这些判断继续散落在对话里，后续又被实现会话各自理解。

## 一、先给结论

### 1.1 我们需要两种“保活”，但必须严格区分

需要，而且是两种完全不同的问题：

1. `任务级保活`
   - 关心某条工作流是否还活着、有没有推进、该不该恢复或暂停。
2. `应用级保活`
   - 关心移动端/桌面端在切后台、息屏、系统回收、网络抖动之后，任务系统还能不能继续或恢复。

这两者可以协作，但不能混成一个层。

### 1.2 `watchdog` 应存在，但它不是新的大脑

`watchdog` 的价值是成立的，但它应是一个：

1. 小而稳
2. 低频
3. 少状态
4. 不读正文
5. 不判断文学语义

的活性保底层。

它不能变成第二个 `supervisor`，更不能变成“另一个会分析剧情的智能体”。

### 1.3 `supervisor` 仍是调度大脑，`watchdog` 只是保底神经

更准确的分工是：

1. `worker/runtime lane`
   - 真正执行一次写作、提取、总结、审稿或修复。
2. `dispatcher/scheduler`
   - 决定下一步派发什么。
3. `supervisor`
   - 消费结构化结果，决定继续、暂停、修复、等待用户、人工注意、终止等动作。
4. `watchdog`
   - 只负责确认上面这些层是否还活着、是否卡住、是否长时间无前进，并在必要时重新唤起调度。

一句话：

```text
watchdog 保活
supervisor 决策
dispatcher 推进
worker 执行
```

### 1.4 “目标模式”本质上是轻量连续任务，不是正式长任务的缩水复刻

用户这轮提出的判断是成立的：

目标模式确实像一个“小的长任务”。

但它不应直接复用完整长任务那套重模型，而应被理解为：

1. 一条有明确 objective 的连续会话链。
2. 运行轮次通常更少。
3. 调度对象是“继续下一轮会话”，而不是“运行一整条章节队列”。
4. 需要最小化 watchdog / supervisor 能力，但不需要完整长任务中心那样重的 registry、station、checkpoint UI。

也就是说：

```text
目标模式 = 轻量连续调度任务
不是 = 长篇小说队列系统的迷你复制品
```

### 1.5 写作策略层值得引入，但必须只负责“走向控制”，不能吞掉调度层

策略层是有必要的。

它解决的不是“任务活着没”，而是：

1. 什么时候完全由智能体继续演进。
2. 什么时候在故事容易跑偏、代价高、走向分岔大时停下来请求用户抉择。
3. 什么时候需要更严谨地要求资料、边界或结构确认。

它属于：

1. 创作控制
2. 用户参与密度
3. 风险阈值

而不属于：

1. watchdog
2. heartbeat
3. pause/resume 持久化
4. 运行实例恢复

所以：

```text
策略层决定“该不该继续这样写”
调度层决定“系统能不能继续跑”
```

### 1.6 `watchdog` 不应只服务长任务，它应服务所有“连续任务族”

这点需要明确写死，不然实现时很容易又退回“长任务才有控制面，别的流程各写各的”。

在我们现在的项目里，至少这些都属于连续任务族：

1. 长篇写作任务
2. 普通但跨多轮的目标模式
3. 参考提取 / 拆书 / 知识录入
4. 多轮资料收集与研究整编
5. 未来的批量审稿、批量修复、批量导入

它们的内容语义不同，但在控制面上共享：

1. 多轮推进
2. 中断恢复
3. retry / pause / cancel
4. 活性检测
5. 运行记录与可恢复状态

所以：

```text
watchdog 是连续任务基础设施
不是“长任务小说线程专用插件”
```

### 1.7 “没有写成 sqlite”目前不是缺少 toolcall，而是挂载层仍写向本地 JSON 仓储

这次沿着真实代码链路核下来，结论已经比较明确：

1. 参考提取主执行阶段已经有 `SqliteReferenceEvidenceSubstrate`。
2. 但提取完成后，挂载到项目的信息层时，走的是：
   - `ProjectReferenceExtractionMountService`
   - `LocalKnowledgeCardRepository`
   - `LocalDesignElementRepository`
   - `LocalResearchNoteRepository`
   - `LocalReferenceWorkRepository`
   - `ProjectInformationProjectionWriterService`
3. 这些 repository 的目标路径就是：
   - `.novel_agent/information/**/*.json`

也就是说，当前偏差更像：

```text
执行阶段已经有 sqlite substrate
项目挂载阶段仍默认写向 local json repositories
```

因此这里不能简单归因为“智能体缺少某个能写 sqlite 的 toolcall”。

更准确的判断应是：

1. 不是 tool 面完全缺失。
2. 而是挂载 / 投影阶段的主事实源没有切换到我们想要的 sqlite 基底。
3. 换句话说，这是适配器与持久化出口的问题，不是单纯提示词或工具数量问题。

### 1.8 提取相关工具应偏向“提取智能体组特有”，但必须配套暴露策略

这点和前几轮关于“写作智能体组”和“提取智能体组”能力侧重不同的判断是一致的。

更合理的方向是：

1. 写作智能体组
   - 默认拥有写作、审稿、资料消费、轻量知识调用能力
2. 提取智能体组
   - 默认拥有更重的源材料分段、证据绑定、知识归档、引用边界、来源处理能力

但这里不能走向另一个极端：把工具做成完全写死且无法策略暴露。

更好的做法是：

1. `capability family`
   - 写作、审稿、提取、研究、导入、发布
2. `tool exposure policy`
   - 某个智能体组默认开放哪些 capability family
   - 哪些需要显式确认
   - 哪些仅 supervisor / host 可调
3. `task profile binding`
   - 不同任务类型自动请求不同的默认工具暴露组合

这样既能让提取工具不污染普通写作面，也不会把后续扩展做死。

## 二、为什么这几层必须拆开

## 2.1 过去反复混乱的根因

这几轮讨论之所以容易混，是因为“继续”这个词同时出现在三种不同语义里：

1. 运行语义：
   - 任务有没有卡死，系统要不要继续跑。
2. 创作语义：
   - 剧情还要不要按当前方向继续推进。
3. 产品语义：
   - 用户切后台、息屏、过一会儿再回来时，应用还能不能接得上。

如果不拆开，就会变成这些坏结果：

1. `watchdog` 里塞剧情判断。
2. `supervisor` 同时负责文学抉择和心跳恢复。
3. UI 一旦想做暂停/恢复，就不得不摸进 runtime 内脏。
4. 移动端保活问题被错误地下放给长任务控制层。

## 2.2 为什么 `watchdog` 不能兼任策略层

`watchdog` 一旦承担策略判断，会立刻长歪：

1. 它需要读更多上下文。
2. 它需要知道故事现在写到哪里。
3. 它需要知道“跑偏”是什么意思。
4. 它会开始消费题材、风格、资料、用户意图。
5. 它会从活性保底器变成第二个不透明大脑。

这会让它失去最关键的价值：

1. 低复杂度
2. 高稳定性
3. 可机械复现

## 2.3 为什么策略层也不能兼任 `supervisor`

策略层如果接管 `supervisor`，也会出问题：

1. 文学/用户走向判断会污染技术恢复路径。
2. 某次“需要用户决定剧情方向”会被误认为“运行失败”。
3. 某次网络或 provider 抖动会被误当成“应该停下让用户选”。
4. pause/retry/recover 与 narrative checkpoint 会混成一团。

所以后续必须坚持：

1. 技术性停顿
2. 任务性停顿
3. 创作性停顿

三者分开建模。

## 三、推荐的最终分层

## 3.1 四层控制面

推荐长期稳定收口成以下结构：

1. `Execution Lane`
   - 单次运行实体。
   - 执行一个写作轮、研究轮、提取轮、修复轮、审稿轮。
2. `Dispatcher / Scheduler`
   - 根据队列、依赖、预算和 supervisor 决策安排下一步。
3. `Supervisor`
   - 消费结构化结果，决定：
   - `continue`
   - `retry`
   - `repair`
   - `pause_waiting_user`
   - `pause_manual_attention`
   - `complete`
   - `failed`
4. `Watchdog`
   - 检查：
   - heartbeat 是否超时
   - lease 是否过期
   - queue 是否长时间无推进
   - supervisor tick 是否停摆
   - dispatcher 是否失活

## 3.2 策略层放在哪里

策略层不并入这四层，而是挂在 `supervisor` 可消费的结构化输入里。

更准确地说：

1. 策略层输出“当前创作控制策略”。
2. `supervisor` 消费它，但不拥有它。
3. `watchdog` 完全不碰它。

这样可以保证：

1. 运行健康层不读故事。
2. 创作策略层不碰 heartbeat。
3. 最终动作仍统一从 `supervisor` 出口出去。

## 3.3 应保持最小状态的层

应刻意保持最小状态的层有两个：

1. `watchdog`
2. `app keepalive shim`

它们都不应持有膨胀上下文。

更建议的做法是：

1. 持久事实尽量写账本/运行记录。
2. 内存态只保留：
   - 最近一次 pulse
   - 当前 lease
   - 有界队列中的少量事件
3. 队列超长后首端淘汰。

这和用户提出的“非内存膨胀式、固定长度队列、首端销毁”是同向的，而且是对的。

## 3.4 控制面应按“连续任务族”泛化，而不是按“小说长任务”写死

这一步现在必须提前写明白，因为我们已经遇到参考提取也具备连续任务特征了。

如果控制面继续潜意识里只围绕“长篇章节队列”建模，就会出现这些问题：

1. 参考提取自己长出一套断点续跑
2. 目标模式自己长出一套 pause / resume
3. 研究收集再长出第三套 retry / timeout 语义

这会让项目在运行时控制语义上重新碎裂。

因此更推荐的抽象不是：

1. 长任务控制面
2. 提取控制面
3. 目标模式控制面

而是：

1. `continuous task control plane`
2. 不同任务族只是在其上绑定不同的：
   - worker 类型
   - step 合同
   - watchdog 节奏
   - supervisor 判定规则
   - tool exposure policy

## 四、`watchdog` 的生命周期该怎么定义

## 4.1 `watchdog` 应是常驻、低频、可重启的

最合适的生命周期不是“每次任务临时造一个大对象”，而是：

1. 生命周期长于单个 worker。
2. 心跳频率低于 worker 内部流式事件。
3. 可重启，不依赖完整内存上下文恢复。

它监控的不是具体故事，而是控制面是否还活着。

## 4.2 `pause` 对 `watchdog` 来说意味着什么

用户这轮提出的直觉很对：

`watchdog` 的 pause 不应等于“整个系统死掉”，而应意味着：

1. 继续保留任务身份与 lease 信息。
2. 停止继续推动新的工作轮。
3. 向 `supervisor` 或 `dispatcher` 发出“本轮结束后停下”的意图。
4. 在状态上转入：
   - `paused_by_user`
   - `paused_waiting_user`
   - `paused_manual_attention`
   等更具体的终点。

也就是说：

```text
watchdog 的 pause 是保活层停止继续唤起推进
不是把任务事实本身删除
```

## 4.3 `resume` 应如何发生

`resume` 不应靠内存对象“接着跑”，而应靠：

1. 读取持久 run record
2. 恢复 lease
3. 重新激活 dispatcher/scheduler
4. 让 supervisor 决定下一步从哪里继续

这样做的价值很大：

1. 桌面端重启后可恢复
2. 容器化后可恢复
3. 移动端被系统杀掉后仍有机会恢复

## 4.4 `stop` 和 `cancel` 不能混

建议明确区分：

1. `pause`
   - 可恢复
2. `stop`
   - 本次运行停止，但任务不一定取消
3. `cancel`
   - 用户明确终止，不应自动恢复
4. `complete`
   - 目标完成
5. `failed`
   - 技术失败或不可恢复失败

如果把它们混掉，后面无论 GUI 还是 CLI 都会变得很难做人话表达。

## 4.5 `watchdog` 的适用范围必须覆盖提取、研究、导入等连续流程

当前项目里最容易被误判的一点就是：

1. 长篇写作看起来像连续任务，所以自然想到 `watchdog`
2. 参考提取、拆书、研究整编看起来像“工具性流程”，于是容易被当成一次性动作

但现实并不是这样。

它们同样会有：

1. 多轮推进
2. 批次边界
3. 中断恢复
4. provider 波动
5. 部分完成 / 继续补齐

因此这些流程同样应挂在统一 `watchdog` 语义之下，只是 profile 不同：

1. 写作长任务：
   - 更长 lease
   - 更重 review / repair
2. 参考提取：
   - 更关注批次覆盖、挂载完成、投影收口
3. 研究整编：
   - 更关注搜索、证据、草案整合

也就是说：

```text
watchdog 的“对象”不是题材
而是所有具备连续推进语义的任务实例
```

## 五、目标模式应怎样纳入这套系统

## 5.1 目标模式的真实定义

目标模式不是“一个 prompt 很长的普通对话”，而是：

1. 用户给出 objective
2. 系统可多轮连续运行
3. 每一轮结束后根据结果决定是否继续
4. 直到：
   - objective 完成
   - 进入等待用户
   - 发生不可恢复失败

它和长任务的共性是：

1. 都需要连续调度
2. 都需要状态持久化
3. 都需要 pause/resume/stop
4. 都需要最小 watchdog 能力

它和正式长任务的差异是：

1. 通常没有庞大章节队列
2. 不一定有重型 checkpoint 体系
3. UI 入口更轻
4. 完成判定更直接围绕 objective

## 5.2 最合理的实现方式

最合理的方向不是再造一套“目标模式专属 runtime”，而是：

1. 共用同一套运行实例合同。
2. 允许目标模式选择更轻的 controller profile。
3. 使用更小的默认 budget、step cap、heartbeat 节奏。
4. 在 UI 和 CLI 上作为不同入口暴露。

也就是说：

```text
目标模式应复用长任务控制面骨架
但使用更轻的策略与默认参数
```

## 5.3 这为什么重要

如果目标模式不复用控制面，会产生两套坏后果：

1. 一套“普通连续会话”的 pause/resume
2. 一套“长任务”的 pause/resume

然后：

1. 两套状态机
2. 两套故障语义
3. 两套 watchdog 口径

项目很快又会进入重复造轮子。

## 六、应用级保活与移动端问题

## 6.1 这不是长任务控制层自己能解决的

移动端的保活、切后台、息屏、系统杀进程，本质上是宿主环境问题。

它和任务控制层的关系是：

1. 控制层负责可恢复
2. 宿主层负责尽可能不中断

不能期待：

1. `watchdog` 自己解决 Android/iOS 的后台限制
2. `supervisor` 自己解决息屏后的系统调度

## 6.2 更合理的两层方案

推荐拆成两层：

1. `App Keepalive Layer`
   - 与平台生命周期打交道
   - 负责前后台切换、短时后台、唤醒、前台服务或系统允许的保活方案
2. `Task Control Plane`
   - 负责 run record、lease、pause/resume、recover、watchdog、supervisor

这样即使应用级保活失败，任务层仍然可以恢复。

## 6.3 应用级保活的现实原则

应用级保活要现实，不应建立在不可控幻想上。

建议原则：

1. 不承诺所有平台都能无限后台运行。
2. 优先保证：
   - 可恢复
   - 可提示
   - 可继续
3. 把“持续后台跑很久”视为增强能力，而不是基线。

这与 docker / 桌面 companion / 外置 daemon 的长期方向是兼容的。

## 七、写作策略层应怎么设计

## 7.1 不是只有“两种模式”

用户举的两种参考方向是有价值的：

1. 完全由智能体演进
2. 在容易跑偏时停下来让用户抉择

但更合理的设计不是只做两个单选按钮，而是抽成可扩展策略轴。

至少应表达：

1. `autonomy_level`
   - 智能体自动推进程度
2. `checkpoint_sensitivity`
   - 多大偏差/不确定性就该请求用户
3. `research_rigour`
   - 对资料严谨性的要求
4. `continuity_risk_tolerance`
   - 对设定漂移、风格漂移的容忍度
5. `creative_branching_policy`
   - 分岔时是继续收敛、主动提问、还是保持开放

## 7.2 这层应由谁决定

默认情况下，这层不应要求普通用户先手动配满。

更合理的顺序是：

1. 项目类型给默认策略
2. 智能体在演化阶段可建议调整
3. 用户可在高级设置里修改
4. `supervisor` 只消费已解析后的结果

这样可以同时满足：

1. 不增加主流用户心智负担
2. 保留高级控制能力
3. 不把策略逻辑写死在某个项目类型里

## 7.3 策略层与用户确认点的关系

用户确认点不是系统失败，而是策略层主动产出的正常行为。

所以应显式区分：

1. `waiting_user_for_story_decision`
2. `waiting_user_for_permission`
3. `waiting_user_for_manual_recovery`

这三类等待用户，原因完全不同，不应继续混成一个 `waiting_user`。

## 九、对后续实现的约束

## 9.1 应优先守住的原则

后续不管在哪个会话里实现，都应守住：

1. `watchdog` 只做活性与前进性监察。
2. `supervisor` 继续做结构化调度决策。
3. 写作策略层不污染 heartbeat / lease / pause-resume 基础设施。
4. 目标模式复用控制面骨架，不另起第二套连续任务系统。
5. 应用级保活与任务控制面分层，不互相冒充。
6. `watchdog` 服务所有连续任务族，不只服务长篇写作。
7. 参考提取挂载层的主事实源收口，应优先修适配器出口，不要误判成“再加一个 toolcall 就好了”。
8. 提取类工具默认只对提取 / 研究相关智能体组开放，再通过暴露策略有限扩展到其他任务族。

## 9.2 应避免的坏实现

需要明确避免：

1. 把剧情判断塞进 watchdog。
2. 把移动端息屏问题塞进 long-task supervisor。
3. 把目标模式做成一套完全独立的 runtime。
4. 把策略层简化成一个无法扩展的二选一开关。
5. 把所有 `waiting_user` 混成同一状态。
6. 把 `watchdog` 只绑在长任务线程上，让提取、研究、导入各自重写保活语义。
7. 误把“当前落到了 json”解释为“因为没有 sqlite toolcall”，从而绕过真正的挂载层设计问题。
8. 让普通写作智能体默认拿到整套重型提取工具，而不经过任务画像与暴露策略控制。

## 9.3 当前最合适的落地方向

从实现顺序上，最自然的推进方式是：

1. 继续保持当前 supervisor/control-plane 主线不推翻。
2. 在它之上补最小 watchdog 生命周期和 lease 行为。
3. 让参考提取 / 研究整编也接入统一 continuous-task watchdog profile。
4. 再给目标模式接入轻量 controller profile。
5. 之后把参考提取挂载链从 local json repositories 收口到 sqlite-first substrate。
6. 最后再考虑应用级保活适配和移动端平台策略。

这样不会把问题做得更复杂，也能保持已有设计继续积累。

## 十、最终结论

这几轮新增讨论最值得记住的，不是某个具体实现点，而是下面这组边界：

1. **任务级保活** 与 **应用级保活** 必须分层。
2. **watchdog** 值得要，但只能做最小活性保底。
3. **supervisor** 仍应是调度决策中心。
4. **目标模式** 应视为轻量连续任务，而不是长任务系统的拙劣复制。
5. **写作策略层** 应独立存在，用来控制故事推进与用户介入密度，但不能吞掉调度层。
6. **参考提取 / 研究整编** 也属于连续任务族，应共享 watchdog / supervisor 基础设施。
7. **提取落盘没有进入 sqlite** 目前首先是挂载层持久化出口问题，而不是简单缺少某个 toolcall。
8. **提取类工具** 应以提取智能体组为默认宿主，但必须配套明确的暴露策略，而不是硬写死或完全裸奔。

如果后续实现能一直守住这几条，项目的控制面就会越来越清楚；如果再混回去，后面无论是长任务、目标模式、移动端保活还是资料型任务，都会重新缠成一团。

## 十一、`watchdog` 与连续性冲突的职责边界

## 11.1 实时稳定性确实该由 `watchdog` 兜底，但只兜“运行”

这次哈利波特参考提取的真实现象已经说明了一点：

1. 提取链并不是完全提不出来。
2. 真实运行里仍会遇到 provider `500`、超时、无前进、任务中断等问题。
3. 这些问题首先是运行时稳定性问题，而不是知识结构设计本身的问题。

因此，用户提出“这不正是 `watchdog` 该做的吗”，判断是成立的，但要严格限定语义：

`watchdog` 应兜住的是：

1. provider 500 / timeout / transient failure 后的重试窗口
2. 长时间无心跳、无新 checkpoint、无状态推进
3. 运行实例被宿主或上游打断后的恢复触发
4. lease 过期、dispatcher 停摆、supervisor tick 丢失
5. pause / resume / cancel 的活性收口

它不应兜住的是：

1. 这条知识是否足够完整
2. 这段角色描写是否与前文性格冲突
3. 作者是否遗忘设定
4. 哪条冲突事实应被视为当前 canon

一句话：

```text
watchdog 负责“别死、死了拉起、拉起后能续”
不负责“内容是否真对、冲突怎么解释”
```

## 11.2 “作者失忆 / 设定冲突”不能并入 `watchdog`

用户举的韩立例子很典型，而且不是特例：

1. 角色前后性格变化可能是正常成长。
2. 也可能是阶段性策略变化。
3. 也可能是叙事视角差异。
4. 当然也可能真是作者遗忘、笔误或后设 retcon。

这类问题如果塞进 `watchdog`，会立刻把它从“最小保活层”污染成“又一个会读正文、会猜文学语义的隐式大脑”，这是我们当前必须避免的。

因此这里要补一个明确边界：

1. `watchdog`
   - 只看运行活性和前进性。
2. `supervisor`
   - 只消费结构化状态，决定 retry / recover / wait / stop。
3. `continuity / audit layer`
   - 才负责保留、归并、解释和审计设定冲突。

## 11.3 对“冲突事实”的正确态度不是覆盖，而是保留证据

这部分如果继续做成“新事实覆盖旧事实”，后面无论是同人、拆书、长篇回收还是参考写作，都会越来越脆。

更自然的模型应是：

1. `fact evidence`
   - 记录提取到了什么、来自哪里、证据锚点是什么。
2. `conflict cluster`
   - 把可能在说同一主体同一属性、但值不同的事实聚成一簇。
3. `project canon decision`
   - 项目级决定当前采用哪条解释、哪条版本、哪种阶段性理解。
4. `review alert`
   - 在实际写作或提取使用时提示“这里有未解释冲突”。

要点不是立刻断定谁对谁错，而是：

1. 先保留。
2. 再归并。
3. 再分类。
4. 最后由项目决议决定当前消费口径。

## 11.4 更合理的冲突分类

后续实现如果做连续性审计，不应只有“通过 / 失败”二元，而应至少能区分：

1. `正常演化`
   - 性格成长、关系变化、实力变化带来的自然转变。
2. `条件性变化`
   - 平时谨慎，但在特定压力下会冒险。
3. `视角差异`
   - 角色自述、旁人评价、作者旁白不一致。
4. `世界线或记忆条件变化`
   - 重生、回档、失忆、多世界、附身、人格偏移。
5. `未解释冲突`
   - 看起来明显矛盾，但文本没有给足桥接。
6. `高疑似作者失误 / retcon`
   - 前后互斥且难以合理解释。

关键是：后两类也不能删证据，只能标状态。

## 11.5 这些冲突该在哪个阶段处理

不应指望某一层“一口气处理完”。更合理的是分阶段：

1. `提取阶段`
   - 只保留，不裁决。
2. `归档 / 建库阶段`
   - 形成冲突簇与候选解释。
3. `项目演化 / 写作前规划阶段`
   - 明确当前项目采用哪种 canon 或解释。
4. `生成阶段`
   - 只把当前有效设定和高风险冲突提醒喂给写作智能体。
5. `审核阶段`
   - 检查本轮输出是否违背项目当前采纳的连续性，而不是重判整个原作真相。

所以我们这里要明确补一条长期约束：

```text
程序负责发现冲突候选
智能体负责提出解释
项目决议负责确定当前采用口径
```

## 十二、参考提取存储现实与原设计目标之间的落差

## 12.1 当前真实状态：不是“只有 md”，但也还不是“以 sqlite 为主”

这轮实际产物可以明确说明当前状态：

1. 可读层：
   - `knowledge/项目知识摘要.md`
   - `knowledge/设计元素摘要.md`
   - `references/引用作品边界.md`
2. 隐藏事实层：
   - `.novel_agent/information/knowledge_cards/*.json`
   - `.novel_agent/information/design_elements/*.json`
   - 其他同类 `information/*.json`
3. `sqlite`：
   - 项目整体架构里已经有 `sqlite_project_store`、`sqlite_reference_evidence_substrate` 等基础设施
   - 但本次参考提取产物并没有落成我们想要的“项目级可分发主知识基底”

换句话说，当前不是“md 当真相”，而是：

```text
json 是当前事实源
md 是当前可读投影
sqlite 基础设施存在，但尚未成为这条链的主承载
```

这和最初希望的“这部分可分发、可映射查找、应以 sqlite 为主”之间，确实还有落差。

## 12.2 现状为什么不够理想

### A. `markdown projection` 体积太重

对于参考提取这种高密度知识资产：

1. 大量结构化事实已经存在于隐藏层。
2. 再把几乎完整的结构化内容投成庞大 `md`，会让：
   - token 消费变高
   - 激活时摘要选择更难
   - 用户浏览时噪音更多
   - 分发时包体更臃肿

`md` 应承担的是：

1. 浏览入口
2. 轻摘要
3. 人工校对入口
4. 少量草案回流

不应承担的是：

1. 完整数据库镜像
2. 巨量结构化快照回放
3. 面向智能体的主查询面

### B. 来源显示为原始本地文件路径，不适合作为分发语义

当前投影里直接显示：

1. `D:\FlutterProjects\NovelAgentFlutter\references\files\Harry Potter - Volume 1 Raw.txt`

这在本地调试时可接受，但在项目分发、共享、导出时不优雅，也不稳定：

1. 机器相关
2. 用户名相关
3. 目录结构相关
4. 不适合作为持久引用 ID

因此来源层需要分成两类身份：

1. `display identity`
   - 如：`Harry Potter - Volume 1 Raw`
   - 来源类型、语言、版本标签、导入批次
2. `resolver identity`
   - 如：内部 `source_id`、content hash、attachment id、archive uri

而原始绝对路径最多只能作为：

1. 本地调试痕迹
2. 可选的宿主级附加元数据

不能继续作为分发态主来源名片。

### C. `json` 文件树不利于“知识基底级复用与映射查询”

`json` 文件树的优点是直接、可读、容易落地。

但它在“大框架 / 可分发知识资产 / 项目级映射调用”场景里的缺点也很明显：

1. 批量查询、过滤、关联不自然
2. 跨条目关系、冲突簇、版本簇难以优雅表达
3. 分发时文件数膨胀
4. 合并、迁移、索引维护成本高
5. 对“工具按需检索”不如数据库形态自然

所以从长期设计上看，用户这次指出的问题是对的：

```text
当前形态更像“调试期结构化落盘 + 可读投影”
还不像“最终知识基底产品形态”
```

### D. 当前没写成 sqlite，更像“挂载出口设计”问题，不像“工具数量不够”

这一点需要单独写出来，防止后面方向走偏。

当前真实链路是：

1. 提取执行与参考基底阶段：
   - 已有 `SqliteReferenceEvidenceSubstrate`
2. 项目挂载阶段：
   - 由 `ProjectReferenceExtractionMountService` 组装
   - 调用 `LocalKnowledgeCardRepository` 等本地 repository
   - 最终写到 `.novel_agent/information/**/*.json`
3. 可读投影阶段：
   - `ProjectInformationProjectionWriterService`
   - 生成 `knowledge/*.md`、`references/*.md`

因此最准确的判断不是：

1. “缺了一个写 sqlite 的 toolcall”

而是：

1. 这条链执行完成后，项目挂载出口仍然指向本地 JSON 仓储
2. 所以即便智能体本轮提取得再好，最终项目内主事实源仍会落成 `json + md projection`

这意味着后续修正优先级应是：

1. 先改挂载出口与 repository 组合
2. 再考虑是否需要补更细的工具合同
3. 而不是先扩大量工具调用面

## 12.3 更合理的最终方向

这里最稳的收口不是“直接砍掉 md”，也不是“继续默认 json 就够了”，而是三层分工：

1. `SQLite substrate`
   - 作为项目级或资产级主查询基底
   - 存 entry、source、evidence、conflict、projection index、tag、version
2. `JSON interchange`
   - 只承担导入导出、调试快照、兼容层
   - 不是长期主事实源
3. `Markdown projection`
   - 只保留轻量摘要、人工检查视图、草案回流入口

也就是说：

```text
sqlite 做主基底
json 做交换与兼容
md 做轻投影
```

这和我们早前的存储设计文档也是一致的，只是当前参考提取链还没完全走到那里。

## 12.3A 提取相关工具应按“任务族 + 智能体组 + 暴露策略”开放

既然这条链不是简单缺 toolcall，那工具设计就要更克制、更分层。

提取相关工具不应默认铺给所有智能体，而应至少遵守三层约束：

1. `任务族`
   - 写作任务
   - 提取任务
   - 研究任务
   - 审核任务
2. `智能体组`
   - 主写作组
   - 提取组
   - 审核组
   - 研究组
3. `暴露策略`
   - 默认开放
   - 需要显式确认
   - 仅宿主 / supervisor 可调用

对参考提取而言，更合理的默认是：

1. 重型源材料切片、证据绑定、批次续跑、挂载确认类工具
   - 默认只给提取组 / 研究组
2. 普通写作组
   - 默认只消费已挂载好的知识与引用摘要
   - 不直接拥有整套重型提取权限
3. 当写作过程中确实发现知识缺口时
   - 由 supervisor 或任务画像触发“研究 / 提取子流程”
   - 而不是让主写作线程临时拿满全部提取能力

这样做的好处是：

1. 降低普通写作线程工具干扰
2. 保持提取链的专业化与稳定性
3. 让权限与能力暴露有清晰产品语义

## 12.4 `md` 不该被彻底废掉，但必须明显瘦身

`md` 仍然有价值，因为它天然适合：

1. 用户阅读
2. PR / artifact 检查
3. 人工补充草案
4. 模型在低权限浏览模式下先看摘要再决定是否深挖

但它必须瘦身到“摘要层”，而不是“结构化全量镜像层”。

更合理的投影形态应是：

1. 顶部摘要：
   - 条目总数
   - 主题分布
   - 高风险冲突数
   - 来源覆盖概况
2. 小样本明细：
   - 每类展示少量高价值条目
3. 可跳转索引：
   - 指向 `sqlite` 中的稳定 entry id 或附件 id
4. 草案块：
   - 允许用户补充或修正

而不是整份大快照。

## 12.5 来源展示应采用“资产身份 + 可选本地解析”

后续来源层应明确区分：

1. `source_asset_id`
2. `source_display_name`
3. `source_kind`
4. `source_language`
5. `source_version`
6. `resolver_uri`
7. `local_hint_path`（可选、非分发关键字段）

这样可以同时满足：

1. 本地调试可回到原文件
2. 分发时不暴露机器路径
3. 导入他人资产时仍能稳定映射
4. 智能体工具调用能用稳定 ID 检索

## 12.6 对当前项目的实际结论

这部分需要非常诚实地记下来，避免后面又默认“已经做完了”：

1. 当前参考提取链的内容结构，已经比纯 `md` 阶段前进很多。
2. 当前也不是没有结构化事实源。
3. 但它仍以 `json + markdown projection` 为主，不符合我们最终希望的“可分发、可映射、以 sqlite 为主基底”的终态。
4. 同时，来源在投影层直接暴露绝对文件路径，也不适合作为资产级分享与复用方案。
5. 当前偏差首先是挂载层 persistence target 仍指向 local json repositories，而不是简单缺少一个 sqlite toolcall。
6. 提取类能力后续应优先绑定到提取智能体组，再通过暴露策略决定是否向其他任务族受控开放。

因此后续应明确收口到：

1. `sqlite substrate first`
2. `md summary projection only`
3. `absolute local path demoted to optional debug metadata`
4. `stable source asset identity promoted to first-class contract`

这不是否定当前实现，而是给它一个更清楚的演化终点。
