## 1. 本文解决什么

这份文档用于把最近几轮关于参考提取系统的新增结论，以及上一个目标模式没有继续往下推进的断尾部分，一次性收口成下一轮可执行的总分析。

本轮明确要解决的不是单一 bug，而是下面四类问题之间的关系：

1. 参考提取主链已经立起来，但还没有完成“整本书级别高保真提取”的运行时收口。
2. 摄取预算、分批规划、覆盖状态还停留在分析层，没有正式落到 runtime 主链。
3. 参考提取系统之外，整个项目仍需要做一次非针对性的广泛扫描，重点修稳定性，但不只修稳定性。
4. 下一轮目标模式既要继续补参考提取，也要承担全项目可用性治理，并最终用真实提取与真实写作进行回归验证。

因此，本文的作用不是替代任务顺序文档，而是为下一轮目标模式提供：

1. 已确认的架构结论。
2. 明确保留与明确否定的实现方向。
3. 上一轮尚未继续做下去的尾项。
4. 下一轮目标模式应该如何统筹“项目全面扫面 + 提取主链收口 + 真实验证”。

## 2. 已经确认、不得回退的架构结论

### 2.1 当前程序化抽取仍只是 bootstrap，不是完整提取

这条已经反复确认，不能再摇摆：

```text
`ReferenceSourceDocumentExtractionService`
的职责仍然只是 source bootstrap / seed extraction / evidence scaffolding。
```

它负责：

1. 读取原始文本。
2. 基础切段。
3. 初始 seed 条目。
4. 证据底稿。

它不负责：

1. 整本书级语义定稿。
2. 风格全貌提炼。
3. 可复用参考资产包的最终审核。

### 2.2 正式参考提取是一条重任务主链

真正的 `reference_extraction` 已经被确认为：

1. 独立任务族。
2. 智能体主导语义提取与审核。
3. 程序负责导入、预算、切批、证据定位、调度、持久化和投影。
4. 默认应按重任务的纪律设计，而不是当成“补一个 prompt”。

### 2.3 三层信息架构继续保留

必须继续保留：

1. `ReferenceEvidenceSubstrate`
2. `ProjectReferenceAttachmentLayer`
3. `ProjectInformationCapabilityLayer`

下一轮不得为了提取方便，把应用级与项目级重新糊在一起。

### 2.4 不允许把哈利波特、快穿、死亡回归等题材写死进核心

这些例子仍然只是测试和压力样本，不是 core 语义。

下一轮如果为了通过测试而在 core 中显式写死：

1. 哈利波特原作结构
2. 多世界穿越
3. 死亡回归
4. 某类特定风格或题材触发分支

都属于明显回退。

## 3. 新增确认的三条运行时结论

### 3.1 分批策略应是“结构优先，预算逼近，超限裂解，缺结构退化”

这一轮已经把分批原则进一步收口，不再只是“能分章就按章”。

正式推荐口径应是：

```text
先尊重显式结构，
再在结构内部贴近预算，
只有结构超预算或结构不存在时，
才进入下一层切分。
```

落地时建议分四层：

1. 显式章节优先。
2. 章内自然结构优先。
3. 无章时按段落簇与结构识别切分。
4. 最后才允许机械窗口兜底。

这意味着：

1. 章节是优先锚点，不是绝对边界。
2. 预算是约束，不是主宰。
3. 允许轻微欠预算，优先保留语义完整性。

### 3.2 当前默认应是单并发，不是多并行

用户最后明确修正了口径：这里要保留的是**单并发**，不是多并发。

这一点现在已经可以定性为正式运行时原则：

```text
参考提取运行时当前默认采用单并发主链，
尤其是重文本消费阶段默认单路执行。
```

原因不是“不会做并行”，而是：

1. 同一段原文被多个线程/智能体重复消费，会直接放大输入预算消耗。
2. 不同模型、不同 provider、不同轮询模型未必共享缓存命中。
3. 对于真实用户成本，这种“看起来优雅”的并发很可能很蠢。
4. 在整本书提取仍未彻底稳定之前，多并发会把问题复杂度和定位成本抬高。

因此当前主线不应做成：

1. 同一 source batch 多个智能体并发重读原文。
2. 同一批原文同时跑多条重提取线程。
3. 把多并发作为默认行为。

### 3.3 仍应保留未来扩展到多并行的合同能力

虽然当前默认是单并发，但也不能把未来路线封死。

下一轮应该保留的是：

1. batch planning 层对未来并行分发的可扩展性。
2. progress / run state 对多批状态记录的可扩展性。
3. execution policy 对未来高级用户开放并行策略的扩展位。

但当前不要求实现真正多并行主链。

更准确的口径应是：

```text
当前默认单并发，
未来可扩展多并行，
但多并行不是本轮交付目标。
```

## 4. 上一目标模式的断尾与当前真实未完成项

上一轮目标模式之后，已经完成了几件重要事情：

1. 参考提取任务族、组覆盖解析、staging/review/finalize 主链已立起。
2. 应用级参考证据基座与项目级挂载/投影主链已基本立住。
3. GUI 已接上最小可用的提取策略选择入口。
4. 一条真实 GUI 提取 probe 已再次跑通。

但这些不等于“整本书级提取系统已收口”。当前剩余未完成项仍然很清楚：

### 4.1 提取主链的 runtime 深化尚未完成

未完成点包括：

1. 摄取预算策略未正式落地为合同与 resolver。
2. batch plan 尚未正式进入运行主链。
3. coverage state / batch progress 尚未成为正式运行资产。
4. 章节优先的自适应切批尚未替换现有 seed 式切段逻辑。
5. 单并发运行纪律尚未显式成为可验证的 execution policy。

### 4.2 项目范围的广泛稳定性扫描尚未开始

用户原本打算让下一轮目标模式做的，并不是只补提取系统，而是：

1. 非针对性、广泛性地扫描整个项目。
2. 抓出存在问题的部分。
3. 对每个问题做针对性处理或完善。
4. 尤其保证一般长任务与内置特殊长任务的稳定性与可用性。
5. 其他模块也要修，不因“重点关注长任务”就忽略其他功能。

这件事在上一轮并没有真正开始做。

### 4.3 真正的整书级提取回归尚未完成

当前虽然已经有最小 GUI 实提 probe，但还没有完成下面这条更重的回归链：

1. 先验证《哈利波特》第一卷提取可用。
2. 再做完整剧情级提取。
3. 再基于提取结果、知识卡与外部研究，实际写出一条派生小说链。

这条链目前仍然只是目标，不是已完成事实。

## 5. 下一轮目标模式不应只盯参考提取

这点非常重要。

虽然最近几轮的讨论都围绕参考提取展开，但用户这一轮明确要求的是：

```text
做一次更大范围的全项目扫描与治理，
只是把“一般长任务 + 内置特殊长任务的稳定性与可用性”
作为尤其关注的重点，
而不是唯一目标。
```

因此下一轮目标模式的正确姿势不是：

1. 只继续埋头做提取 runtime。
2. 只围绕哈利波特提取修修补补。
3. 只做长任务或只做提取，不看其他可用性问题。

下一轮需要的是一个统筹视角：

1. 先广泛扫描。
2. 按严重度分层归类。
3. 逐个收口会影响真实可用性的主问题。
4. 再进行重验证。

## 6. 下一轮的优先级建议

### 6.1 第一优先级：真实可用性的阻断项

优先抓：

1. 会导致长任务中断、挂死、误完成、假成功的运行时问题。
2. 会导致参考提取整书流程无法继续、无法覆盖、无法收口的问题。
3. 会导致 GUI 主路径实际不可用或误导用户的问题。
4. 会导致知识卡、参考挂载、外部研究结果无法被真实消费的问题。

### 6.2 第二优先级：共享主链缺口

例如：

1. 本应普通任务、长任务、拆书、提取共用，却被写死在某一条路径里的逻辑。
2. 本应 core/adapters/app 分层，却落到了 widget、probe 或临时 runtime 补丁里的逻辑。
3. 本应统一的 execution discipline，却被散落在多个入口各写一份的逻辑。

### 6.3 第三优先级：最小 CLI 接口顺手接入

这一轮不用特别关注 CLI，但如果某个核心能力已经在 core/adapters 收口完毕，可以顺手接最小入口。

注意这里只是顺手，不是主线。

## 7. 对参考提取主链的下一轮正式要求

下一轮关于参考提取的实现，不应继续散着做，而应围绕以下收口点展开：

### 7.1 把预算与分批从分析落到合同

至少应正式考虑：

1. `ReferenceIngestionBudgetPolicy`
2. `ReferenceIngestionBudgetResolverService`
3. `ReferenceSourceBatchPlan`
4. `ReferenceSourceBatchPlannerService`
5. `ReferenceSourceBatchProgress`

### 7.2 明确把单并发纪律写进 execution policy

至少要保证：

1. 当前默认单并发。
2. 同一重文本 source batch 不做多线程重复消费。
3. 未来扩展多并行的能力只预留合同，不急着做成默认实现。

### 7.3 用正式验证取代想当然

下一轮如果收口提取 runtime，至少应补：

1. chapter-first batching focused tests。
2. oversized chapter split focused tests。
3. no-chapter dataset fallback focused tests。
4. single-concurrency execution policy focused tests。
5. batch coverage/progress focused tests。

## 8. 最终真实验证链的定位

用户给出的哈利波特派生故事目标，不应被理解成“题材开发”，而应被理解成一条端到端验收链。

这条验收链应表达的是：

1. 系统能否先完成原作提取。
2. 系统能否把提取结果转为可消费参考资产。
3. 系统能否在项目写作时真实调用这些参考资产和知识卡。
4. 系统能否在必要时通过联网研究补足外部知识。
5. 系统最终能否写出一条明显依赖这些信息资产的作品，而不是假装提取后仍全靠模型裸写。

因此：

1. 《哈利波特》第一卷提取可用，是阶段验证。
2. 哈利波特完整剧情提取，是重验证。
3. 基于提取结果写新故事，是端到端消费验证。

这三层都重要，但只有在前两层成立后，第三层才有意义。

---

## 9. 下一轮不应被当作成功的假信号

以下情况都不应被视为成功：

1. 只把分批分析写成文档，没有进入 core 合同。
2. 只把“默认单并发”写进文档，没有 execution policy 与 focused 验证。
3. 只跑一个小 probe，就把整本书提取说成可用。
4. 只修哈利波特相关链路，其他长任务稳定性依旧脆弱。
5. 只在 GUI 上看起来能点，但 runtime 主链仍靠临时补丁。
6. 把哈利波特或修仙穿越例子写死进核心逻辑里。
7. 为了追求“完成很多事”，继续制造新的大文件或万能 service。

---

## 10. 最终结论

把这几轮真正敲定的内容收成一句话：

```text
下一轮目标模式不是单纯继续补参考提取，
而是要在“全项目广泛扫描与真实可用性治理”的大框架下，
优先收口参考提取 runtime、一般长任务与内置特殊长任务稳定性，
并以哈利波特提取与消费链作为最终重验证；
其中参考提取当前默认保持单并发，
但要为未来高级用户可配置的多并行扩展预留合同能力，
不得把多并行作为当前默认实现。
```

这才是下一轮最稳、最诚实、也最不容易再次返工的推进方式。
