# 表达限制与智能体审核架构分析 2026-06-06

## 目的

本文只做主线分析与架构收口，不直接展开下一轮实现清单。

这一轮要解决的核心，不是“去 AI 没生效”这一个现象，而是更底层的架构边界：

1. `去 AI` 只是一个内置表达限制 preset，不是特殊架构。
2. 表达限制必须是所有项目类型共享的通用能力，不应只服务于某条写作链。
3. 程序可以检查客观合同、收集表面证据，但不应直接充当文学表达裁判。
4. 主观性的“是否符合表达限制”应进入智能体审核合同，而不是继续堆程序化文本规则。
5. 普通写作、长任务、拆书/解书、总结/解说都应复用同一套约束与审核骨架，只在执行强度和调度方式上不同。

这份文档吸收并收口了最近几轮已经确定的共识：

1. `profile / binding / execution policy` 必须分层。
2. 强策略不能污染工具 schema、路径、权限 payload、研究执行等纯技术轮次。
3. 快穿、死亡回归、多世界之类只是压力测试，不应写死进核心。
4. 信息收集属于证据纪律，不属于表达限制，但会与表达限制一起进入共享执行约束层。
5. 长任务稳定性要靠调度、合同、审核与恢复，而不是更多题材特判。

---

## 一、这轮首先确认的事实

### 1.1 `去 AI` 不是特殊系统

`de_ai` 只是：

1. 一个内置 expression constraint profile。
2. 一组用户可理解的表达规则。
3. 一组可观测 risk signals。

它不是：

1. 系统总名。
2. 单独的工作流类型。
3. 可以被程序硬编码清洗的特权 preset。
4. 未来其他表达限制的母版。

这意味着后续核心代码不应再出现：

1. 因为 profile id 是 `de_ai`，所以额外走一条特殊逻辑。
2. 因为某个 preset 命中了一些表面词形，所以程序自动改正文。
3. 因为 probe 特别关注 `去 AI`，就让 production runtime 逐步长成 `去 AI` 专用后处理器。

### 1.2 程序化表面清洗不是正确主线

这轮已经验证出一个重要边界：

把 Markdown 分割线、破折号、`不是……而是……` 之类风险项做成程序化扫描，用来生成证据，是可以讨论的。

但把它们直接做成：

1. 自动替换正文。
2. 自动判定“已经通过表达限制”。
3. 自动代替审核智能体得出主观文学结论。

这条路是不对的。

原因不是实现得还不够细，而是方向本身会持续长偏：

1. 表达限制不只有 `去 AI`。
2. 风险信号不是禁词表。
3. 文学表达天然存在“合理偶发命中”。
4. 每新增一种表达限制，如果都要补程序规则，核心层会越来越重、越来越题材化。

### 1.3 这不是只影响长任务的问题

用户这轮提醒得很对：很多约束逻辑并不属于“普通任务”或“长任务”其中之一，而是所有写作任务共用的。

表达限制、字数策略、资料纪律、章节交付、路径正确性、正文存在性，都属于共享执行事实。

因此这里不能继续按：

1. 普通任务一套。
2. 长任务一套。
3. 拆书一套。

分别堆实现。

更合理的是：

1. 共享层定义事实、合同、审核接口、恢复接口。
2. 各类任务只决定自己消费这些能力的强度、节奏和调度方式。

## 二、应当坚持的总边界

### 2.1 表达限制是什么

表达限制是“文本呈现约束”。

它负责约束：

1. 正文长什么样。
2. 哪些表达习惯要压低。
3. 哪些文本风险需要审核关注。
4. 哪些规则要作为项目资产长期保留。

它不负责：

1. 信息是否真实。
2. 外部资料是否需要联网收集。
3. 章节是否成功交付。
4. 输出路径是否正确。
5. 调度是否继续。

这些能力会和表达限制协作，但不是同一层。

### 2.2 程序应负责什么

程序应负责客观、可稳定复现的部分：

1. 本次运行有哪些 profile 与 binding 生效。
2. 当前 execution policy 是什么。
3. 哪些轮次可以注入表达限制，哪些轮次必须排除。
4. 是否真的生成了正文。
5. 正文是否落到了正确路径。
6. 字数是否严重偏离。
7. 是否存在 review evidence。
8. 是否需要调度 repair / retry / pause / waiting_user。

程序可以额外负责“证据增强”，例如：

1. 扫描正文里是否命中某些 risk signals。
2. 把这些命中以结构化方式挂进 review context。

但程序不应直接负责：

1. 判定文学表现是否自然。
2. 判定角色声音是否被洗平。
3. 判定这次 `不是……而是……` 是否真的不自然。
4. 判定这章是否已经满足用户审美意义上的“去 AI”。

### 2.3 智能体应负责什么

智能体审核层应负责主观、上下文依赖强的部分：

1. 文本是否明显回到模板腔。
2. 表达限制是否与角色声音冲突。
3. 风格修订会不会破坏剧情完整性。
4. 某些风险命中是自然表达，还是重复模板。
5. 当前应该提醒、下章调整，还是直接返修。

这也解释了为什么“表达限制主观审核”不能再继续堆在程序里。

## 三、推荐的正式分层

### 3.1 资源层：`ExpressionConstraintProfile`

这一层继续表示“规则资产本身”。

它包含：

1. `id`
2. `display_name`
3. `summary`
4. `kind`
5. `rules`
6. `risk_signals`
7. `recommended_scope`
8. `metadata`

这一层不应知道：

1. 当前项目是否启用。
2. 本轮运行是否注入。
3. 注入多强。
4. 违规后怎么处理。

### 3.2 项目层：`ProjectExpressionConstraintBinding`

这一层继续表示“项目如何使用这些 profile”。

它应当继续承担：

1. 是否启用。
2. 是否默认对项目生效。
3. 目标智能体、模式、阶段。
4. 权重与优先级。
5. 项目内自定义 profile 的快照持久化。

这一层不应被“应用级内置 profile 的改动”反向破坏项目可复现性。

### 3.3 执行层：`ExpressionConstraintExecutionPolicy`

这一层表示“本次运行如何消费已经绑定的表达限制”。

这里已经有一个正确方向：

1. `disabled`
2. `adaptive`
3. `force`

以及：

1. injection strength
2. review requirement
3. violation disposition
4. technical turn exclusion
5. runtime escalation

这一层是对的，应继续发展。

### 3.4 审核层：`ExpressionConstraintReviewContract`

这一层是目前最需要正式化的缺口。

建议不要再把“review projection”既当提示、又当审核结论、又当 gate 输入。

更自然的做法是新增一层更明确的小合同，例如：

`ExpressionConstraintReviewContract`

至少应包含：

1. `status`
2. `reviewer_agent_id`
3. `reviewer_role`
4. `policy_mode`
5. `review_basis`
6. `findings`
7. `risk_level`
8. `recommended_action`
9. `repair_prompt_brief`
10. `evidence_paths`
11. `voice_protection_notes`
12. `metadata`

其中：

`review_basis` 表示证据来自哪里，例如：

1. 正文摘录
2. profile rules
3. risk signal 命中
4. 前文 continuity 片段
5. 上一章 review 结果

`findings` 应允许同时承载：

1. 偶发风险
2. 连续风险
3. 结构性冲突
4. 声音保护提醒
5. 可接受但需观察

### 3.5 gate / supervisor 层

gate 层不应直接读 profile id 或直接读正文字符串去下最终判断。

更合理的是：

1. 消费客观执行事实。
2. 消费审核合同。
3. 再决定本轮动作。

动作建议维持在有限集合：

1. `none`
2. `remind`
3. `adjust_next`
4. `repair`
5. `pause_for_manual_attention`

这样普通写作、长任务、拆书都可以复用。

## 四、审核应该怎样与智能体组结合

### 4.1 单智能体场景

如果当前项目没有独立 reviewer / critic / editor 智能体，那么：

1. 主智能体先完成写作。
2. 主智能体再按显式审核合同对自己的文本做 review。
3. 程序只负责把 review 结果结构化记录，并把需要的 repair 调度起来。

这里的关键不是“自审是否完美”，而是：

1. 有正式审核步骤。
2. 有结构化审核结果。
3. 审核结论可以进入后续 repair / queue / checkpoint。

### 4.2 多智能体场景

如果当前项目智能体组里存在 reviewer / critic / editor：

1. 写作主智能体负责产出正文。
2. 审核智能体拿到结构化 review brief。
3. 审核智能体不共享主智能体的全部隐藏上下文。
4. 审核智能体只消费项目资料、章节产物、相关 continuity、表达限制合同和必要的执行摘要。

这很重要，因为如果 reviewer 直接共享 writer 的整段隐式上下文，审核会越来越像同一条思维链的回声，而不是相对独立的质量检查。

### 4.3 为什么这比程序裁判更合适

因为这里真正难的不是识别 `——` 或 `不是因为`，而是判断：

1. 这一处是否自然。
2. 这一处是否过量。
3. 修了以后会不会把人物声音修没。
4. 当前文本风险是否值得打断主链。

这类判断更接近“专业审核”，不适合继续强行程序化。

## 五、与普通写作、长任务、拆书的统一方式

### 5.1 普通写作

普通写作不必强制走完整长任务重调度，但仍应复用：

1. execution policy
2. chapter delivery contract
3. review contract
4. repair scheduling contract

区别只在于强度更轻：

1. 可以写完一章后再触发轻量 review。
2. 可以只在明显风险时才触发 repair。
3. 可以把更多情况收束成提醒，而不是暂停主流程。

### 5.2 长任务

长任务则应把这套能力接入 supervisor / queue / checkpoint：

1. 连续风险要能累计。
2. review 结果要能形成 checkpoint evidence。
3. repair 要能物化为真实队列任务。
4. 必要时暂停，而不是任由问题连续扩散几十章。

但这里必须补一个更重要的边界：

**一般长项目的审核不是“要不要有”的问题，而是“以什么强度、什么时机、挂在哪条调度线上”的问题。**

长项目如果完全没有审核层，表面上吞吐更高，实际上会引入更大的系统性成本：

1. 角色声音、叙事边界、设定状态、资料纪律会缓慢漂移。
2. 表达限制与字数策略的失控会在十几章后才被人工发现。
3. 错误一旦积累到几十章，修复成本远大于中途 checkpoint。
4. “写作成功”与“产物可继续使用”会重新混在一起。

所以对一般长项目而言，审核层不是特殊高级功能，而是稳定可用所必需的基础设施。

### 5.2.1 一般长项目为什么必须有审核层

这里说的“审核”，不等于每章都重跑一遍昂贵的全量审稿。

更准确地说，一般长项目至少需要四类审核能力：

1. 客观交付审核：
   章节是否存在、路径是否正确、正文是否为空、字数是否严重失控、工具交付是否完整。
2. 轻语义审核：
   当前章是否明显回到模板腔、边界是否松动、是否出现应尽早止损的重复风险。
3. 检查点审核：
   若干章后统一看角色、关系、设定、节奏、伏笔、资料纪律、表达限制是否在累计漂移。
4. 修复决策审核：
   问题是提醒即可、下一章回调即可，还是必须插入 repair 任务。

没有这四层中的至少前三层，一般长项目会出现一个典型错觉：

```text
任务一直在推进
!=
作品一直在变好
!=
当前产物仍然适合继续往下写
```

### 5.2.2 审核不是全阻塞，而应分层阻塞

一般长项目最容易走偏的地方，是把审核理解成只有两种状态：

1. 完全同步阻塞。
2. 完全异步放养。

这两种都不够好。

更合理的是分层阻塞：

1. `硬阻塞同步审核`
   只处理客观失败或高确定性风险。
   例如：缺正文、错路径、严重字数失控、缺少必须 evidence、repair 任务未完成却继续主链。
2. `轻阻塞同步审核`
   写完一章后用极轻量的 review contract 给出继续 / remind / adjust_next。
   它应尽量短小，不抢占主生成时间。
3. `异步后台审核`
   对主链不立即阻塞，但持续生成 review evidence、累计 drift、必要时向 supervisor 报警。
4. `检查点同步审核`
   每个 batch、阶段结尾、里程碑章后执行。
   这类审核可以更重，因为它本来就是长任务的节奏转换点。

也就是说，真正合理的系统不是“同步或异步二选一”，而是：

```text
每章结束后有轻量同步 gate
后台有持续异步审核
阶段边界有明确同步 checkpoint review
```

### 5.2.3 主生成线程与异步审核线程的职责边界

这里建议正式拆成四条 lane，而不是让一条主线程承担所有责任：

1. `generation lane`
   负责生成正文、调用写作工具、完成章节交付。
2. `review lane`
   负责消费正文与上下文，产出 review contract。
3. `repair lane`
   负责把 review 物化成可执行修订任务，而不是临时提示补丁。
4. `supervisor lane`
   负责判断是否继续、暂停、等待用户、提升审核强度或压缩后续 batch。

四条 lane 中，真正应该始终阻塞主生成线程的，只有高确定性的硬失败：

1. 没写出正文。
2. 写错目录。
3. 章节交付不完整。
4. 严重字数越界且已达到当前策略的硬 gate。
5. 已经存在必须先完成的 repair 任务。

而下面这些更适合优先走异步或 checkpoint 审核：

1. 表达限制轻度失真。
2. 风格开始漂移但尚未破坏可读性。
3. 某些资料纪律存在疑点但不一定要当章中断。
4. 角色声音轻微发散。
5. 节奏或场面组织开始出现重复模板。

### 5.2.4 一般长项目最推荐的审核节奏

如果站在“可发布软件”的角度看，一般长项目不该默认走两种极端：

1. 每章都做全量同步重审。
2. 一口气跑几十章再回头看。

更推荐的默认节奏是：

1. 每章结束：
   先跑客观交付 gate。
2. 每章结束后：
   跑一个极轻量 review contract。
   目的不是当场挑完所有文学毛病，而是尽早发现“已经开始歪”的信号。
3. 每 3 到 5 章，或 batch 结束后：
   跑一次更完整的 checkpoint review。
4. 每次 checkpoint 后：
   supervisor 根据 review 结果决定：
   继续、缩短下个 batch、插入 repair、等待用户、切换更强审核策略。

这里不应该把“每几章 checkpoint”写死成唯一常量。

更好的做法是让它由策略决定，并允许根据风险动态收紧：

1. 低风险项目：
   batch 可以更长。
2. 高约束项目：
   batch 应更短。
3. 连续 drift 项目：
   checkpoint 间距自动缩短。
4. 用户手动盯盘项目：
   可以降低后台审核频率，但不能取消客观 gate。

### 5.2.5 审核必要性不是只针对表达限制

虽然这轮讨论是从表达限制出发，但一般长项目里的审核层不能只服务于表达限制。

它至少还要稳定承接：

1. continuity drift
2. role / relation / world state drift
3. information evidence discipline
4. chapter length discipline
5. delivery integrity
6. user-visible style or format regressions

否则会出现另一种局部最优：

```text
表达限制审核做得很认真
但真正把长项目写坏的其它漂移没人管
```

### 5.3 拆书 / 解书 / 总结 / 解说

这里最容易误走偏路。

拆书和解说并不是都要“套正文去 AI”。

更合理的做法是：

1. 先由 execution policy 判断当前任务是不是“用户可见文本产物”。
2. 如果是分析、整理、抽取、研究，表达限制应降级甚至跳过。
3. 如果是续写正文、书评式解说、对外展示性总结，则可以启用轻量或标准表达限制。

也就是说，表达限制作用在“产物类型”，而不是“项目名”。

## 六、与字数策略、信息纪律的关系

### 6.1 与字数策略的关系

字数策略和表达限制都属于共享执行约束层，但不是一回事。

字数更适合程序化：

1. 目标
2. 偏差
3. 容忍区间
4. 严重失控阈值

表达限制更适合“程序取证 + 智能体审核”：

1. 程序记录命中与缺失证据。
2. 智能体审核判断文学层面的真实风险。

所以这两者应并列存在，而不是相互吞并。

### 6.2 与信息纪律的关系

信息纪律不是表达限制，但在实际运行中会交叉影响表达限制。

例如：

1. 写历史题材时，如果事实没收集好，文本即使“很自然”也可能是错的。
2. 写架空科技时，如果资料纪律缺位，表达限制修得再像人，也只是更自然地胡写。

所以顺序上应当是：

1. 先确认是否需要信息收集。
2. 再保证写作执行约束被正确注入。
3. 再进入审核与 gate。

不能把信息纪律塞进表达限制，也不能让表达限制替代信息纪律。

## 七、应明确拒绝的几条错误方向

### 7.1 拒绝把 preset id 变成 production branch

以后不应再出现：

1. `if profileId == de_ai`
2. `if profileId == strict_pov_boundary`
3. `if profileId == low_jargon_narration`

这类 production 逻辑分支。

如果某个表达限制真的需要特别的审核提示，应优先通过：

1. `kind`
2. `rules`
3. `risk_signals`
4. `metadata`
5. 审核 prompt 变量

表达，而不是硬编码 preset id。

### 7.2 拒绝程序直接改正文来“实现表达限制”

程序可以：

1. 发现风险。
2. 记录风险。
3. 触发 repair。

程序不应直接：

1. 把正文里的某些符号替换掉。
2. 自动删段落。
3. 自动把某种句式换写成另一种句式。

这会让 production runtime 逐步长成“文本后处理补丁中心”。

### 7.3 拒绝 probe 独自长成第二套业务中心

probe 可以帮助发现问题，但：

1. probe 不应定义 production 真相。
2. probe 不应拥有一套 production 没有的私有裁判。
3. probe 的断言应尽量消费正式 contract。

否则后面会出现“probe 看起来修好了，真实链路依然歪着”的假收敛。

---

## 八、与参考项目的取舍

可吸收的不是某个参考项目的具体代码，而是它们的产品事实：

1. 后台任务记录要稳定。
2. 上下文层级要明确。
3. 审核与写作要分步。
4. 章节质量问题不能只靠事后人工翻文件发现。

就这一块而言，真正值得吸收的是：

1. 后台任务表与可恢复记录。
2. 写作与审核的分工。
3. 章节上下文、人物、组织、伏笔、资料等分层喂给不同角色智能体。
4. 长流程里有明确 checkpoint，而不是一口气盲跑。

### 8.1 成熟项目真正值得吸收的审核节奏

从已有成熟项目和本地参考材料里，真正值得吸收的不是“它用了哪个模型”，而是它们怎样把分析和生成拆开：

1. 章节生成可以带可选同步分析。
2. 更重的分析可以异步后台落任务。
3. 一旦启用同步分析，严重错误会中断批量生成，而不是继续带着坏状态往下跑。
4. 分析结果会变成任务记录、结构化资产或后续修复入口，而不是一次性日志。

这些产品事实对我们有三个直接启发：

1. 审核不必永远阻塞，但必须始终可落盘、可追踪、可升级。
2. “是否启用同步审核”不应是单布尔开关，而应是策略层能力。
3. 异步审核不是“晚点看看”，而是有正式任务身份的后台工作。

### 8.2 我们最该吸收的不是“同步分析”，而是“同步与异步并存”

单纯复制“启用同步分析”这件事是不够的。

因为我们的系统比一般批量生成器更复杂：

1. 有 project-level constraints。
2. 有 long-task supervisor。
3. 有 repair queue。
4. 有多智能体和未来的不同 reviewer 能力。

所以我们真正该吸收的是这个中心思想：

```text
生成不是唯一主线
审核也不是附属日志
两者都应是正式任务对象
只是在不同时机决定谁阻塞谁
```

### 8.3 推荐的默认策略：普通长项目走混合审核

对一般长项目，我不建议默认：

1. 全同步重审核
2. 全异步放任式审核

最推荐的默认策略是混合审核：

1. 每章客观 gate 同步。
2. 每章轻 review 可以同步，但应非常轻。
3. 更重的语义 review 默认异步。
4. checkpoint review 同步。
5. 异步重 review 一旦判定为 `repair` 或 `pause`，由 supervisor 改写后续调度，而不是继续静默写下去。

这是对“稳定性、成本、吞吐、可用性”四者最平衡的方案。

### 8.4 参考项目的真实处理方式

如果只看理念，容易把“审核层”说得很空。结合本地 `references/` 里的几个项目，能看到几种非常具体的做法。

#### MuMuAINovel：生成主链 + 可选同步分析

`MuMuAINovel` 在批量生成里最关键的做法，不是“分析很强”，而是它明确提供了一个 `enable_analysis` 开关，并把它接进批量生成主链。

从 `references/MuMuAINovel-main/backend/app/api/chapters.py` 和 `.../models/batch_generation_task.py` 可以提炼出几个要点：

1. 批量生成任务本身有正式状态：
   `pending / running / completed / failed / cancelled`
2. 任务显式记录：
   当前章、当前重试次数、失败章节列表、最大重试数
3. 每章生成成功后，如果启用了同步分析，就立刻进入分析步骤
4. 同步分析有自己的重试逻辑
5. 一旦同步分析连续失败，整个批量任务会直接终止，而不是继续往下写

它背后的思想很明确：

1. 不是所有长线生成都必须同步重审
2. 但一旦用户选择“要同步分析保障连续性”，分析失败就必须成为硬中断条件

这对我们的启发不是“照搬 `enable_analysis` 布尔开关”，而是：

1. 审核强度必须是用户和策略可选的
2. 一旦某个审核层被声明为当前任务的硬保障，它的失败就不能再被降级成日志

#### Ai-Novel：正式任务 runtime + pause / watchdog / reconcile

`Ai-Novel` 的价值更接近我们需要的“无人值守控制面”。

从 `references/Ai-Novel-main/backend/app/services/batch_generation_service.py`、`project_task_runtime_service.py`、相关 tests 可以提炼出这些要点：

1. 长任务不是一条裸循环，而是正式的 `ProjectTask`
2. 批量生成和其子步骤有运行时视图、事件流、checkpoint、step payload
3. 有 heartbeat
4. 有 watchdog
5. 有 orphan queue reconcile
6. 有 pause / recovery，而不是只有 success / failed 两种结局

尤其值得吸收的是这几个处理：

1. 运行中任务会定期 heartbeat，超时由 watchdog 标记失败
2. 队列里丢失但数据库里仍是 queued 的任务，会被 reconcile 重新入队
3. 某个 step 失败时，不一定立刻把总任务打成 failed，可以转成 paused
4. paused 状态会保留结构化错误、checkpoint 和 step 信息，便于恢复
5. runtime view 不只展示最终状态，还展示 timeline / checkpoint / step / artifact

这说明无人值守长线生成真正可用，依赖的不是“模型够聪明”，而是：

1. 任务有正式身份
2. 审核/失败/暂停/恢复都是正式状态转换
3. 后台线程异常、队列丢失、任务孤儿化都有非 LLM 控制面接住

#### Book-OS：审核代理与写作代理分离

`book-os-main` 里虽然不是完整的长任务调度系统，但它的 `prose-reviewer` 非常说明问题。

`references/book-os-main/claude-code/agents/prose-reviewer.md` 展示的是：

1. 审核角色是明确独立的 agent
2. 审核 agent 只读，不直接改稿
3. 审核输出结构化反馈，而不是直接进入正文修改

这对我们很重要，因为它证明了另一件事：

1. 审核层不一定要一上来就变成自动修稿器
2. 完全可以先稳定成“独立 reviewer + 结构化结论 + 主链消费其结果”

这与我们前面定下的方向一致：

1. 程序不做文学裁判
2. reviewer agent 输出合同
3. repair lane 再决定是否把合同转成修订任务

### 8.5 从这些参考里真正该吸收什么

综合看，成熟项目处理无人值守长线生成时，并不是靠某一种单点技巧，而是几种机制叠加：

1. 生成任务必须是正式任务对象，而不是纯内存循环
2. 审核可以是可选强度，但一旦声明为硬保障，就必须能中断主链
3. 轻审核和重审核要分开
4. 暂停、恢复、重试、超时、孤儿任务重入队都要有正式 runtime 支撑
5. 审核结果要落成结构化事件、checkpoint、artifact，而不是临时日志

换句话说，成熟项目真正解决的不是“要不要审核”，而是：

```text
当长线生成在无人值守状态下继续推进时
谁负责观察
谁负责判定
谁负责暂停
谁负责恢复
谁负责把失败保留下来而不是静默吞掉
```

这正是我们现在应该继续补强的部分。

不应吸收的是：

1. 把所有写作风格问题都做成程序规则。
2. 按题材持续扩张专用工作流。
3. 让 probe 或测试题材反向决定核心领域模型。

## 九、对比 MuMu 的 watchdog：我们是不是已经有更全面的 supervisor 层

这个问题需要直接回答，而且要分清“设计意图”和“运行时兑现度”。

### 9.1 先把两个词讲清楚

#### watchdog

`watchdog` 更像是一个偏窄的运行时健康控制角色。

它通常负责：

1. 心跳超时检测。
2. 运行中任务僵死检测。
3. 队列孤儿任务重整。
4. worker 丢失后的状态纠偏。
5. 最基础的失败收口。

也就是说，watchdog 关注的是：

```text
任务还活着吗
它是不是卡死了
队列和状态是不是分叉了
```

它的职责很重要，但通常不天然覆盖更高层的写作调度语义。

#### supervisor

我们当前一直在追求的 `supervisor / control plane`，本来就不只是 watchdog。

它应当至少覆盖：

1. heartbeat / stale detection
2. pause / resume / stop
3. retry / recover / requeue
4. checkpoint dispatch
5. review lane / repair lane 调度
6. waiting_user / manual attention 状态
7. batch 缩放与后续计划收紧
8. 对正式任务、step、artifact、evidence 的统一消费

换句话说，supervisor 的合理定义更接近：

```text
watchdog
+ runtime scheduler
+ recovery dispatcher
+ checkpoint arbiter
+ review/repair coordinator
```

所以如果只从设计 scope 看，答案是：

**是，我们想要的 supervisor 的确比 MuMu 所说的 watchdog 更全面。**

### 9.2 但“范围更大”不等于“已经彻底实现”

这里也必须诚实。

用户之所以会怀疑“我们不是已经有更全面的监督者层了吗”，原因并不在于这个怀疑不懂架构，而在于：

**设计上的更全面，并没有自动变成运行时里的更稳定。**

也就是说，目前更准确的说法应当是：

1. 架构目标上，我们的 supervisor 明显大于 watchdog。
2. 运行成熟度上，我们还不能说这套 supervisor 已经在所有长链路里稳定兑现。

这两句话要同时成立，才是对当前现状最诚实的描述。

### 9.3 MuMu 的 watchdog 强在哪里

从参考项目吸收到的事实看，像 MuMu 或与之接近的后台长任务系统，强的不是“名字叫 watchdog”，而是它把若干基础控制能力做成了真正持续生效的后台纪律：

1. 后台任务有正式身份，不是内存循环。
2. 每个运行中任务都持续可见。
3. 出错、暂停、失败、恢复都有结构化状态。
4. watchdog/watch-runtime 会周期性收口异常，而不是等人工翻目录。
5. 一旦某个保障层被声明为硬要求，它的失败会阻断主链。

这类系统的价值不在于“它做的事情很多”，而在于：

```text
它负责的事情，真的会在运行时持续发生
```

### 9.4 我们的 supervisor 比它多了什么

如果站在理想架构上看，我们的 supervisor 应当比纯 watchdog 多出几块重要职责：

1. 不只盯任务是否活着，还盯章节交付合同是否闭合。
2. 不只盯队列状态，还盯 review / repair / checkpoint 是否应该插入。
3. 不只负责失败判定，还负责继续、提醒、返修、暂停、等待用户等调度动作。
4. 不只服务某一种长任务，而应服务普通写作、长任务、拆书、解说等共享执行骨架。
5. 不只消费队列事实，还消费 chapter delivery、review contract、constraint policy、information discipline 等结构化结果。

所以从领域建模角度看，我们的方向其实更像：

```text
watchdog 是 supervisor 的一个子职责
而不是 supervisor 的替代品
```

### 9.5 但我们现在真正缺的是什么

问题不在“概念比别人小”，而在“有些链路还没有被这层真正兜住”。

从之前反复出现的失败形态看，当前至少还有几类缺口会让用户产生“监督层并没有真正生效”的感受：

1. 某些写作轮仍可能在只读轮、空正文轮、标题轮后没有被稳定转成正式的 retry / repair / paused。
2. review lane、repair lane 和 supervisor 的耦合关系还没有完全成为主链一等公民。
3. 有些失败仍然更像“事后从 probe 里发现”，而不是“运行中被控制面拦住并收口”。
4. 某些 runtime 问题虽然被记录了，但未必立刻改变后续调度。
5. 监督层的心跳、暂停、恢复、人工注意状态，和内容链上的缺章/空章/弱交付之间，还没有在所有路径上完全打通。

这意味着当前真正的差距不是：

1. 我们缺一个 watchdog 名字。
2. 我们缺再多一条后台线程。

而是：

1. supervisor 的职责边界已经想清楚很多。
2. 但它和实际写作/审核/修复链之间的合同，还没有全部收口成稳定、统一、强制生效的运行时协议。

### 9.6 哪些东西应该保持 watchdog 化，哪些应该保持 supervisor 化

这一步如果不分开，后面实现又会混。

#### 应保持 watchdog 化的职责

这些职责应该尽量机械、客观、周期性：

1. heartbeat timeout
2. stale running detection
3. orphan queue reconcile
4. lock/ownership 过期检查
5. worker liveness
6. 最基础的 task runtime 健康修复

它们的共同特点是：

1. 不读正文。
2. 不做文学判断。
3. 不依赖题材。
4. 尽量不依赖模型。

#### 应保持 supervisor 化的职责

这些职责则是更高层的非 LLM 控制编排：

1. 什么时候插 checkpoint
2. 哪个 review 该同步、哪个该异步
3. repair 是否必须先执行
4. 下一批章节是否应缩短
5. 当前应继续、暂停、等待用户还是人工接管
6. review contract / delivery contract / information evidence 如何共同影响后续调度

它们虽然仍然不做文学裁判，但已经进入“工作流控制”而不仅是“活性检测”。

### 9.7 所以，这个问题的最终回答是什么

最准确的回答是：

1. **在架构 scope 上，是的，我们的 supervisor 比 MuMu 式 watchdog 更全面。**
2. **在运行时成熟度上，还不能因为 scope 更大，就说这层已经被完全兑现。**
3. **watchdog 该做的那部分，我们应该继续保留，而且要做得机械、稳定、无题材依赖。**
4. **supervisor 该扩展的那部分，重点不是再加概念，而是把 review、repair、checkpoint、pause/recovery 真正接成统一合同。**

如果再压缩成一句话，那就是：

```text
我们要做的不是“用更大的名词替代 watchdog”
而是把 watchdog 纳入一个真正可运行、可恢复、可调度、可审核的 supervisor control plane
```

这才是当前最值得守住的判断。

## 十、当前项目最合理的下一阶段目标

这轮之后，最合理的主线不是继续补更多表面规则，而是正式建设“表达限制智能体审核合同”。

建议目标按顺序理解为：

1. 保持现有 `profile / binding / execution policy` 不倒退。
2. 保持程序只负责客观合同与证据增强。
3. 新增正式 review contract。
4. 让单智能体与多智能体都能走 review contract。
5. 让 gate / supervisor 消费 review contract，而不是消费 preset 特判。
6. 让普通写作、长任务、拆书共用这套骨架。

但如果再往前推进一步，下一阶段目标应再明确补上一层：

7. 为“一般长项目”正式定义审核强度与调度模型：
   - 哪些审核同步
   - 哪些审核异步
   - 哪些审核只在 checkpoint 触发
   - 哪些结果足以打断主生成线程
8. 把审核从“表达限制特例”提升为共享 review lane。
9. 让 review lane 与 repair lane 成为 supervisor 的正式一等输入。

这才是“通用、稳定、优雅、可扩展”的主线。

---

## 十一、最终结论

表达限制不是单纯提示词，也不是后处理补丁，更不是 `去 AI` 专用系统。

更准确的定位应当是：

1. 用户可配置、可扩展、可绑定的文本呈现约束资产。
2. 进入共享执行约束层的运行时事实。
3. 由程序负责注入边界、合同检查、证据收集。
4. 由智能体审核合同负责主观质量判断。
5. 由 gate / supervisor 负责把审核结果转成继续、提醒、返修、暂停等动作。

如果坚持这个边界：

1. `去 AI` 不会再劫持整个架构。
2. 新表达限制可以自然接入。
3. 普通写作、长任务、拆书都能复用同一主线。
4. 后续再遇到“表达限制失效”，我们修的是审核与执行合同，而不是继续往正文后处理里塞补丁。

这才是当前阶段最值得守住的主线。
