## 1. 这份文档解决什么

这份文档只解决一个问题：

**在保留现有知识体系不动的前提下，是否应该为项目增加一条平行的 RAG 知识提取分支；如果应该，加在什么位置、采用什么架构、如何兼容 GUI / CLI / Docker / 多种宿主能力。**

这里必须先把问题说清：

我们讨论的不是“要不要用 RAG 替换现有知识体系”，也不是“要不要为了移动端去找一个全端都能跑的神奇向量库”。

真正要回答的是：

1. 现有结构化知识体系是否应保留。
2. RAG 在系统中的正式地位是什么。
3. RAG 是不是应该作为知识提取下的一条平行产物线存在。
4. GUI 首批该如何暴露。
5. 底层是否应该抽成接口，而不是绑死某个 Flutter 包、本地库或远端服务。

---

## 2. 结论先行

先给明确结论。

### 2.1 可以做，而且值得做

**可以，而且值得做。**

但前提是：

**RAG 必须是现有知识体系旁边的平行“检索证据分支”，而不是新的正式事实源。**

### 2.2 现有知识体系必须保留

你前面强调得很对：

**现有知识体系是项目的思想成果，不能因为引入 RAG 而被降格或替换。**

也就是说，下列内容继续保留为正式主线：

1. `knowledge_cards`
2. `design_elements`
3. `research_notes`
4. `reference_works`
5. 各类结构化总结、长期规则、设计边界

这些仍然是项目的信息正式事实层。

### 2.3 RAG 的正确定位

RAG 的正确定位是：

**原文证据层 / 语义召回层 / 模糊检索层**

它擅长的是：

1. 找回原文片段
2. 为智能体补证据
3. 支持拆书、同人、续写、资料检索时的模糊回忆
4. 在大文本中做语义召回

它不该负责的是：

1. 定义角色长期设定
2. 定义世界规则真相
3. 定义时间线正式结论
4. 替代知识卡、研究卡、设计元素卡

### 2.4 最终建议

最终建议可以收成一句话：

**在知识库提取 / 参考资产提取下，新增一条 `RAG 提取分支`；它生成的是可挂载的 RAG 语料资产包，项目可同时挂载结构化知识资产与 RAG 语料资产。**

---

## 3. 为什么不能用 RAG 替代现有知识体系

这一点必须钉死。

从我们现有文档看，项目已经多次明确：

1. `knowledge/` 只是可读投影，不是事实源。
2. 正式事实源应落在 `.novel_agent/information/*`。
3. GUI / CLI 应消费结构化事实与投影，不应靠目录文本充当真相。

这条基线如果因为 RAG 引入而被打破，后面一定会出问题。

### 3.1 RAG 的天然局限

RAG 召回的是“像相关”的内容，而不是“已确认的正式结论”。

它天然存在这些问题：

1. 召回片段相关，但未必是当前问题最关键的片段。
2. 同人物、同场景、同设定的近义描述容易混召回。
3. 对中文小说中的别称、绰号、暗示、隐喻，纯向量检索容易漂。
4. 对“当前有效规则”这种带强优先级的事实，RAG 没有结构化知识稳。

### 3.2 结构化知识体系擅长的事情

现有知识体系擅长：

1. 长期设定沉淀
2. 可复用知识摘要
3. 风格、结构、设计巧思的抽象总结
4. 审核、连续性、研究任务可以共享的正式事实

这类内容如果退回到 RAG 召回，会出现两个坏结果：

1. 真相不再稳定
2. 智能体很容易被召回片段带偏

### 3.3 正确分工

正确分工应是：

1. 结构化知识层回答：
   - “正式结论是什么”
   - “当前已确认规则是什么”
   - “角色/设定/风格被系统如何长期表达”
2. RAG 层回答：
   - “相关原文片段有哪些”
   - “相似设定/相关章节/可能证据在哪里”

换句话说：

**结构化知识给结论，RAG 给证据。**

## 4. RAG 应该加在什么位置

### 4.1 不该作为新的独立大系统入口

首批不建议把它做成一个厚重的“RAG 正式面板”。

原因很简单：

1. 第一阶段用户真正需要的是“提取 -> 挂载 -> 检索”，不是日常编辑 RAG。
2. RAG 本身更像资产构建结果，而不是编辑型内容。
3. 过早做大面板，会让 GUI 又多一个需要长期维护的复杂入口。

### 4.2 应该加在提取系统下面

最合适的位置是：

**知识库提取 / 参考资产提取下面，新增一个平行分支：`RAG 提取`。**

提取产物不再只有一类，而是可以存在：

1. 结构化知识提取
2. RAG 语料提取
3. 混合提取

这比单独起一个新项目类型更稳。

### 4.3 正式命名建议

这里建议尽量避免把内部术语直接全暴露给普通用户。

外部可见可以是：

1. `结构化知识`
2. `RAG 检索库`
3. `混合提取`

内部合同建议使用更中性的术语：

1. `StructuredKnowledgePackage`
2. `RagCorpusPackage`
3. `HybridReferencePackage`

## 5. GUI 分支设计是否合理

你提出的 GUI 方向是：

1. GUI 上先加一个 `RAG 知识库提取` 分支。
2. 它不需要指向正式大面板。
3. 分成两种模式：
   - 没有可用模型时
   - 有可用模型时

我的结论是：

**总体合理，但需要把“用户可见能力”与“底层正式合同”分开。**

### 5.1 GUI 首批不需要正式面板

这点是对的。

首批 GUI 完全可以只做：

1. 入口选择
2. 源选择
3. 模式选择
4. 构建状态
5. 产物摘要
6. 项目挂载

也就是说：

它更像“资产构建流程”，不是“RAG 管理中心”。

### 5.2 但必须有最小可见摘要

虽然不做大面板，仍要给用户最小可见信息：

1. 语料库名称
2. 来源
3. 语言
4. 分章数 / chunk 数
5. 构建策略
6. 是否使用模型
7. 最近更新时间
8. 是否已挂载到当前项目

这部分更适合做成资产摘要卡，而不是编辑器面板。

### 5.3 不要让系统动作依赖冷识别

这一点需要补进主分析，避免后续实现再走偏。

RAG 主线里会出现几类“系统动作”：

1. 构建 RAG 语料资产
2. 重建 / 续建 RAG 资产
3. 挂载 / 卸载 RAG 资产
4. 检索 RAG 证据
5. 把检索命中转换为 activation package

这些动作里，只有“检索问题内容”天然带有自由文本属性；
其余动作本质上都是**显式系统操作**。

因此必须明确一条补充原则：

**RAG 主线不能依赖自然语言冷识别来触发正式系统动作。**

也就是说，不应该让系统依赖下面这种脆弱链路：

1. 用户或智能体在会话里说“帮我挂载这份 RAG”
2. 宿主去猜这是不是一个系统命令
3. 再偷偷改系统状态

这样做的问题和我们刚刚讨论的“长任务启动不能靠冷识别”完全一样：

1. 易误判
2. 不可测试
3. GUI / CLI / Docker 行为难统一
4. 智能体说自己做了，和系统到底有没有真正执行，容易分叉

正确做法应当是：

1. GUI 提供显式入口
2. CLI 提供显式命令
3. 智能体通过显式 toolcall 调用正式能力

换句话说：

**文本只表达意图，正式状态变更必须走显式合同。**

### 5.4 这条原则对 RAG 的实际影响

这不是一句空口号，它会直接影响 RAG 主线的工具设计。

至少需要分清两类工具：

1. **状态/资产操作工具**
   - `list_rag_corpora`
   - `inspect_rag_corpus`
   - `mount_rag_corpus`
   - `unmount_rag_corpus`
   - `build_rag_corpus`
   - `rebuild_rag_corpus`
2. **内容证据工具**
   - `retrieve_rag_passages`
   - `build_retrieval_activation_package`

其中：

1. 资产操作工具负责正式状态变化
2. 内容证据工具负责把资料召回给智能体

二者不能混。

如果不这么做，后续很容易出现两种坏味道：

1. 检索工具顺手带着挂载/构建副作用
2. 智能体靠 prompt 猜测“现在是不是该构建/挂载”

这两种都不该进入正式主线。

### 5.5 与长任务启动讨论的关系

我们刚刚确认了一条更通用的项目级原则：

**像“启动长任务”这类正式系统动作，应由显式 GUI 动作或显式 toolcall 完成，而不是依赖冷识别。**

这条原则不只适用于长任务，也应该同步适用于 RAG 主线。

所以，RAG 任务主线应吸收这个结论：

1. 不靠自然语言冷识别触发 RAG 构建/挂载
2. 资产构建、挂载、卸载、重建都必须是显式操作
3. 智能体如需发起这些动作，必须调用正式工具
4. GUI / CLI / Docker / probe 都消费同一份工具合同与资产合同

这会让整条 RAG 主线更稳，也更符合我们一直坚持的“系统动作走合同、文本内容走会话”的设计基线。

## 6. 你提出的两种模式，是否可行

答案是：**可行。**

但要做两个修正。

---

## 6.1 无模型模式：可行，且应该先做

你说的第一条路是：

1. 无可用模型
2. 只能导入 `txt`
3. 用默认内置简单分章策略
4. 清洗干扰
5. 录入 RAG

这条路非常适合做第一阶段。

### 为什么它适合作为第一阶段

因为它具备几个优点：

1. 不依赖模型
2. 不依赖联网
3. 成本低
4. 易测试
5. CLI / Docker / GUI 都好复用
6. 非常适合先验证“RAG 平行分支”的架构本身

### 它的现实限制

也要明确承认它的限制：

1. 只能处理比较干净的纯文本
2. 分章质量不会特别高
3. 干扰清理要谨慎
4. 这是“可检索语料构建”，不是“高质量语义理解”

### 这里最重要的修正

GUI 第一阶段可以只暴露 `txt`，这完全合理。

但底层不要把规则写死成：

```text
无模型 == 只能 txt
```

更正确的表达应是：

```text
第一阶段 GUI 无模型模式只开放 txt；
底层标准化接口保留未来支持 md / 其他纯文本来源的空间。
```

这是非常重要的差别。

也就是说：

**产品可先保守，架构不能先写死。**

---

## 6.2 有模型模式：可行，但不应叫“模型自己拆书就完了”

你说的第二条路是：

1. 有可用模型
2. 可以导入 `epub / 文件夹 / md` 等
3. 模型智能拆书
4. 拆完再录入 RAG

这条路同样成立，但必须更谨慎。

### 为什么它成立

因为复杂资料的问题，不在于“能不能读取字节”，而在于：

1. 哪部分是正文
2. 哪部分是前言/目录/版权/注释/尾页
3. 怎样判断章/卷/番外/设定集边界
4. 文件夹内多个文件如何组成同一作品

这些地方，模型确实可以提供价值。

### 为什么不能直接写成“智能拆书”

因为“智能拆书”过于黑盒，后面一定难以验收。

更准确的定位应该是：

**模型辅助文稿标准化 / 模型辅助分章 / 模型辅助去噪**

然后再进入统一的 RAG 入库链。

### 这里还需要再收一条：优先复用我们已经实现的智能拆书接入

这次要把一个新结论正式并进来：

**RAG 的模型辅助前段，不应再平行长出第二套“智能拆书”实现，而应优先复用我们已经实现的拆书智能导入接入。**

也就是说：

1. RAG 模型辅助模式仍然存在
2. 但它的“复杂格式标准化 / 正文识别 / 分章 / 去噪”前段
3. 优先接到现有的智能拆书接入链
4. 然后把产出的标准化结果喂给 RAG ingestion runtime

这样做的好处很直接：

1. 不重复造轮子
2. `txt / md / epub / folder` 的复杂输入处理逻辑不再分叉
3. 后续修乱码、识别章节、清广告、清版权页时，只修一处
4. GUI、拆书项目、RAG 提取都能共享同一套“模型辅助正文标准化”能力

### 但要注意：这不等于把 RAG 绑死到拆书项目语义

这里必须分辨两个层面：

1. **能力复用层**
   - 复用现有智能拆书接入
   - 复用其临时工作区、模型执行、清洗产物约定
2. **产品语义层**
   - RAG 仍然是 RAG 提取
   - 不是“先创建一个拆书项目，再顺手做 RAG”

所以正确关系不是：

```text
RAG = 拆书项目
```

而是：

```text
RAG 模型辅助标准化
    -> 复用智能拆书接入能力
    -> 输出标准化正文
    -> 进入 RAG ingestion
```

### 为什么这条边界很重要

如果不这样处理，后面很容易出现两种坏实现：

1. RAG 自己又做一套“智能拆书”
2. 或者反过来，把 RAG 提取粗暴绑定成“先经过拆书项目”

前者会造成逻辑重复、修复分叉；
后者会把产品语义搅乱，让用户和系统都不清楚自己在做“拆书”还是“RAG 提取”。

所以更优的演化是：

1. 智能拆书接入下沉为**可复用的模型辅助标准化能力**
2. 拆书项目消费它
3. RAG 模型辅助提取消费它
4. 以后普通项目导入如有需要，也可以消费它

### 它仍然必须是可选的，但“可选”的含义要说准

这一点也必须钉住：

**RAG 前处理必须允许用户在“纯离线简单识别”和“模型辅助智能拆书”之间选择。**

因此：

1. 纯离线简单识别仍然走基础规则链
2. 模型辅助智能拆书才复用现有智能拆书接入
3. 即使配置了模型，也不代表必须使用模型辅助智能拆书
4. 用户在 RAG 提取时应能明确选择当前使用哪种前处理模式

这是为了保持：

1. 成本可控
2. 行为可预期
3. CLI / Docker / 无模型环境仍可工作
4. “基础可用 + 增强可选”的产品分层

换成更工程化的表达，RAG 主线应是：

```text
RAG source preprocessing mode
  - offline_basic
      规则读取 / 规则分章 / 基础去噪
  - smart_deconstruction_assisted
      复用现有智能拆书接入 / 模型辅助识别正文与章节

两种前处理模式
  -> 统一标准化产物
  -> 统一 RAG ingestion
  -> 统一 mount / retrieve / activation
```

所以这里不能做成两套 RAG：

1. 不能有一套“离线 RAG ingestion”
2. 再有一套“智能拆书 RAG ingestion”

它们只能是同一条 ingestion 主链前面的两个可选前处理策略。

### 这条路的主要风险

1. 模型误拆章节
2. 模型把干扰内容混入正文
3. 模型成本更高
4. 稳定性不如规则链
5. 如果没有正式输出合同，后续无法重跑、修复、比较

### 所以必须加的硬约束

模型不能只返回一坨整理后的文本。

至少应返回：

1. 识别出的正文单元
2. 章节边界
3. 章节标题
4. 被排除的干扰块
5. 不确定块

也就是说：

**模型输出必须合同化。**

---

## 7. 这两条路的更优抽象

你现在的分法，在产品层是合理的，但在架构层最好不要直接叫：

1. 无模型模式
2. 有模型模式

更优的架构抽象应是：

### 7.1 源标准化层

负责把不同来源变成统一文稿单元。

例如：

1. txt
2. md
3. epub
4. 目录型多文件来源

### 7.2 分段策略层

负责决定如何得到“章节 / 段 / 文稿片段”。

例如：

1. 规则分章
2. 模型分章
3. 混合分章

### 7.3 chunk 构建层

负责把文稿变成 RAG 用的 chunk。

例如：

1. 按章切
2. 按段切
3. overlap 策略
4. 元数据注入

### 7.4 检索库构建层

负责 embedding、索引、元数据入库、版本记录。

这样一来，产品层仍可以显示成两条模式：

1. 基础提取
2. 模型辅助提取

但底层不会被绑死。

---

## 8. RAG 的底层路线应该怎么选

前面已经讨论过关键问题：

**多端兼容不等于所有端都必须纯 Dart 内建同一种 RAG 实现。**

这点很重要。

### 8.1 Flutter GUI 不是唯一宿主

项目明确是多宿主：

1. Flutter GUI
2. Dart CLI
3. 后续 Docker

所以 RAG 能力绝对不能直接绑死在：

1. 某个 Flutter-only 包
2. 某个移动端本地向量库
3. 某个纯 Dart 的受限实现

### 8.2 正确路线：抽象成接口族

RAG 不该先被设计成“一个库”，而应被设计成：

**一组正式的 Retrieval / RAG Provider 接口。**

共享的是：

1. 检索语义
2. 挂载语义
3. 结果合同
4. 生命周期

不共享的是：

1. embedding 怎么生成
2. 向量索引怎么实现
3. 是本地跑还是远端跑
4. 是 Flutter 本地库、CLI sidecar 还是 Docker 服务

### 8.3 为什么依赖外部能力是可行的

这一步完全可行，而且应该是正式设计。

尤其是：

1. CLI 不需要为了移动端纯 Dart 约束而自废武功。
2. Docker 更适合外置检索服务。
3. 桌面端也完全可以接 sidecar / native engine / 远端 embedding。

所以“依赖附加的外部接口”不是临时妥协，而是健康架构。

---

## 9. 正式架构建议

### 9.1 三层知识/检索结构

最终结构建议如下：

#### 第一层：结构化事实层

继续使用现有体系：

1. `.novel_agent/information/knowledge_cards/*`
2. `.novel_agent/information/design_elements/*`
3. `.novel_agent/information/research_notes/*`
4. `.novel_agent/information/reference_works/*`

这是正式事实源。

#### 第二层：RAG 检索证据层

新增：

1. `RagCorpusPackage`
2. `RagChunk`
3. `RagIndexHandle`
4. `RagMountBinding`

这是检索证据层。

#### 第三层：可读投影层

继续保留：

1. `knowledge/*.md`
2. `research/*.md`
3. 未来可选的 RAG 构建摘要投影

这是给用户看的，不是事实源。

### 9.2 资产挂载方式

项目应允许挂载多种参考资产，而不是“知识库二选一”。

例如同一项目可同时挂载：

1. 哈利波特结构化知识包
2. 哈利波特 RAG 语料包
3. 中国古代官制研究包
4. 科技发展参考 RAG 包

也就是说：

**RAG 不是替换挂载，而是新增可并存挂载。**

### 9.3 工具层必须分开

智能体工具层不能做成一个模糊的“查知识库”。

至少应分开：

1. `query_knowledge_cards`
2. `query_design_elements`
3. `query_reference_works`
4. `retrieve_rag_passages`

否则结构化结论与召回证据会被混在一起。

## 10. 底层接口建议

这一节是最关键的工程落点。

### 10.1 不要先问“选哪个库”

应该先问：

**系统需要哪些正式能力接口。**

建议至少定义这些接口族。

### 10.2 输入与提取链接口

#### `RagSourceNormalizer`

职责：

1. 接收 txt / md / epub / folder 等来源
2. 输出统一文稿单元
3. 记录源路径、语言、格式、来源类型

#### `RagSegmentationStrategy`

职责：

1. 规则分章
2. 模型分章
3. 混合分章

#### `RagChunkBuilder`

职责：

1. 章节级切块
2. 段级切块
3. overlap 与 chunk metadata 构建

### 10.3 检索与索引接口

#### `EmbeddingProviderPort`

职责：

1. 生成 embedding
2. 声明是否本地/远端
3. 声明支持的语言/维度/批处理能力

#### `RetrievalIndexPort`

职责：

1. 建库
2. 增量更新
3. 删除
4. 重建

#### `RetrievalSearchPort`

职责：

1. 查询
2. topK
3. source scope 过滤
4. project mount 过滤
5. rerank（如后续支持）

#### `RetrievalHealthPort`

职责：

1. 能力探测
2. backend 健康状态
3. 当前宿主是否支持该 provider

### 10.4 元数据基座

这里建议继续沿用 SQLite 作为跨宿主元数据基座。

SQLite 应保存：

1. corpus id
2. source id
3. chunk id
4. chapter / range / title
5. language
6. version
7. mount binding
8. backend handle

注意：

**SQLite 管元数据与映射，不强行等于向量索引本体。**

向量索引后端可以是：

1. 本地库
2. sidecar
3. 远端服务
4. Docker 子服务

## 11. 宿主兼容路线

### 11.1 Flutter GUI

首批最合理：

1. 支持远端 embedding + 本地 metadata
2. 可选支持轻量本地 RAG provider
3. GUI 只负责资产提取入口、摘要、挂载、最小状态展示

### 11.2 CLI

CLI 不需要纯 Dart 限制。

它更适合：

1. 本地 native engine
2. sidecar 检索服务
3. 远端 embedding / 远端 retrieval provider

### 11.3 Docker

Docker 最适合：

1. embedding service
2. retrieval service
3. 独立索引构建服务

这意味着 Docker 完全可以不和 Flutter 走同一底层实现，只共享合同。

### 11.4 核心原则

**共享的是合同，不共享的是底层引擎。**

这就是多宿主下最合理的路线。

## 12. 首发策略建议

### 12.1 第一阶段：先做基础 RAG 提取

建议第一阶段只做：

1. Flutter 本地 provider

## 13. 不该做的事

这部分同样重要。

### 13.1 不要做成替换现有知识体系

RAG 不是新事实源。

### 13.2 不要先做大面板

第一阶段不需要完整 RAG 浏览器、编辑器、管理台。

### 13.3 不要把无模型模式写死成永远只支持 txt

首批 GUI 可以只开 txt，底层接口不能被写死。

### 13.4 不要把“模型智能拆书”做成黑盒一步到位

必须输出正式合同，而不是只回一坨整理文本。

### 13.5 不要把向量后端写死进 Flutter 包

否则 CLI / Docker 会被反向绑架。

### 13.6 不要把 RAG 工具和结构化知识工具混成一个万能工具

证据召回与结构化结论必须分开。

### 13.7 不要让 GUI 成为 RAG 真相层

GUI 只消费资产摘要、挂载状态、提取状态，不解释底层正式合同。

## 14. 最终结论

这轮讨论后的最终结论很清楚：

### 14.1 总结判断

1. 现有知识体系必须保留，而且继续作为正式结构化事实层。
2. RAG 值得引入，但只能作为平行的检索证据分支。
3. 最合适的加入位置，是知识库提取 / 参考资产提取下面的新分支，而不是新建一个独立重系统入口。
4. GUI 第一阶段不需要正式大面板，只需要提取入口、摘要和挂载能力。
5. “无模型基础模式 + 有模型辅助模式”这个产品思路是可行的。
6. 但在底层，必须把它收成：
   - 源标准化
   - 分段策略
   - chunk 构建
   - 检索库构建
7. RAG 底层不应绑死为纯 Dart 或某个 Flutter 包，而应先抽成接口族，再按 GUI / CLI / Docker 各自接不同实现。

### 14.2 一句话结论

**最优方案不是“把知识库改成 RAG”，而是“保留现有结构化知识体系，在提取系统下新增一条平行的 RAG 语料资产分支，并通过统一 Retrieval 接口为不同宿主接入不同后端实现”。**

这条路线既保住了你们已有的思想成果，也为后续多宿主、多后端、多模式提取留下了足够稳的演化空间。

### 14.3 实施收口备注

这份分析对应的主线已经在后续 session 中落地完成，当前应按已实现基线理解：

1. RAG 已经是项目中的正式平行证据分支，不再只是架构提议。
2. `RagCorpusPackage`、`RetrievalMountBinding`、`RetrievalQuery`、`RetrievalHit`、`RetrievalActivationPackage` 等正式合同已经用于实现和测试。
3. 基础 `txt` 模式、挂载、检索、activation package、provider capability 与 GUI / CLI 消费边界都已经按合同收口。
4. 模型辅助能力仍保留为扩展位，但不再需要重新定义主线边界。
