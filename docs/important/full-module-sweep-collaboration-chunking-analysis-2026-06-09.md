# 全模块巡检、协作分块与逐块收口分析 2026-06-09

## 目的

这份文档解决的不是某一条专题主线，而是一个更上层的问题：

```text
当项目已经积累了多条实现主线、分析文档、探针与半收口模块时，
如何做一次真正全方位的模块巡检，
把残留问题一个一个抹除，
同时把模块切成适合协作、适合独立充实、独立测试、独立修改、独立交付的粒度。
```

这里的“分块”不是把代码随便拆开，也不是为了多线程开发而机械分目录。

我们真正要得到的是：

1. 每一块都有清楚职责。
2. 每一块都有稳定输入输出。
3. 每一块都能单独验收。
4. 每一块都能被不同会话或不同智能体安全接力。
5. 每一块失败时，影响面可控、回滚边界清楚。

这里尤其要强调一件事：

```text
分块的第一目标不是“看起来整齐”，
而是防止协作时出现“我动你的、你动我的”，
最后因为同步失配让同一逻辑长出两个实现。
```

同时，这份文档还要解决另一个同样重要、但更容易被忽略的问题：

```text
项目推进得很快时，
很多模块往往不是“完全错误”，
而是“做到了七八成，剩下一截没有收口”。
```

这类问题最危险，因为它们在日常使用里常常“看起来能跑”，但真实状态可能是：

1. 功能只覆盖了主路径，分支没补全。
2. 合同已经定义了，但消费者仍在吃旧字段。
3. 核心逻辑已经迁移，UI / probe / fallback 还残留旧判断。
4. 行为大体正确，但失败处理、恢复路径、边界条件没收住。
5. 多个模块都“顺手补了一点”，最后没人能明确哪条才是主链。

所以这轮分析必须额外把下面这件事钉死：

```text
全模块检查不是为了写一份巡检报告，
而是为了把现有模块的残留问题一个一个抹除，
直到每一块都达到“可被协作消费”的程度。
```

---

## 一、为什么现在必须做这件事

项目走到当前阶段，已经有几个非常明显的现实：

1. 不是没有架构，而是架构已经很多。
2. 不是没有功能，而是功能已经跨越：
   - 普通写作
   - 长任务
   - 参考提取
   - 信息基底
   - 连续性
   - 审稿与修复
   - 智能体组 / 技能组
   - GUI / CLI
3. 不是没有测试，而是测试、probe、真实验证入口已经很多。

这时候再继续“想到哪修到哪”，会出现三个坏结果：

1. 局部问题被修了，但共享主链继续弯。
2. 会话之间难以协作，因为边界不清楚。
3. 单个目标模式很容易在上下文里糊成一团，既扫不全，也修不稳。

而且比这些更危险的是：

1. 同一个问题被两个会话分别修。
2. 两边都不知道对方已经补了哪一层。
3. 最后合并时不是冲突在文本上，而是冲突在架构上。
4. 表面看都“能跑”，实际上项目里同时存在两套语义近似、落点不同的实现。

所以现在需要的不是再补一轮零散文档，而是：

```text
先做全模块巡检视角，
再给项目建立“协作就绪分块”的长期约束，
之后所有治理、补全、回归、扩展都按这个粒度推进。
```

## 二、这里的“协作分块”到底是什么意思

## 2.1 不是按目录名机械切

一个块，不等于一个目录，也不等于一个页面，更不等于一个 service。

例如：

1. `long_task_station/` 目录不是天然一个块。
2. `reference_extraction/` 目录也不一定只对应一个块。
3. 一个块可能跨 `core + adapters + app`，但仍然服务同一稳定职责。

所以分块标准不是“文件放一起”，而是：

1. 是否服务同一能力闭环。
2. 是否共享同一运行时真相。
3. 是否能独立验收。
4. 是否能被单独修改而不把整个系统拖下水。

## 2.2 一个合格的协作块至少要满足六件事

### 1. 目标单一

这一块必须回答：

```text
它到底解决哪一类问题？
```

如果一个块同时在解决：

1. UI 交互
2. 持久化
3. 业务决策
4. 探针验证

那它大概率已经不是一个合格块。

### 2. 公开合同明确

每个块都应有稳定的：

1. 输入模型
2. 输出模型
3. 状态变化口径
4. 错误/失败分类

没有公开合同的块，后续协作只能靠“读心术”。

### 3. 持久化边界明确

要清楚：

1. 这一块的事实源是什么
2. 哪些只是投影
3. 哪些只是调试/缓存/兼容层

否则后面会不停出现：

1. UI 改了投影，结果以为改了真相
2. probe 看的是缓存，却以为验证了主链

### 4. 测试入口独立

每一块都要能被单独验证：

1. focused unit / contract test
2. integration / adapter test
3. 必要时 real probe

如果一个块只能靠“顺手跑完整应用看看”，那它还不够协作友好。

### 5. 交付边界独立

一个块做完以后，应当可以明确说：

1. 完成了什么
2. 没完成什么
3. 下一块怎么接

这决定了它是否适合目标模式或多会话接力。

### 6. 影响面可估算

要能回答：

1. 改这一块会波及哪些模块
2. 不会波及哪些模块

如果影响面不可估算，这一块就太散了。

## 2.3 一个合格协作块还必须满足“防分叉三条件”

这三条是比“好维护”更硬的要求。

### 条件 A：同一块同一时间只能有一个主实现出口

也就是说：

1. 一个能力块必须有当前唯一正式主链。
2. probe、fallback、兼容层、临时桥不能偷偷再长出第二条主链。
3. 如果要迁移主链，必须先显式声明“旧出口降级为兼容层”，而不是两条并存长期漂着。

### 条件 B：同一块在同一阶段只能有一个主负责会话

协作时不能默认：

1. A 会话修这块的一半
2. B 会话顺手也改同一块的另一半
3. 最后靠合并碰碰运气

更合理的做法是：

1. 一个块在某一轮有主负责会话
2. 其他会话只能消费它稳定暴露的合同
3. 若必须跨块协作，先冻结共享合同，再串行落实现

### 条件 C：跨块问题优先抽共享合同，不允许双边各补一份

很多双实现问题都来自这种场景：

1. A 发现缺一个字段，于是在 app 层补一份
2. B 发现同一个缺口，于是在 adapter 层补一份
3. 后来两边都自洽，但语义不同

正确做法是：

1. 先确认这是不是共享缺口
2. 如果是，先抽 core / contract
3. 再决定哪个块主落地、哪个块消费

## 三、协作真正要防的不是冲突文件，而是“双实现”

文本冲突通常还能被看到。

真正麻烦的是：

1. 没有文本冲突
2. 但是两边都各自补了一套逻辑
3. 还都能过一部分测试

这时系统会进入最坏状态：

1. 人不知道该信谁
2. 测试不能准确表明真相
3. 后续再修的人更不知道要删哪套

最常见的五种来源是：

1. fallback 长成主链
2. probe 长成业务中心
3. viewmodel / widget 私下补业务
4. adapter 与 core 各补一份语义
5. 迁移未完成，旧链和新链并存过久

因此下面的分块，首先是为了避免这些双实现风险。

## 四、项目当前最合适的分块方式

下面这套分块，不是最终永恒真理，但它很适合作为当前阶段的协作与治理单位。

## 4.1 控制面块

负责：

1. 连续任务族
2. watchdog / supervisor / dispatcher / worker
3. pause / resume / retry / recover
4. failure taxonomy

不负责：

1. 文学内容判断
2. 具体 UI 呈现
3. 特定题材逻辑

验收方式：

1. contract tests
2. runtime tests
3. production-truth regression

## 4.2 写作执行块

负责：

1. 普通写作
2. 长任务写作
3. 章节交付
4. 字数/表达限制执行桥

不负责：

1. 提取源材料
2. 设置页面
3. 智能体生态编辑

验收方式：

1. chapter delivery focused tests
2. 长短链写作 probe

## 4.3 审稿与修复块

负责：

1. review contract
2. repair contract
3. disposition
4. 审稿执行者选择

不负责：

1. 控制面保活
2. UI 面板布局

## 4.4 连续性与状态块

负责：

1. narrative claims
2. ledger
3. profile
4. semantic review
5. conflict cluster
6. canon decision

不负责：

1. provider 调用
2. 文件选择 UI

## 4.5 参考提取块

负责：

1. source bootstrap
2. ingestion budget
3. batch plan
4. coverage / progress
5. reference substrate
6. project attachment
7. sqlite-first mount

不负责：

1. 普通写作线程默认行为
2. 题材定制逻辑

## 4.6 信息基底与激活块

负责：

1. knowledge
2. design
3. research
4. reference work
5. activation bridge
6. projection

不负责：

1. 主写作调度
2. 页面布局

## 4.7 智能体生态块

负责：

1. agent
2. agent group
3. skill
4. skill group
5. loadout
6. capability family
7. tool exposure policy

不负责：

1. 具体章节写作内容
2. 参考提取 persistence 细节

## 4.8 宿主壳与工作台块

负责：

1. workbench 交互
2. long task station
3. 资产浏览
4. 设置入口
5. 主路径 UX

不负责：

1. 新的业务规则
2. 直接解释 provider 协议

## 4.9 CLI / 自动化块

负责：

1. 最小命令入口
2. 输出摘要
3. 自动化消费稳定合同

不负责：

1. 重新实现 GUI 逻辑
2. 自建第二套业务中心

## 4.10 probe / regression 块

负责：

1. focused verification
2. regression suite
3. real probe

不负责：

1. 定义 production 真相
2. 常驻业务逻辑

## 五、全模块巡检时应怎样工作

## 5.1 先建立模块审计台账，不要直接下手改

巡检第一步不应是“先挑最顺眼的 bug 修”，而应先建立台账。

每个块至少记下：

1. 模块名称
2. 当前职责
3. 事实源
4. 主要入口
5. 当前残留问题
6. 问题严重度
7. 是否影响共享主链
8. 是否适合单独交付
9. 是否需要先拆再修

除此之外，还应再补三列，否则很容易把“看起来能跑”的模块误判为已完成：

10. 当前完成度判断依据
11. 尚未闭环的缺口
12. 本块是否已经达到“可安全协作接手”

这里第 10 项尤其重要。不能写“应该差不多好了”，而要写：

1. 已通过哪些真实入口验证
2. 还有哪些入口没验证
3. 验证的是主链还是旁路
4. 验证覆盖的是 happy path 还是包含失败恢复

## 5.2 优先级排序规则

按下面顺序：

1. 阻断真实可用性的主链问题
2. 会污染多个模块的共享问题
3. 会让后续协作失控的耦合问题
4. 局部 UX 或投影问题
5. 非核心清洁项

这里还应补一条现实规则：

```text
不要优先挑“最好修”的问题，
而要优先挑“放着不管会继续制造伪完成感”的问题。
```

因为真正拖慢协作的，往往不是显眼报错，而是：

1. 模块看似完成，实际缺一段关键恢复路径
2. 文档看似齐，实际合同消费仍有旧链
3. probe 看似通过，实际主链没有被真正覆盖

## 5.3 处理顺序必须是“先拆清，再修正”

如果某模块当前明显是混块状态：

1. 先抽合同
2. 再拆职责
3. 最后修 bug

不能继续在混块里直接堆补丁。

## 5.4 巡检时必须额外登记“重复实现风险”

每个块除了普通问题，还要额外查四项：

1. 当前有没有两个以上入口在做近似同一逻辑
2. 当前有没有 fallback / probe / viewmodel 在复制主链判断
3. 当前有没有新旧链并存但未明确主次
4. 当前有没有不同会话很容易同时去改的共享地带

如果这四项不查，后续协作依然会不断长歪。

## 5.5 巡检时还必须登记“残留问题类型”

不是所有残留问题都叫 bug。

为了后续能稳定清扫，每个块的问题至少要落到下面几类之一：

1. `missing_path`
   - 主功能已经存在，但某条必要分支根本没接。
2. `incomplete_contract_consumption`
   - 合同层已更新，但消费者没有完全切换。
3. `shadow_logic`
   - 主链之外还有旧逻辑、投影逻辑、补丁逻辑在偷偷参与决策。
4. `state_truth_blur`
   - 事实源、缓存、投影、调试产物边界不清。
5. `recovery_gap`
   - 正常流程可跑，但失败、暂停、恢复、重试没有闭环。
6. `ux_surface_mismatch`
   - 核心逻辑正确，但 GUI / CLI / 文案把系统状态表达错了。
7. `test_coverage_gap`
   - 功能改了，但没有对应 focused 验证或真实入口验证。
8. `ownership_blur`
   - 谁是主出口、谁是兼容层、谁负责这一块不清楚。

这样分类的目的，不是加管理术语，而是避免后面继续出现：

1. 把合同消费问题当成 UI bug 修
2. 把恢复缺口当成稳定性“偶发”
3. 把双实现风险当成只是代码重复

## 5.6 什么才算“检查过了”

以后不能再出现“我看过了，大致没问题”这种模糊结论。

一个块只有同时满足下面几条，才算真的检查过：

1. 主实现出口已经明确。
2. 事实源已经明确。
3. 外围层没有再偷偷复制主链判断。
4. 真实使用入口至少跑过一遍。
5. 失败或边界路径至少抽一条验证过。
6. 当前未收口项已经被记录，而不是留在记忆里。

也就是说，“看代码觉得合理”只能算第一步，不能算验收。

## 5.7 什么才算“残留问题被抹除”

一个问题被真正抹除，不是指把报错压下去，而是至少满足：

1. 原问题的根因已经被定位在正确能力块。
2. 修复发生在主实现出口，而不是旁路。
3. 与它同类的重复入口被降级、删除或切回消费合同。
4. 对应验证已经补上。
5. 文档或台账已更新，后续接手的人不会再重复补同一处。

如果只是：

1. 在 viewmodel 补一层转换
2. 在 probe 里特殊判过
3. 在 fallback 里再兜一下

那不叫抹除问题，只叫隐藏问题。

## 5.8 全模块巡检的最终交付不应只是“问题列表”

这轮工作的交付至少应包含四类产物：

1. 模块审计台账
2. 重复实现风险台账
3. 每个已收口块的主实现出口说明
4. 每个未收口块的下一步精确入口

否则就算扫描得再广，也仍然很容易在下一会话里重新散掉。

## 六、目标模式为什么单靠一个大目标往往做不好

这次用户的判断是对的。

如果只给目标模式一句：

```text
把项目所有问题都修好
```

大概率会出现：

1. 扫描不全
2. 抓不到共享主链
3. 容易被局部显眼问题吸走
4. 改动分散、难验收
5. 会话结束后无法稳定交接

所以目标模式更适合消费的是：

1. 分块视图
2. 明确顺序
3. 每轮只收口一个块
4. 每块有独立验收

也就是说：

```text
目标模式不是不够强，
而是需要“协作就绪分块”来降低任务熵。
```

## 七、这套分块对协作模式意味着什么

如果后续进入协作模式，这套分块应该直接成为协作单位。

每个协作单位都应具备：

1. 负责的块
2. 不可越权的边界
3. 交付产物
4. 必测项
5. 回交接口

例如：

1. 一个会话修控制面块
2. 一个会话修参考提取块
3. 一个会话修工作台与 GUI 消费块

只要合同稳定，这三者就能并行或接力。

反过来，如果块划不清：

1. 大家都在改同一个万能 service
2. 同一个 bug 被不同会话从不同层补
3. 最后合并时更容易长歪

## 八、对项目级长期约束的实际要求

这部分必须进入 `agent.md`，否则后续每次加功能还要再手动拆一遍。

应该新增的长期约束至少包括：

1. 新功能默认先归属到某个已有协作块；若不适配，先定义新块再实现。
2. 一个实现块必须同时声明：
   - 目标职责
   - 事实源
   - 公开合同
   - 验证入口
3. 不允许跨多个块同时半实现，除非先把共享合同落稳。
4. 若一个功能同时触碰 core / adapters / app / probe，必须按块分层推进，而不是在一个会话里散改。
5. 如果一个块已经重到难以单独测试、单独交付、单独回滚，就说明必须拆块。
6. 新增 probe、bridge、fallback、viewmodel 不得变成新的业务中心；它们只能消费对应块的稳定合同。
7. 同一能力块同一时间只能存在一个正式主实现出口；若出现新旧并存，必须显式标明主链、兼容层与移除计划。
8. 同一能力块同一阶段只能有一个主负责会话；其他会话不得顺手补第二套实现。
9. 跨块共享缺口必须先抽合同，再串行落地；禁止两边各补一份“能跑就行”的实现。

---

## 九、推荐的近期治理顺序

如果按当前项目现状，我更推荐下面的治理顺序：

1. 先完成一次全模块审计台账与重复实现风险台账
2. 连续任务控制面块
3. 参考提取块
4. 信息基底与激活块
5. 连续性与状态块
6. 审稿与修复块
7. 智能体生态块
8. 工作台 / 长任务站 / 资产 GUI 消费块
9. CLI / 自动化块
10. probe / regression / release 清洁块

原因很简单：

1. 没有第一步，后面很容易重复修同一问题。
2. 中间几块决定主链是否真实可用。
3. 后面几块才是产品消费和协作扩展。

---

## 十、最终结论

这轮最重要的，不是再多出一份“万能总目标”，而是把项目推进方式收束成下面这条原则：

```text
先按协作就绪块理解整个项目，
再按块巡检、按块收口、按块测试、按块交付，
并且始终防止同一逻辑在协作中长出双实现，
而不是继续在全项目范围无边界地同步修改。
```

只有这样，后面的目标模式、协作模式、多会话接力、长期维护，才会越来越顺，而不是越做越难合并。
