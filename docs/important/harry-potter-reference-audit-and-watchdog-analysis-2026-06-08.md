# 哈利波特参考资产审计与 watchdog / supervisor 架构分析 2026-06-08

## 目的

本文收口三件事：

1. 知识提取是否应保留来源与证据。
2. 现有哈利波特参考资产是否真的能过“常用问题”和“刁钻问题”两类验收。
3. 长任务稳定性是否需要补一层类似 watchdog 的能力，以及它与现有 supervisor 的边界应如何划分。

本文不是任务顺序文档，而是给后续实现与修正提供判断基线。

---

## 一、先给结论

### 1.1 来源必须保留，而且不应只保留“有这个文件”

应保留，而且要保留到足够可回溯的粒度。

至少应稳定保留：

1. 原始来源对象：
   - 源文本
   - 图片
   - 导入文档
   - 网络页面
   - 其他结构化资料
2. 来源身份：
   - 来源类型
   - 唯一标识
   - 标题或标签
   - 语言
   - 采集时间或版本
3. 证据锚点：
   - 章节/片段/页码/段落
   - 文本范围或结构化 span
   - 提取时使用的切片摘要
4. 转换链：
   - 这是 seed 抽取、agent 提案、review 定稿，还是后续合并产物
5. 使用边界：
   - 是否只允许参考
   - 是否允许衍生
   - 是否允许直接引用

用户这次提出“来源是智能体找不到细节时的补救”，这个判断是对的，而且比单纯的审计理由更贴近产品现实。

### 1.2 现有哈利波特参考资产不能算合格的“第一卷知识库”

不能。

它在结构上是有效的，甚至有明显进步，但在内容覆盖上仍然不够：

1. 常用问题能答一部分。
2. 刁钻问题很快失真。
3. 更关键的是，它不是“偶尔漏了几点”，而是整条提取链对第一卷中后段核心信息覆盖不足。

### 1.3 当前问题不是“历史产物脏了”，而是提取链完成标准过宽

我重新补跑了一次真实提取，结果仍然如此。

所以当前问题不是旧产物偶发损坏，而是：

1. 提取链会正式 PASS。
2. 但 PASS 时仍可能只产出“开篇概况级”资产。
3. 也就是说，当前 PASS 更接近“结构跑通”，还不是“知识库可用”。

### 1.4 watchdog 可以要，但不能让它变成第二个 supervisor

最合理的方向不是把现有 supervisor 打散重做，也不是让 watchdog 读正文、懂语义、做文学判断。

更合理的分层是：

1. `watchdog`：最小化、确定性、只做活性与前进性监察。
2. `supervisor`：消费结构化运行结果，负责恢复、暂停、人工注意、重试等调度策略。
3. `scheduler / dispatcher`：实际推进任务。

也就是说：

```text
watchdog 与 supervisor 应共存
watchdog 不能替代 supervisor
supervisor 也不该降级成纯 heartbeat 检查器
```

## 二、现有来源链路的现实状态

### 2.1 当前实现已经不是“没有来源”

仓库现状表明，来源与证据不是空概念，已有正式建模：

1. `source_refs`
2. `evidence_refs`
3. `source_url_or_ref`

相关实现锚点至少包括：

1. `packages/novel_agent_core/lib/src/reference_substrate/reference_package_models.dart`
2. `packages/novel_agent_core/lib/src/reference_substrate/reference_source_document_extraction_service.dart`
3. `packages/novel_agent_core/lib/src/reference_substrate/reference_entry_projection_mapper_service.dart`
4. `packages/novel_agent_core/lib/src/reference_extraction/reference_extraction_proposal_models.dart`
5. `packages/novel_agent_core/lib/src/reference_extraction/reference_extraction_package_merge_service.dart`
6. `packages/novel_agent_adapters/lib/src/workflow/project_information_activation_bridge_service.dart`

所以“是否保留来源”这个问题，已经可以从方向讨论进入质量讨论。

### 2.2 现在的问题不在于有没有来源，而在于来源质量还不够漂亮

这次抽检里已经暴露出两个来源层面的真实问题：

1. 有来源，但存在重复 source ref。
2. 有 evidence span，但 entry 级 summary 与 source boundary 还不够对齐。

例如：

1. `哈利·波特的身世与初入魔法世界` 这个条目有明确的章节级 evidence span。
2. 这很好，说明“回到原文定位”已经不是做不到。
3. 但它同时挂了多条完全相同的 `source_ref`，这会让来源信息变臃肿，降低可读性。

所以结论不是“来源要不要留”，而是：

```text
来源必须保留
但要去重、分层、可折叠、可回跳
```

## 四、历史包审计：`hp_full_series_bulk_v1`

### 4.1 它最突出的毛病不是“少”，而是“边界混杂”

历史包表面看条目很多：

1. 总条目数 495
2. `knowledge_fact` 209
3. `design_element` 118
4. `reference_work_boundary` 93
5. `style_technique` 75

但真正审下来，问题非常明显：

1. 条目里大量强调“仅覆盖前五章”。
2. 同时又混入整份大文本的高频专名统计。
3. 于是出现一种不自然状态：
   - 正文边界像是“前五章样本”
   - 角色频次却像是“整书甚至整合集”

这会直接导致知识库语义发虚：

1. 它能告诉你罗恩、赫敏频率很高。
2. 但不能可靠说明他们在第一卷里具体如何进入叙事。
3. 它能告诉你“后续重要”，却不能真正支持同人或参考写作时的细节调用。

### 4.2 常用视角下，它只能算“开篇导读包”

用普通问题去问，历史包还能勉强回答：

1. 哈利与德思礼家的关系
2. 女贞路 4 号
3. 海格登场
4. 对角巷初次引入
5. 德思礼一家对“正常”的执念

这说明它并非完全无用。

但它更像：

```text
《哈利波特与魔法石》开篇五章导读包
而不是第一卷知识库
```

### 4.3 刁钻视角下，它很快暴露失真

一旦问到第一卷中后段的典型元素，问题立刻显现：

1. `分院帽`
2. `魁地奇`
3. `厄里斯魔镜`
4. `尼可勒梅`
5. `奇洛`
6. `伏地魔`
7. `古灵阁`
8. `麦格`

这些都无法形成像样回答。

这说明历史包不适合作为“已经完成的哈利波特知识库”。

也就是说，它对于“故事刚开场时如何写得像哈利波特”有一定参考价值。

### 5.3 刁钻视角验收：仍明显不通过

我直接用第一卷内部就应当具备的细节去查：

1. `分院帽`
2. `古灵阁`
3. `奇洛`

6. `尼可勒梅`

结果：

1. 最终条目里基本没有。
2. 提案层里也基本没有。
3. 这说明问题不是 review 把它们全丢了。
4. 而是 proposal generation 本身就没有稳定把这些第一卷核心信息抽出来。

### 5.4 这次最关键的实证结论

最重要的证据链是：

1. 源文件本身确实包含这些内容。
2. staging 文件里能看到完整第一卷原文。

这意味着根因更接近：

1. seed/bootstrap 过度偏向开篇几章；
2. batch 执行虽然覆盖整卷，但提案提示词没有稳定推动“后半卷关键设定”进入结构化结果；
3. 当前 `coverage=1.00` 只说明批处理跑完，不说明语义覆盖完成。

这是本轮最值得修正的判断口径。

## 六、从“常用视角”和“刁钻视角”分别看，它到底差在哪

### 6.1 常用视角

常用视角关心的是：

1. 这是谁
2. 故事从哪里开始
3. 世界基调是什么
4. 主要冲突的入口是什么

在这类问题上，当前资产能给出：

1. 足够写简介
2. 足够写开篇模仿
3. 足够做引子参考

但还不够做：

1. 正式同人基底
2. 正式第一卷剧情知识库
3. 细节级世界观复用包

### 6.2 刁钻视角

刁钻视角关心的是：

1. 当智能体忘了某个细节，能不能被救回来。
2. 能不能区分“开篇概况”和“后续关键机制”。
3. 能不能支撑真正的剧情偏移写作。
4. 能不能支撑风格、人物、设定、时间线的综合调用。

在这类问题上，当前资产主要输在四点：

1. **后半卷关键实体没被稳定显式抽出。**
2. **边界条目偏多，细节条目偏少。**
3. **人物高频线索很多，但关系和作用层次不够。**
4. **“可回到原文”能力存在，但“该回到哪里”还不够精确可用。**

## 七、对当前提取链的真正诊断

### 7.1 通过标准过宽

当前 PASS 更像：

1. 文稿读进来了
2. 分批执行了
3. 产出了结构化条目
4. review 接受了一批

但还没要求：

1. 第一卷关键实体必须覆盖到某个最低集合
2. 第一卷关键机制必须至少有若干条进入正式包
3. 风格、角色、设定、剧情结构必须形成更均衡分布

### 7.2 seed 对主提案仍有过强锚定作用

现象上看，seed 仍强烈牵引提案往开篇段落收缩。

它的问题不是 seed 不该存在，而是：

1. seed 该是脚手架
2. 不该变成整轮提案的视野上限

### 7.3 coverage 指标定义不够真实

当前的 `coverage=1.00` 很容易误导。

它更像：

1. 批都处理过了

而不是：

1. 关键设定覆盖达标
2. 中后段情节覆盖达标
3. 角色网络覆盖达标

所以后续应把 coverage 拆开：

1. 批执行覆盖
2. 章节覆盖
3. 关键锚点覆盖
4. 条目类型覆盖

## 八、来源保留应该怎么演化

### 8.1 要保留，但不要把用户淹没

最合理的产品形态不是把所有来源 JSON 裸露给用户，而是：

1. 默认展示结构化结论
2. 可折叠查看来源
3. 可展开到证据片段
4. 必要时可跳回原文位置

这样才能既保留补救能力，又不增加主流用户心智负担。

### 8.2 建议的来源层级

后续来源信息建议稳定分成三层：

1. `origin`
   - 资产本体来自哪里
2. `evidence`
   - 这条结论由哪些具体片段支撑
3. `derivation`
   - 这条结论是 seed、agent 提案、review 合并、还是后处理整理得到

### 8.3 来源层的几个必须修正点

1. 去重重复 `source_ref`
2. 优先保留有效 `evidence_ref`
3. 边界条目和事实条目都应可回跳
4. 网络来源要保留抓取时间、域名、快照身份
5. 图片或多模态来源要保留附件引用，不要被压扁成纯文字标签

## 九、watchdog / supervisor 要不要分层

### 9.1 用户提出 watchdog 的动机是成立的

这次的直觉是对的：

1. 现在的问题不只是“某个判断不够聪明”
2. 而是长任务持续运行本身还不够让人放心
3. 所以需要一种更小、更稳、更少状态、更偏纯调度的保底层

而且这层确实不应由智能体承担。

### 9.2 但 watchdog 不应吞掉 supervisor

如果把 watchdog 做成第二个 supervisor，会立刻重演旧问题：

1. 角色重复
2. 状态来源重复
3. 恢复决策分叉
4. 两套“谁来判失败”的逻辑互相打架

所以正确方向不是二选一，而是清晰分边界。

---

## 十、推荐的最终分层

### 10.1 四层结构

推荐收口成四层：

1. `worker / runtime lane`
   - 真正执行写作、拆书、提取等任务
2. `scheduler / dispatcher`
   - 负责把下一步任务送出去
3. `supervisor`
   - 消费结构化状态，决定 retry / repair / pause / waiting_user / manual_attention
4. `watchdog`
   - 监控上面三层是否还活着、是否还在推进、是否卡死

### 10.2 watchdog 的职责

watchdog 应只做这些事：

1. heartbeat 是否超时
2. 运行 lease 是否过期
3. 队列是否长时间无前进
4. supervisor tick 是否停摆
5. dispatcher 是否失活
6. 是否需要重新唤起 supervisor / dispatcher
7. 是否需要产出一条明确 incident 记录

它不应做这些事：

1. 不读正文
2. 不判文学质量
3. 不理解题材语义
4. 不决定“这章写得像不像哈利波特”
5. 不替代 review lane

### 10.3 supervisor 的职责

supervisor 应继续负责：

1. 消费 `delivery / constraints / information / collaboration / evidence` 摘要
2. 判定是 `recoverable`、`waiting_user`、`manual_attention` 还是 `completed`
3. 调度 retry、repair、resume、checkpoint
4. 维护恢复预算与分支策略

也就是说：

```text
watchdog 保活
supervisor 决策
```

### 10.4 scheduler / dispatcher 的职责

这层只负责推进，不负责解释文学语义，也不负责做最终恢复决策。

它只做：

1. 取可运行任务
2. 校验依赖
3. 派发执行
4. 回写结果

## 十一、watchdog 的存在形态怎么选

### 11.1 短期最现实：先做轻量同进程 watchdog + 持久 lease

这是最容易落地、也最不容易把问题做复杂的方案。

优点：

1. 改动小
2. 能先验证职责边界
3. 能快速发现 supervisor 停摆与调度无前进问题

缺点：

1. 如果整个主进程挂掉，它也一起挂

### 11.2 中期更稳：可选的进程外 watchdog / daemon

如果目标是更强的无人值守与长时间后台运行，那么最终应支持：

1. 独立守护进程
2. 或 docker/runtime worker 进程
3. 或桌面端外部 companion service

它只需要：

1. 读任务账本
2. 读 heartbeat / lease
3. 在必要时重新唤醒 dispatcher / supervisor

不需要：

1. 持有正文上下文
2. 持有章节内容
3. 持有智能体语义状态

### 11.3 结论

因此最合理的路线是：

1. **先不把 supervisor 推翻。**
2. **先在现有 control plane 之上补一个极薄的 liveness guard。**
3. **等 docker / 长后台运行成熟后，再把它外置成真正 watchdog。**

## 十二、这轮最值得记住的判断

### 12.1 关于参考资产提取

当前参考资产提取链的主要问题不是“没有结构”，而是：

1. 结构通过早于内容可用
2. 开篇 bias 过强
3. coverage 指标失真
4. 关键设定覆盖没有验收门槛

### 12.2 关于来源

来源必须保留，而且未来会越来越重要。

它不仅服务审计，更服务：

1. 智能体遗忘时回溯
2. 同人写作的细节取证
3. 历史/科学/神话等客观依据的复用
4. 网络资料与导入资料混合后的可信边界管理

### 12.3 关于稳定性

当前稳定性缺口已经说明：

1. 只靠 supervisor 不够让人安心，
2. 但再造一个“会判断一切的 watchdog”也不对。

正确做法是：

1. watchdog 只做活性与前进性保底
2. supervisor 继续做结构化调度判断
3. 两者共存，职责不重叠

---

## 十三、下一步修正方向

下一步最值得做的不是继续盲目扩充参考资产条目数，而是先修判断与覆盖：

1. 为参考资产提取增加“关键设定覆盖”验收口径。
2. 拆开 `batch coverage` 与 `semantic coverage`。
3. 减弱 seed 对整轮提案的视野束缚。
4. 让提取组对中后段关键实体、设定、剧情机关进行强制抽取。
5. 把来源层做去重与更友好的显示折叠。
6. 为长任务补最小 watchdog / liveness guard，而不是继续把所有恢复责任都压到 supervisor 一个层上。

---

## 十四、最终结论

这轮审计后，可以明确说：

1. **来源保留方向是对的，应保留并继续加强。**
2. **现有哈利波特参考资产还不能当合格的第一卷知识库使用。**
3. **我已经补跑过一次真实提取，问题依旧存在，所以根因在提取链标准与覆盖逻辑，不在旧产物偶发损坏。**
4. **稳定性方面，watchdog 值得补，但应作为 supervisor 之上的最小保活层，而不是另起一套语义调度系统。**

这几个判断已经足够作为后续修正的正式基线。

## 十五、输出侧预算与完整性合同分析

### 15.1 这次新暴露的问题是什么

这轮讨论后，需要把一个此前没有被正式拉出来的问题单独建模：

```text
当前参考提取、拆书、信息收集、总结类任务，
已经开始有“输入预算”和“分批预算”，
但还没有把“输出侧预算不足导致结果被压缩、简化、失真”
正式建模成一等运行时问题。
```

用户的直觉是：

1. 长输出很可能受到模型输出长度限制。
2. 有些模型在长回答时会主动偷懒，变成概括腔。
3. 即使没被硬截断，也可能因为输出压力主动简化答案。
4. 所以需要更合理的压缩与显式提醒，让专门执行这类任务的智能体输出更全面。

这个判断是成立的。

### 15.2 但不能只把它理解为“再多提醒几句”

如果只是补一句：

1. “请尽量全面”
2. “不要遗漏”
3. “请详细输出”

通常是不够的。

因为模型在高输出压力下常见的退化不是“拒绝回答”，而是：

1. 只保留最显眼的结论。
2. 把多个独立知识点压扁成一条大概括。
3. 保证 JSON 看起来合规，但覆盖率实质不足。
4. 默认省略后半段内容，却不显式声明“装不下了”。

所以这不是单纯的 prompt 口吻问题，而是：

```text
输出侧预算与完整性合同缺失问题
```

### 15.3 当前实现缺的不是输出预留，而是输出目标

现有链路已经有：

1. `responseReserveRatio`
2. `instructionReserveRatio`
3. `carryForwardReserveRatio`
4. `safetyReserveRatio`

这些都属于正确方向，但它们主要解决的是：

1. 给输出留空间
2. 避免原文吃满上下文

它们还没有正式解决：

1. 这一轮输出应覆盖哪些维度。
2. 这一轮输出应有多细。
3. 输出不下时应如何报告缺口。
4. 什么叫“输出看起来成功但其实被压缩失败”。

所以现状更准确地说是：

```text
我们已经有输入预算，
但还没有正式的输出预算目标与完整性验收合同。
```

### 15.4 当前 prompt 还在诱导“大而泛的条目”

当前提取 prompt 有几个现实副作用：

1. 单批只要求少量 proposal。
2. proposal 数量上限偏保守。
3. 输出格式要求较重，但覆盖维度没有被显式拆开。

这会诱导模型倾向于：

1. 提几个“看起来很像总结”的大条目；
2. 而不是把当前 batch 中多个独立要点拆出来。

也就是说，现在的问题不只是模型自己压缩，还有：

1. 运行时合同鼓励“少而像样”
2. 却没有强约束“全而诚实”

### 15.5 不能追求单轮绝对完整

这里也要反过来纠偏。

不能把新问题简单改成：

1. 一轮必须把所有东西说全
2. 一轮必须输出得极长极细

这样会产生新问题：

1. 成本暴涨
2. JSON 更脆
3. 模型更容易崩成半截
4. 输出越长越模板化
5. review 成本也会跟着暴涨

所以更合理的方向不是：

```text
强迫单轮完整
```

而是：

```text
让单轮范围明确、
输出目标明确、
遗漏显式、
多轮可续、
最终再 consolidate
```

## 十六、推荐的新建模：输出预算与完整性合同

### 16.1 建议新增的核心对象

建议把这一层正式建成共享合同，而不是继续混在 prompt 文案里。

至少建议新增这些中性对象：

1. `OutputBudgetPolicy`
2. `OutputCoverageContract`
3. `OutputCoverageLedger`
4. `OmissionReport`
5. `ContinuationRequest`
6. `OutputCompressionRisk`

这些对象不应只服务参考提取，也应为以下任务复用：

1. 参考资产提取
2. 拆书
3. 信息收集
4. 风格提炼
5. 长任务 checkpoint 总结
6. 一般项目中的阶段性知识归档

### 16.2 `OutputBudgetPolicy` 应至少表达什么

它不应只是“输出最多多少字”，而应至少能表达：

1. `target_output_density`
   - 当前批次希望输出的细粒度程度。
2. `min_output_slots`
   - 至少需要多少个独立条目/槽位。
3. `max_output_slots`
   - 单轮最多允许多少个条目，防止输出爆炸。
4. `max_summary_chars_per_item`
   - 单条摘要上限，避免单条条目吞掉输出预算。
5. `must_report_omissions`
   - 输出不全时必须声明缺口。
6. `continuation_allowed`
   - 当前轮装不下时，允许显式请求续提。
7. `preferred_output_language`
   - 输出目标语言。
8. `compression_fallback_mode`
   - 输出紧张时是优先保留覆盖广度、细节密度，还是证据锚点。

### 16.3 `OutputCoverageContract` 应按维度交付，而不是只说“请全面”

当前更合理的方式是把“全面”拆成结构化目标。

例如在参考提取中，至少可要求模型显式考虑：

1. 角色事实
2. 地点 / 组织 / 物件
3. 剧情机关 / 世界机制
4. 风格手法
5. 时间线或阶段边界
6. 当前 batch 尚未覆盖但值得继续提的缺口

这样做的好处是：

1. 模型更难把整类信息直接吞掉。
2. review 更容易知道它漏了哪一类。
3. 后续 merge / coverage ledger 才能真正做事。

### 16.4 `OmissionReport` 应成为一等产物

这一点非常关键。

输出不全时，系统现在最差的状态不是“模型答错”，而是：

1. 模型悄悄省略
2. 系统把它当成功

所以建议要求此类任务允许或要求模型显式交付：

1. 已覆盖维度
2. 未覆盖维度
3. 未覆盖原因：
   - 输出预算不足
   - 当前 batch 证据不足
   - 当前批次更适合留给后续 consolidate
4. 建议下一轮优先补提什么

这能把“静默压缩”变成“显式续跑”。

### 16.5 `ContinuationRequest` 不应被当作失败

当前系统容易把“这一轮没说完”理解成：

1. 失败
2. 输出不合格
3. 需要重试

但对重提取任务来说，更合理的是：

1. 若结构正确、覆盖诚实、缺口明确；
2. 那么“请求继续下一轮”应被视为正常运行状态，而不是失败。

所以应引入类似：

1. `needs_continuation`
2. `continuation_reason`
3. `recommended_next_focus`

这类正式字段。

### 16.6 `OutputCompressionRisk` 应进入 review / finalize 口径

当前 review 更像看：

1. 证据是否存在
2. 置信度是否过线

后续应额外看：

1. 当前条目分布是否异常偏概括
2. 是否缺少应有维度
3. 是否存在“少量大条目吞并大量事实”的压缩风险

也就是说，review 不只判真假，还要判：

```text
这是不是一个看起来合规、实则被压缩过的结果
```

## 十七、与现有架构的关系：哪些保留，哪些需要修正

### 17.1 与 `ReferenceIngestionBudgetPolicy` 不冲突

这点要明确。

新引入的输出侧合同不是否定已有输入预算，而是补全它。

更合理的完整结构应是：

1. `IngestionBudgetPolicy`
   - 控输入与切批
2. `OutputBudgetPolicy`
   - 控当前轮应如何交付结果
3. `CoverageLedger`
   - 控全局是否真的提够了

所以它们是互补关系，不是竞争关系。

### 17.2 与当前“单并发默认”不冲突

输出侧完整性问题并不要求改成多并发。

恰恰相反，在当前阶段：

1. 单并发更利于观察输出压缩退化
2. 更利于把“为什么不全”定位清楚
3. 不会因为多线程重复消费原文，把问题与成本一起放大

所以这部分与“默认单并发”完全兼容。

### 17.3 与 seed/bootstrap 定位不冲突

这也不意味着要把 seed 提取得更重。

seed 仍然只是：

1. 初始脚手架
2. 证据骨架
3. 分批定位辅助

输出侧合同应落在：

1. agent proposal generation
2. review / finalize
3. coverage merge

而不是把所有复杂性倒灌回 bootstrap。

### 17.4 与 watchdog / supervisor 分层不冲突

输出侧完整性主要属于：

1. 提取运行时合同
2. review / finalize 口径
3. coverage 账本

它不属于 watchdog 职责。

watchdog 只负责：

1. 这条运行链是不是还活着
2. 是不是卡死
3. supervisor / dispatcher 是不是失活

所以这里不能把“输出不够全”错误地下放给 watchdog。

### 17.5 与“共享能力”方向高度一致

这是一个应当上升为共享能力的典型例子。

因为“输出被压缩、结果看似成功却不完整”绝不只发生在参考提取。

它也会发生在：

1. 拆书
2. 资料总结
3. 阶段性项目总结
4. 长任务 checkpoint 回顾
5. 多智能体中的审核与复盘

所以它适合做成共享合同层，而不是只写进某一个 prompt。

## 十八、这轮冲突与缺漏检查

### 18.1 当前文档与既有分析没有根本冲突

这轮新增判断与以下结论保持一致：

1. `reference-ingestion-budget-and-batch-architecture-analysis-2026-06-08.md`
   - 已经承认输入预算与切批需要正式建模。
2. `reference-extraction-runtime-sweep-analysis-2026-06-08.md`
   - 已经承认 runtime 还没有真正完成整书级收口。
3. `reference-extraction-agent-architecture-analysis-2026-06-07.md`
   - 已经确认 bootstrap 不是完整提取。

本轮只是进一步补上：

1. 输入预算不够，输出预算也要建模。
2. 覆盖率不够，完整性也要正式表达。

### 18.2 当前最主要的缺漏已被识别出来

目前看最需要补的，不是新的题材能力，而是这些共性缺漏：

1. 没有正式 `OutputBudgetPolicy`
2. 没有正式 `OmissionReport`
3. 没有正式 `ContinuationRequest`
4. 没有把 `semantic coverage` 与 `output completeness` 分开
5. 没有把“被压缩的假成功”纳入 review / finalize 口径

### 18.3 需要避免的新误区

后续实现时要避免两种过度修正：

1. 把所有批次都改成超长输出，导致成本和脆弱性一起上升。
2. 把“全面”做成文学意义上的强判定，再次让程序去替代智能体做语义审稿。

更稳的方向仍然是：

1. 程序建合同
2. 智能体按合同交付
3. review / merge 消费合同

## 十九、确定的后续目标

这轮讨论后，可以把后续目标明确成一句话：

```text
把参考提取及其相邻任务中的“输出侧预算、完整性交付、遗漏显式报告、续提机制、覆盖账本”正式建模为共享合同层，并接入 reference_extraction 主链，确保系统不再把被压缩、被概括、未覆盖充分的输出误判为完成。
```

若展开为更具体的目标，则应至少包含：

1. 为参考提取建立正式 `OutputBudgetPolicy`。
2. 为 proposal / review / finalize 建立完整性交付合同。
3. 让模型在输出不足时显式提交 `OmissionReport` 或 `ContinuationRequest`。
4. 让 runtime 能区分：
   - 结构完成
   - 语义覆盖不足
   - 输出压缩风险
   - 需要继续提取
5. 让这套合同未来可复用于拆书、信息收集、阶段总结等任务族。
