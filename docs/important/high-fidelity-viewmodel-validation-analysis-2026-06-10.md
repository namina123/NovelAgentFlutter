# 高保真 ViewModel 验收探针与修复闭环分析

最后更新：2026-06-10

## 1. 这份文档解决什么

这份文档为下一轮“测试、修复、重跑、验收”定下执行边界。它不是再补一个普通 probe，也不是把以前的真实探针扩大章节数后重跑，而是把当前项目已经实现的普通项目、长任务、多智能体、信息收集、知识库、拆书续写、表达限制、连续任务监管等能力，放到更接近真实用户的 GUI ViewModel 路径里验收。

这次测试的核心目标是：

1. 从新项目开始。
2. 通过 ViewModel / Controller 层模拟用户操作。
3. 读取模型真实返回、GUI 状态、项目文件和运行记录。
4. 根据结果动态决定下一步，而不是靠预设提示词跳过前置流程。
5. 任何测试线失败，先定位并修复，再重跑该线及受影响回归，直到通过或给出明确阻塞证据。

这次最重要的变化是：测试脚本不能再像旧探针一样直接把项目喂到某个中间运行时，然后预设“现在写第 N 章”。旧探针可以验证底层合同，但它不能证明用户从 GUI 真实使用时体验是完整、稳定、可恢复的。

## 2. 与旧探针的区别

### 2.1 旧探针允许的捷径，本轮不允许

旧探针常见做法：

1. 直接创建项目目录并预置大量文件。
2. 直接调用 `ProjectWorkflowRuntimeService`、`ProjectConversationDraftRuntimeService` 或类似底层服务。
3. 直接给模型一个强提示：“请生成第 01 章并调用 submit_chapter_delivery”。
4. 探针脚本事后扫描文件判断是否成功。
5. 某些 probe provider / mock provider 会把普通开篇输入短路成正文交付。

本轮不允许这些捷径作为主验收路径。底层服务可以作为辅助取证，但验收必须证明 GUI ViewModel 这条用户路径可用。

### 2.2 本轮必须模拟的用户行为

每条主测试线都要尽量从用户视角进入：

1. 启动应用控制器或同源 ViewModel harness。
2. 创建新项目。
3. 选择或确认智能体组 / 默认智能体组。
4. 发送用户自然语言需求。
5. 读取会话区、当前执行区、项目资源树、状态条、运行记录。
6. 根据模型返回决定下一步：
   - 如果模型要求确认，就模拟用户确认。
   - 如果模型先收集资料，就等资料完成后再继续。
   - 如果模型生成大纲，就检查是否合理再要求下一步。
   - 如果模型直接写正文，要判断这是否符合用户输入和项目阶段。
   - 如果工具失败，要修复真实链路后重跑。

### 2.3 本轮报告不能只写 PASS / FAIL

每条测试线必须输出结构化报告：

```json
{
  "lane_id": "ordinary_information_before_writing",
  "ok": true,
  "report_category": "success",
  "project_root": "...",
  "artifact_dir": "...",
  "viewmodel_steps": [],
  "model_decisions": [],
  "tool_events": [],
  "files_created": [],
  "validation": {},
  "failures": [],
  "fixes_applied": [],
  "rerun_count": 0
}
```

失败分类至少包括：

1. `technical_failure`：代码异常、工具异常、写文件失败、路径错误、provider 调用失败。
2. `product_flow_failure`：GUI / ViewModel 入口不合理、用户路径无法继续、状态提示误导。
3. `runtime_stability_failure`：长任务停止、watchdog / supervisor 未接住、恢复链失效。
4. `content_quality_failure`：正文、知识、续写、表达限制、信息准确性未达验收线。
5. `validation_failure`：探针无法证明结果，证据缺失或报告字段不可信。
6. `blocked_external`：模型服务、网络、输入文件缺失、权限等外部阻塞。
7. `waiting_user`：流程正确停在用户确认点，不应误判成失败。

## 3. 并行测试原则

### 3.1 并行的含义

本轮“并行”指测试线彼此独立、产物隔离、失败闭环独立，而不是把所有测试一口气跑完再统一分析。

正确方式：

1. 每条测试线有自己的 workspace、run id、artifact dir、report。
2. 每条测试线可以独立启动、暂停、恢复、重跑。
3. 任意测试线失败后，立即进入该线的定位与修复。
4. 修复如果触及共享底座，要重跑受影响的相邻线。
5. 不要求等待其他长线全部结束后才处理当前失败。

### 3.2 并行波次

测试不是所有线完全无序地一起跑。部分线存在数据前置依赖，应拆成波次：

1. **Wave 0：基线与语料准备**
   - API / provider / network / proxy / key 安全检查。
   - ViewModel harness 自检。
   - Harry Potter 知识库输入准备。
   - Re:Zero 文本编码转换与分段定位。
   - 网络资料收集最小权限确认。

2. **Wave 1：普通项目与知识生成基础线**
   - 普通项目信息先行再写作。
   - 普通项目多智能体调度。
   - 用户侧知识库生成。
   - 常规书籍导入知识库生成。
   - 网络信息知识库生成。

3. **Wave 2：消费与长任务线**
   - 哈利波特同人写作信息准确性。
   - 历史 + 科技发展资料纪律写作。
   - 一般长任务稳定性。
   - 一般长任务多智能体调度稳定性。
   - 多剧烈变化剧情走向长任务。

4. **Wave 3：拆书续写多层级线**
   - Re:Zero 源文本分段后续写。
   - 基于章节摘要续写。
   - 基于角色 / 世界 / 伏笔 / 时间线资料续写。
   - 基于长任务式拆书续写。

5. **Wave 4：总体验收**
   - 统一报告。
   - 共享底座回归。
   - GUI / ViewModel 真实入口复核。
   - 残留问题分类成“必须修复 / 可延后 / 外部阻塞”。

## 4. 全局硬约束

### 4.1 从新项目开始

每条主测试线都必须创建新项目，不允许复用旧探针项目状态。允许复用应用级设置、内置智能体、内置技能、内置表达限制和已有知识库资产，但项目自身必须从新建开始。

### 4.2 不把测试题材写进核心代码

快穿、哈利波特、Re:Zero、历史穿越、科技发展都只是测试输入。它们不能成为 core / adapters / app 的硬编码分支。

如果需要表达“多世界 / 剧烈变化 / 同人信息准确性 / 科技发展严谨性”，应通过：

1. 用户提示。
2. 项目资料。
3. 智能体组策略。
4. 知识库或参考资产。
5. 信息收集与审核合同。

不能通过 core 中的题材枚举或特殊 if 分支实现。

### 4.3 ViewModel 是主入口

本轮主验收必须从 GUI ViewModel 层获取模型结果并决策下一步。允许使用 headless harness，但它必须消费同源 controller / view data，而不是绕过 UI 语义直接调用底层 runtime。

最小要求：

1. 使用项目创建 controller 或同源 use case 后立即加载到工作台 ViewModel。
2. 使用会话 action handler / controller 发送用户输入。
3. 从 `WorkbenchViewData` / conversation entries / resource entries / tool status / task station view data 读取状态。
4. 根据 ViewModel 状态决定下一步用户输入或确认动作。

### 4.4 表达限制是横切验证

表达限制不是单独只测一次。所有写作类测试都要顺带验证：

1. 新项目是否默认装载内置默认表达限制。
2. 当前执行约束里是否出现表达限制 binding。
3. 模型输出是否明显违背内置去 AI 等表达限制。
4. 多智能体子任务是否也能看到合适的表达限制。
5. 若表达限制被策略跳过，报告必须解释为什么。

### 4.5 知识卡和知识库是横切验证

写作类测试要顺带验证：

1. 需要事实或设定时，智能体是否先收集或调用知识库。
2. 需要沉淀项目资料时，是否生成知识卡 / 研究记录 / 设计元素 / reference work。
3. 后续写作是否真的消费了这些资料，而不是生成后遗忘。
4. 来源是否保留但不泄漏本地绝对路径。

### 4.6 修复后必须重跑

每次修复后必须重跑：

1. 失败测试线。
2. 与修复文件相关的 focused tests。
3. 受影响的相邻主测试线。

不能只修代码不重跑，也不能把失败压成文档结论后继续往下。

### 4.7 动态决策循环

本轮测试脚本不是把提示词一次性塞给模型后等待最终产物，而是要像真实用户一样在每一步读取 ViewModel 结果，再决定下一步。

每个交互 step 至少要执行以下循环：

1. 发送用户输入或确认动作。
2. 等待 ViewModel 状态稳定到可判定阶段。
3. 读取会话条目、工具条目、资源树、当前任务状态、长任务站状态。
4. 分类当前状态：
   - 模型请求用户确认。
   - 工具仍在执行。
   - 工具完成并返回结果。
   - 进入资料收集 / 知识库 / 大纲 / 写作 / 审核 / 修复阶段。
   - 发生技术错误或运行中止。
5. 根据状态选择下一步：
   - 若是合理确认点，模拟用户确认。
   - 若工具仍在执行，继续等待或记录 pending，不把 pending 误判成失败。
   - 若模型直接越过应有阶段，要标记为 product flow 或 prompt discipline 问题。
   - 若工具失败，进入失败定位与修复。
   - 若正文、知识库、续写等产物出现质量问题，进入内容质量失败定位。

这个循环是本轮高保真的核心。若测试只检查最终文件，不记录中途 ViewModel 状态，就不能算通过。

### 4.8 耗时工具与动态结果显示

许多工具不会马上出结果，包括联网检索、书籍导入、知识库提取、长任务章节生成、审核修复、拆书续写等。测试必须验证 GUI / ViewModel 对这些工具的状态表达是否真实：

1. 工具开始后应出现执行中状态。
2. 未完成时不能显示成“已完成”或把空结果当成结果。
3. 完成后应更新为结果摘要，并能展开或追溯关键证据。
4. 失败时要展示可理解的错误，而不是只在日志里出现。
5. 重试、暂停、恢复时，状态变化应与实际调度一致。

工具状态验证既是 UI 易用性测试，也是稳定性测试。过去很多“像是模型没有写正文”的问题，本质上可能是工具轮、结果投影、后处理证据之间的状态断裂，本轮必须把这些断裂暴露出来。

### 4.9 运行台账与产物路径

每轮 HFVV 运行必须创建独立 run id，建议路径为：

```text
artifacts/high_fidelity_viewmodel_validation/<run_id>/
```

每条 lane 使用独立目录：

```text
artifacts/high_fidelity_viewmodel_validation/<run_id>/<lane_id>/
```

每条 lane 至少保留：

1. `lane_report.json`：结构化验收报告。
2. `step_XXX_viewmodel.json`：每一步 ViewModel 快照。
3. `step_XXX_model_event.json`：模型返回摘要，不能包含密钥。
4. `step_XXX_tool_events.json`：工具调用、pending、完成、失败、重试摘要。
5. `project_manifest.json`：新项目位置、项目类型、挂载知识库、表达限制、智能体组摘要。
6. `fix_log.md`：若该 lane 修复过，记录问题、修改点、重跑结果。

报告不得提交 API key、私有配置、大体量原文复制、本机绝对路径作为可分发来源。需要记录来源时，应使用 source asset id、相对路径、哈希、导入时间、来源类别等可分发身份。

### 4.10 失败修复闭环

任意 lane 出现失败时，执行顺序必须是：

1. 冻结失败现场，保存 step 快照、模型事件、工具事件、产物文件和相关日志。
2. 分类失败。
3. 判断是否触及共享底座。
4. 修生产链路，不在 probe / harness 中吞错。
5. 补 focused test 或 contract test。
6. 重跑失败 lane。
7. 若触及共享底座，重跑受影响的相邻 lane 或共享回归。
8. 更新 `fix_log.md` 和 `lane_report.json`。

如果同一失败经过三轮仍无法推进，应标为明确 blocker，写清缺失条件，例如模型服务不可用、网络不可用、输入文件缺失、外部接口限制，而不是继续无限重试。

### 4.11 长任务最小运行长度

凡是以“长任务稳定性”为主验收目标的测试线，必须至少跑到 50 个有效章节，不能只跑几章样章就判定通过。

适用范围：

1. 一般长任务稳定性。
2. 一般长任务多智能体调度稳定性。
3. 多剧烈变化剧情走向长任务。
4. 拆书续写中的长任务式续写子线。

有效章节必须同时满足：

1. 章节文件或等价章节产物已经稳定落盘。
2. 不是只有章号或标题。
3. 正文长度达到该项目当前章节策略的最低可接受范围。
4. 表达限制、知识资料、连续性状态、长任务状态都有可追溯记录。

这个限制只属于测试验收，不代表产品核心要强行把所有长任务写成 50 章。测试执行时也不能预排 1-50 章或 1-200 章任务清单；应让智能体自然规划和推进，只是在验收层要求运行必须持续到 50 个有效章节，或给出明确 `blocked_external` / 不可恢复失败证据。

## 5. 测试矩阵

### 5.1 普通项目信息先行再写作

目标：

1. 用户创建普通小说项目。
2. 用户输入“历史 + 科技发展”类题材，例如社畜穿越到明代或其他朝代，想用现代科学知识发展。
3. 智能体应先判断是否需要收集历史、制度、时代技术、风险边界等信息。
4. 除非用户明确要求“先不要查资料，直接写”，否则不应直接编造大量事实背景并进入正文。

验收：

1. 会话中出现资料研究请求、研究记录、知识卡或等待确认。
2. 若使用网络，来源质量应符合事实严谨要求。
3. 资料收集后再推进大纲 / 设定 / 正文。
4. 输出避免明显时代常识错误，例如盐铁管制、技术可得性、工艺条件、社会制度完全无视。
5. 表达限制生效。

### 5.2 普通项目多智能体写作体系

目标：

1. 创建普通小说项目。
2. 使用包含主智能体、资料/设定子智能体、审核子智能体或写作子智能体的智能体组。
3. 用户提出需要分工的任务。
4. 主智能体应在合适时机调用子智能体，而不是所有工作都自己硬做。

验收：

1. ViewModel 显示子智能体运行记录或相应投影。
2. 子智能体没有继承主智能体完整上下文，而是通过项目资料、主智能体任务说明、工具读取获取必要信息。
3. 子智能体结果回到主线程，被主智能体消费。
4. 子智能体也受工具权限、表达限制、信息纪律约束。

### 5.3 用户侧知识库生成

目标：

1. 用户从 GUI / ViewModel 入口创建知识库或参考资产。
2. 输入小规模材料，要求智能体提取可复用知识。
3. 测试是否能保存结构化结果、来源、摘要和映射信息。

验收：

1. 不只生成一份大 Markdown。
2. 结构化基底可查找。
3. 来源身份合理，不暴露原始本地绝对路径作为分发事实。
4. 用户可从 GUI 找到生成结果。

### 5.4 常规书籍导入知识库生成

目标：

1. 使用 `references/files/Harry Potter.txt` 或小规模切片先做导入。
2. 模拟用户选择“从书籍生成可复用知识库”。
3. 由提取类智能体组完成，而不是写作智能体组硬做。

验收：

1. 结果为中文。
2. 包含角色、时间线、地点、组织、魔法体系、重要物品、情节因果、文风观察、伏笔与限制。
3. 能回答常见问题与刁钻问题。
4. 能被后续写作项目挂载消费。

### 5.5 网络信息知识库生成

目标：

1. 用户创建历史 / 科技发展资料知识库。
2. 通过网络收集事实资料。
3. 测试大陆网络代理配置与来源质量策略。

验收：

1. 客观事实优先严谨来源。
2. 网络失败时不假装已经查到。
3. 能形成可复用知识，而不是只生成一次性聊天回答。
4. 能区分事实、推测、创作建议。

### 5.6 哈利波特同人写作信息准确性

目标：

1. 使用 Harry Potter 知识库。
2. 写用户之前提到的题材：地球中国主角，天师老死后转生哈利波特世界，与哈利同级，利用修仙知识解决问题，轻松向，解决原作意难平并处理剧情偏移。
3. 验证知识库消费、同人信息准确性和剧情偏移合理性。

验收：

1. 不凭空改原作关键事实。
2. 能说明使用了哪些知识库条目。
3. 原作意难平的改动有代价、有因果、有后续偏移。
4. 修仙知识来自知识卡或可解释设定，不抢走魔法世界规则。
5. 表达限制生效。

### 5.7 一般长任务稳定性

目标：

1. 从 GUI / ViewModel 创建普通长任务项目或普通项目长任务。
2. 不预排 1-200 章。
3. 让智能体根据内容自然规划与推进。
4. 测试 watchdog / supervisor / retry / recovery / task station 的真实可用性。
5. 至少跑到 50 个有效章节，不能只以少量样章通过。

验收：

1. 长任务不会无故停止。
2. 停止时能分类原因。
3. 缺正文、只读轮、字数严重偏离、表达限制失效等能进入恢复链。
4. GUI 长任务站能看到真实状态。
5. 重跑可恢复，不重复写坏章节。
6. 50 个有效章节均有落盘、状态与工具事件证据。

### 5.8 一般长任务多智能体调度稳定性

目标：

1. 使用包含主写作、资料、审核、连续性维护等成员的智能体组。
2. 运行一般长任务。
3. 验证主智能体在章节规划、资料核查、审核修复阶段能调度子智能体。
4. 至少跑到 50 个有效章节。

验收：

1. 子智能体调度不是假显示。
2. 子智能体结果影响后续任务。
3. 子智能体失败时 supervisor 能处理。
4. 多智能体不会破坏章节交付和表达限制。
5. 50 个有效章节内能看到稳定的主 / 子智能体调度证据。

### 5.9 多剧烈变化剧情走向

目标：

1. 用一般长任务测试“多世界 / 剧烈变化 / 快穿式走向”。
2. 这只是通用压力输入，不允许 core 写死快穿。
3. 用户输入可用快穿举例：主角从自己的世界穿书到都市高武、修仙、女频恋爱等世界，每个世界结束后回归现实调整再进入下一个世界。
4. 至少跑到 50 个有效章节，验证剧烈变化不是前几章样板。

验收：

1. 变化点由叙事状态、项目资料、智能体判断处理，不靠程序枚举词判断。
2. 世界切换前后角色状态、记忆、任务目标、世界规则能稳定记录。
3. 分段点可以在章节中部出现，不要求只在章首章尾。
4. 长任务稳定性、表达限制、信息资料都仍然生效。
5. 50 个有效章节内至少覆盖多次关键变化，并记录变化依据。

### 5.10 拆书续写多层级

目标：

1. 使用 `references/files/re从零开始的异世界生活.txt`。
2. 文件存在编码问题，先复制到 artifacts 或 local 临时区并转换编码，不修改原文件。
3. 在合适位置分段，大约 100 万字左右作为续写起点，优先按章节边界或自然段落边界。
4. 从多个层级并行测试拆书续写：
   - 原文片段直接续写。
   - 摘要层续写。
   - 角色 / 世界 / 伏笔 / 时间线资料续写。
   - 长任务式拆书续写，至少跑到 50 个有效章节。

验收：

1. 续写能延续上下文、人物口吻、悬念、节奏和冲突。
2. 不因为分段导致角色记忆或状态断裂。
3. 不把原作资料和新创作混成无法区分的事实。
4. 能记录续写造成的偏移。
5. 表达限制在续写正文中仍然生效。
6. 长任务式续写子线达到 50 个有效章节，或给出明确阻塞证据。

## 6. 需要补充的测试点

用户列出的测试点之外，还应补以下内容：

1. **默认表达限制装载**  
   新项目创建后，检查应用级默认表达限制是否进入项目 binding；显式关闭时不装载。

2. **工具动态显示**  
   长耗时工具需要先显示执行中，完成后再显示结果；不能把 pending 工具当成已完成。

3. **用户确认点**  
   信息收集、外部联网、重大剧情分歧、知识库挂载等确认点应能暂停并恢复。

4. **来源与隐私**  
   知识库、书籍导入、网络资料不应把本机绝对路径作为分发事实源暴露。

5. **SQLite / 结构化事实源**  
   参考资产和知识库验收要检查结构化基底，不只检查 Markdown 投影。

6. **失败分类与 watchdog**  
   长任务、提取任务、拆书续写都属于连续过程，失败应进入可观察调度，而不是静默停止。

7. **成本与预算证据**  
   报告应记录模型、请求次数、输入输出粗略规模、重跑次数，避免无限重试吞预算。

8. **密钥与测试产物安全**  
   不提交测试 API key、不提交大体量原文复制、不把 private config 写入公开文档。
