## 1. 本文解决什么

这轮不是讨论“要不要给拆书多加几个按钮”，而是要把下面几件事一起收口成一套合理架构：

1. 拆书项目当前是否应该接入知识库系统。
2. 拆书后的目标类型是否应该分流。
3. 拆书续写与拆书同人的产物边界应该如何区分。
4. 拆书原文必须如何留存。
5. `epub`、文件夹导入、多文件扫描应该落在哪一层。
6. 一般项目导入与拆书导入哪些逻辑应该共享，哪些不该混。
7. “智能分析导入内容类型”是否合理，以及应该如何暴露。

用户这轮给出的关键约束非常明确：

1. **拆书项目目前不用接入知识库系统，就按现在的体系走。**
2. **拆完后必须尽可能完整地提取有效信息。**
3. **拆书后需要一个次级选项，至少支持：**
   - 拆书续写
   - 拆书同人
4. **拆书续写时，拆开的原作章节需要进入正文体系。**
5. **`epub` 等多文件形态必须支持文件夹导入，并扫描层级内所有支持格式。**
6. **一般项目导入未来也要用到同一套格式解析层，但上层业务语义不同。**
7. **只有已有项目导入应有“智能分析”选项，默认勾选，用于判断导入内容到底是什么。**
8. **智能分析必须允许选择执行分析的智能体或智能体组；拆书导入不需要这层。**

我认为这组要求总体是合理的，但要做一些关键修正，不然会在后续实现时把“源材料导入”“拆书分析”“续写工程”“知识库治理”重新揉成一团。

## 2. 先确认现状：当前拆书真实在做什么

当前项目里的拆书，不是“生成一个独立知识库项目”，而是：

1. 读取源文稿。
2. 做轻量结构化抽取。
3. 生成一个可确认的 preview / application plan。
4. 将结果桥接为：
   - continuity claims
   - profile proposals
   - semantic reviews
   - knowledge cards
   - design elements
   - research notes
   - reference works
5. 再把这些写回当前项目。

这意味着：

```text
当前拆书本质上是“结构化拆书分析桥”，
而不是“知识库项目创建器”。
```

这个定位本身没有错。

所以，用户提出“拆书项目目前不用接入知识库系统，就按现在的”，我认为是正确的。至少在当前阶段，不应该把拆书链强行改造成：

1. 一导入就生成 SQLite 知识库项目。
2. 所有拆书结果都必须走知识库治理 UI。
3. 拆书项目和知识库项目语义合并。

这样会把两类完全不同的事情绑死在一起：

1. 拆书是“为了后续创作承接而分析来源作品”。
2. 知识库治理是“为了结构化沉淀和复用而管理事实资产”。

二者当然会重叠，但不是同一个产品入口。

## 3. 现状里的真正问题

当前真正需要修的，不是“拆书为什么没进知识库”，而是下面这几条。

### 3.1 原文留存目前不一致

现状有两条不同链：

1. 工作台“导入 + 自动拆书”：
   - 会先复制原文件进项目
   - 再生成自动拆书预演

2. 拆书专用面板：
   - 只把外部文件读到内存
   - 确认时写 preview 和结构化结果
   - **不会强制把原文归档到项目**

这是明显不合理的。

因为拆书这类工作比普通写作更依赖可追溯性：

1. 后续要复核是否抽错。
2. 后续要重新提取更细的结构时，不能要求用户重新找原文。
3. 后续若要派生同人、续写、解说等不同项目，原文应是稳定来源。
4. 未来若要分享拆书项目，结构化结果不能脱离原始来源完全漂浮。

所以：

**拆书原文留存必须从“有时会留”升级成“必留”。**

### 3.2 当前把拆书原文和预演纪要写到 `chapters/` 不合理

当前工作台自动拆书对 `book_deconstruction` 项目默认行为是：

1. 导入原文到 `chapters/`
2. 自动拆书预演纪要也写到 `chapters/book_deconstruction_xxx.md`

这会造成三类语义污染：

1. 来源材料和正式正文混在一起。
2. 预演分析纪要和原作章节混在一起。
3. 后续续写时很容易把“原作章节”“分析预演”“新写正文”都当成同一层内容。

所以现在最大的问题不是“有没有导入”，而是：

**导入后的内容层次不清。**

### 3.3 当前拆书抽取是轻量结构化提取，不足以承担“完整有效信息抽取”

用户这轮明确说：

> 拆完后必须保证所有有效信息都提取出来。

这一点和当前实现之间有明显落差。

当前 `BookDeconstructionDraftBuilderService` 更像：

1. 轻量结构化摘要器
2. 章级轮廓抽取器
3. 手工补录字段整合器

它擅长的是：

1. 快速得到可看、可确认的结构化预演
2. 为 continuity / information 桥接生成底稿

它不擅长的是：

1. 大规模、多章节、多来源的完整知识抽取
2. 对全书风格、命名系统、伏笔、深层设定做高覆盖率提炼
3. 对复杂原作做高保真、可复核的全量信息生产

所以这里需要非常诚实：

**当前拆书足够作为“预演型拆书”和“后续续写前置分析”，但还不足以直接宣称“完整有效信息都能提出来”。**

这不意味着方向错了，而是意味着我们必须补“导入解析层 + 分批摄取层 + 更正式的拆书提取运行时”。

## 4. 关于“拆书项目暂不接知识库系统”的正式判断

我的结论是：

### 4.1 这个判断合理，而且应该保留

原因不是我们不要知识，而是：

1. 拆书和知识库治理是不同产品语义。
2. 拆书首先服务“后续创作承接”。
3. 知识库首先服务“长期治理、复用、映射、分享”。
4. 当前拆书结果已经会产出 information 类资产，但这不等于应该强制切到知识库项目工作流。

### 4.2 但要保留未来对接位

虽然现在不接知识库系统，但架构上应明确：

1. 拆书来源、拆书预演、拆书提取结果都应可被未来知识库治理系统消费。
2. 拆书结果中的 information artifacts 不能写死成只有拆书自己能看懂的结构。
3. 原文来源记录、覆盖范围记录、来源路径记录必须保留。

也就是说：

```text
当前阶段：拆书不切到知识库主流程。
架构要求：拆书结果必须保留未来进入知识治理的可能性。
```

这是一种“产品不耦合、数据可升级”的姿势。

## 5. 新的核心产品语义：拆书后的“次级类型”应该存在，但它不应等于立刻改项目主类型

用户提出：

> 拆书应当再额外增加一个次级选项，选择拆书后的类型，目前来说，拆书续写和拆书同人两种类型就行。

这个方向我认为是对的，但命名和落点要更精确。

### 5.1 正确的语义不是“拆书项目类型再细分”

不建议把 `book_deconstruction` 本身拆成：

1. `book_deconstruction_continuation`
2. `book_deconstruction_fanfic`

因为拆书项目本身的职责仍然是：

1. 导入来源作品
2. 解析与提取
3. 形成可复核的结构化底稿

它不是正式写作执行项目。

### 5.2 更合理的语义是：拆书后的“后续工程导向”或“派生目标”

也就是：

1. 主项目类型仍是 `book_deconstruction`
2. 在拆书流程中增加一个次级配置：
   - `continuation`
   - `fanfic`

它的意义不是改变拆书项目本体，而是决定：

1. 原文如何归档
2. 预演计划偏向什么
3. 抽取优先级偏向什么
4. 拆书确认后默认派生出什么样的后续工程

所以它更像：

- `followup_intent`
- `deconstruction_target_mode`
- `derived_writing_target`

而不是新的主项目类型。

### 5.3 为什么这样更稳

因为未来一定不止两种：

1. 拆书续写
2. 拆书同人
3. 拆书解说
4. 拆书总结
5. 拆书设定抽取
6. 拆书路线重构

如果现在就把它们都变成主项目类型，很快会让项目类型目录膨胀。

更稳的方式是：

1. 主项目类型保持稳定
2. 次级导向作为策略层扩展

## 6. 拆书续写与拆书同人，应该如何区分

这是这轮最关键的产品边界之一。

### 6.1 拆书续写

它的本质是：

**把导入作品视为同一条正文连续体的前序部分。**

因此它必须满足：

1. 原作拆开的章节进入正文体系。
2. 后续新写章节与导入章节处于同一条连续正文链。
3. continuity / chapter continuity / context activation 都应把这些导入章节当成正式前情。
4. 但这些导入章节仍必须带来源标记，不能和新创作章节完全无差别混写。

所以，用户说：

> 拆书续写就得把拆开的章节放在正文

我认为这个要求是合理的，但要附加一个关键修正：

**进入正文体系，不等于“失去来源身份”。**

也就是说，拆书续写模式下应当允许：

1. 导入章节在 `chapters/` 下可见、可读取、可进入连续性链
2. 但同时必须保存：
   - `imported_from_source = true`
   - `source_document_id`
   - `source_path`
   - `source_range`
   - `frozen_by_default = true`

否则后续系统根本分不清：

1. 哪些正文是原作导入
2. 哪些正文是本项目新写

### 6.2 拆书同人

它的本质不是接正文，而是：

**基于原作信息体系派生新作品。**

因此它和续写不同：

1. 不需要把原作拆开的所有章节塞进正文主链
2. 需要保留原文来源、设定、角色、组织、时间线、风格、命名系统等信息
3. 更重视“信息体系可调用”，而不是“正文连续接写”

所以拆书同人更适合：

1. 保留原始来源于 `sources/` 或 `references/source_texts/`
2. 保留拆书提取结果于现有 continuity / information 层
3. 派生新项目时，把这些信息作为参考资产，而不是正文前文

### 6.3 两者的核心差别

可以用一句话概括：

- 拆书续写：原作正文是“当前正文链的已完成前段”
- 拆书同人：原作正文是“当前创作链的来源材料与事实边界”

这两者如果不分开，后面导入目录、上下文读取、章节承接、引用边界都会乱。

## 7. 原文留存应该如何重新设计

### 7.1 必须区分三层

后续不能再把“原文在哪里”说成一个问题，而应该拆成三层：

1. **原始来源层**
2. **拆解正文层**
3. **结构化提取层**

### 7.2 原始来源层

无论是续写还是同人，都必须保留：

1. 用户导入的原始文件
2. 原始目录结构信息
3. 文件级元信息：
   - 原始文件名
   - 原始绝对路径快照
   - media type
   - 发现时间
   - 内容哈希

推荐目录：

- `sources/imported/`
或
- `references/source_texts/`

我更倾向于：

- `sources/` 作为中性来源层

这样一般项目、拆书项目、知识提取项目将来都能共用。

### 7.3 拆解正文层

只有在 `continuation` 模式下，才应该把拆开的原作章节投影进正文体系。

但这不是直接拿原文件往 `chapters/` 一丢，而是要经过：

1. 来源标准化
2. 章节切分
3. 章节编号与标题解析
4. 冻结标记
5. 连续性接线

然后再写入 `chapters/`

这时每个章节都是：

1. 正文层可消费对象
2. 但仍有来源元数据

### 7.4 结构化提取层

这一层保持当前方向即可：

1. continuity claims
2. semantic reviews
3. profile proposals
4. knowledge cards
5. design elements
6. research notes
7. reference works

这层不应再承担“原文在哪”的职责。

## 8. 文件夹导入与多格式导入：你的思路是对的，而且应该升级为共享解析层

你这轮补充的关键点非常正确：

> `epub` 等一般是多文件，所以拆书本身就应该支持文件夹导入，然后扫描文件夹层级内所有支持格式导入。

我完全同意，而且这一步不能只做成拆书特例。

### 8.1 为什么 `epub` 不是“再加一个扩展名”这么简单

`epub` 本质上是：

1. 压缩容器
2. 内含多文件
3. 可能包含：
   - HTML/XHTML 正文
   - OPF 元数据
   - TOC / nav
   - 样式
   - 图片

所以如果还沿用当前：

1. 文件选择器选单文件
2. `readExternalTextFile()` 直接 `readAsString()`

那就永远不可能正确支持 `epub`。

### 8.2 正确方向：新增“来源解析层”

必须正式新增一个中性解析层，例如：

1. `ImportedSourceDiscoveryService`
2. `ImportedSourceDocumentReader`
3. `ImportedSourceNormalizationService`
4. `ImportedSourceBundle`

它的职责是：

1. 扫描文件或目录
2. 识别支持格式
3. 对不同格式做解析
4. 统一产出标准化 source documents

而不是让拆书服务自己去判断：

- 这是 `.txt`
- 这是 `.md`
- 这是 `.epub`
- 这是目录

### 8.3 共享解析层应至少支持的输入形态

第一批建议支持：

1. 单文件：
   - `.txt`
   - `.md`
   - `.markdown`
   - `.epub`

2. 目录输入：
   - 递归扫描子目录
   - 收集支持格式
   - 保留层级信息

3. 对 `epub`：
   - 从容器内解析正文顺序
   - 生成多个标准化 source documents
   - 尽量保留原书目录与章节顺序

### 8.4 为什么这层必须共享，而不是只给拆书用

因为一般项目导入未来同样会需要：

1. 导入已经写好的设定文档
2. 导入现成大纲
3. 导入旧稿正文
4. 导入参考资料包
5. 导入 markdown 文档集
6. 导入一个目录里的多份材料

也就是说：

**格式支持和目录扫描是宿主级基础能力，不是拆书专属能力。**

但共享的是：

1. 文件发现
2. 格式解析
3. 标准化 source documents

不共享的是上层业务编排。

## 9. 一般导入与拆书导入：应共享解析层，但不能共享同一条业务编排

这点你说得非常对。

### 9.1 共享的部分

一般导入和拆书导入应该共享：

1. 目录扫描
2. 文件格式识别
3. 文本提取
4. 标准化 source document 结构
5. 来源元数据保留

### 9.2 不应共享的部分

它们不该共享同一条“解释业务语义”的编排链。

#### 拆书导入的默认前提

拆书导入天然可以假设：

1. 导入的是一本书或一本书的构成材料
2. 目标是做书籍级分析、提取、承接

#### 一般项目导入的默认前提

一般项目导入不能假设：

1. 导入的是小说原文
2. 导入的一定是完整书籍
3. 导入内容一定应当进正文

它可能是：

1. 设定文档
2. 角色卡
3. 大纲
4. 旧正文
5. 资料参考
6. 灵感草稿

所以：

**解析层共享，业务分类和后续动作不能共享。**

## 10. “智能分析”应只存在于已有项目导入，而且它应当是导入分流器，不是黑箱自动决定器

用户建议：

> 一般项目导入的时候可选智能分析，默认勾选，智能分析就是大致分析导入的内容到底是什么，是小说原文还是什么。

用户随后又补了一条非常重要的边界：

> 智能分析需要选择智能体去做；而且智能分析只有已有项目导入的时候需要，拆书导入的时候不需要。

我认为这个修正是对的，而且比最初版本更自然。

拆书导入的业务语义本来就已经足够明确：

1. 导入的是书籍原文或其构成材料
2. 目标是拆书、提取、承接
3. 后续只需要区分续写/同人等派生方向

在这种前提下，再加一层“智能分析这到底是不是书”并不会让体验更好，反而会：

1. 增加一次不必要的模型调用
2. 让拆书链多一个可能误判的入口
3. 把本来明确的产品语义又重新做模糊

所以这里应该正式收口为：

```text
智能分析只属于“已有项目导入”。
拆书导入直接进入拆书导入编排，不走智能分类。
```

### 10.1 为什么这个功能对“已有项目导入”有必要

已有项目导入如果没有这层，系统就只能：

1. 把所有文件都当普通附件
2. 或让用户逐一手动指定用途

这两种都不够好：

1. 前者太笨
2. 后者心智负担太大

所以引入“智能分析导入内容类型”是合理的。

但这里的合理性明确只成立于：

1. 用户已经在一个既有项目里
2. 用户正在导入一批语义未知或混杂的资料
3. 系统需要帮用户判断这些资料更像大纲、设定、旧稿、参考资料还是正文来源

### 10.2 但它不能直接替用户做最终决定

这层更好的职责应是：

1. 给出建议分类
2. 给出置信度
3. 给出建议目标目录或目标资产类型
4. 允许用户一键确认或改掉
5. 允许用户选择执行分析的智能体或智能体组

不能直接变成：

1. 自动分析
2. 自动落盘
3. 自动把资料写进正文或世界观

因为误分流风险太高。

### 10.3 建议的分类结果

第一批可以先只支持这些建议类别：

1. `novel_source_text`
2. `outline_document`
3. `worldbuilding_document`
4. `character_document`
5. `reference_material`
6. `mixed_unknown`

对于拆书项目：

1. 不显示智能分析开关
2. 不要求用户选择分析智能体
3. 直接按拆书导入编排进入解析与归档

对于已有项目导入：

1. 默认开启智能分析
2. 允许选择执行分析的智能体或智能体组
3. 先给建议，再允许改

### 10.4 这层应该如何落位

这层应该作为：

- `import classification`

或

- `source intent inference`

放在共享解析层之上、具体业务编排层之下。

也就是说：

1. 先发现和解析 source documents
2. 再做内容类型建议分类
3. 再让不同项目类型的导入编排去消费

---

## 11. 关于“所有有效信息都提取出来”的现实判断

这句话方向对，但必须重新定义，不然会误导实现。

### 11.1 不能按字面理解成“一次性全提完”

真正可靠的目标不应是：

1. 单次导入
2. 单轮预演
3. 就把全书所有有效信息完美提光

这是不现实的。

### 11.2 更合理的定义

应定义为：

1. 所有来源原文都被稳定留存
2. 所有来源文本都可被解析成标准化 source documents
3. 拆书提取链对这些 source documents 具备分批摄取能力
4. 提取结果有覆盖状态
5. 后续可以继续补提，而不是只能推倒重来

也就是说：

```text
不是“当前这次就一定全提完”，
而是“系统要有能力逐步稳定地把有效信息提出来，并且可复跑、可补提、可追溯”。
```

### 11.3 对当前拆书的直接要求

当前阶段至少应该做到：

1. 原文不丢
2. 章节不丢
3. 来源范围不丢
4. 结构化预演不丢
5. continuity / information 桥接结果不丢
6. 后续支持更强提取器重跑，而不需要重新导入来源

---

## 12. 推荐的新架构分层

我建议把这块正式拆成下面四层。

### 12.1 第一层：来源导入与解析层

职责：

1. 文件/文件夹选择
2. 递归扫描
3. 支持格式识别
4. 文本提取
5. 标准化 source documents
6. 原始来源归档

这一层共享给：

1. 拆书项目导入
2. 一般项目导入
3. 未来知识提取项目

### 12.2 第二层：导入分类建议层

职责：

1. 智能分析导入内容是什么
2. 给出建议用途
3. 给出置信度
4. 给出建议目标动作
5. 记录 `analyzerAgentId / analyzerAgentGroupId`

这一层只对已有项目导入重要，不进入拆书导入主链。

### 12.3 第三层：项目特化导入编排层

职责：

1. `book_deconstruction`：
   - 来源归档
   - 拆书预演
   - 提取桥接
   - 后续导向分流

2. `novel / long_novel`：
   - 一般资料导入
   - 智能分析
   - 可能的资产映射

这一层不共享具体策略。

### 12.4 第四层：后续工程派生层

职责：

1. continuation 派生
2. fanfic 派生
3. 未来其他派生模式

这一层把拆书结果真正接到后续写作工程上。

## 13. 推荐的具体产品语义

### 13.1 拆书项目新增次级选项

在拆书导入或确认阶段，引入：

- `后续导向`
  - `拆书续写`
  - `拆书同人`

默认值建议：

- 若用户是从“续写”类入口进入，则默认 `拆书续写`
- 若用户是从“同人/衍生”类入口进入，则默认 `拆书同人`
- 否则默认 `拆书续写`

### 13.2 拆书续写模式

执行规则：

1. 原始来源保留到 `sources/`
2. 解析得到的章节标准化后写入 `chapters/`
3. 写入 metadata，标记为 imported/frozen/source-backed
4. 结构化提取照常写入 continuity / information 层
5. 后续新写章节继续接在同一正文链

### 13.3 拆书同人模式

执行规则：

1. 原始来源保留到 `sources/`
2. 不把原作全文默认写入 `chapters/`
3. 结构化提取进入 continuity / information 层
4. 派生新项目时把这些作为来源边界和参考资产

### 13.4 一般项目导入

执行规则：

1. 支持文件/文件夹/多格式导入
2. 默认开启智能分析
3. 允许选择执行分析的智能体或智能体组
4. 给出建议用途
5. 由用户确认再落到具体目录或资产层

## 14. 对当前实现的演化建议

### 14.1 立刻应该做的

1. 统一拆书原文留存策略
   - 专用拆书面板也必须归档原文

2. 停止把拆书项目的原文和预演纪要默认写进 `chapters/`
   - 除非当前导向明确是 `continuation`

3. 新增共享来源解析层
   - 支持单文件与目录
   - 为 `epub` 预留正式 reader

4. 引入拆书后续导向配置
   - `continuation`
   - `fanfic`

5. 把“智能分析”限定在已有项目导入
   - 且允许显式选择分析智能体或智能体组

### 14.2 下一阶段应该做的

1. 建立多 source document 的拆书输入合同
2. 建立覆盖状态与分批提取能力
3. 让拆书提取从“轻量预演”演化为“可补提、可复跑”的正式链
4. 建立 continuation / fanfic 派生工程合同

### 14.3 当前不该做的

1. 不要把拆书项目直接改造成知识库项目
2. 不要把一般导入和拆书导入揉成一条黑箱
3. 不要只靠增加几个扩展名来声称支持 `epub`
4. 不要把拆书续写模式下的导入正文和新创作正文做成完全无差别文件

---

## 15. 最终结论

把这轮结论压缩成几句最关键的话：

1. **拆书项目当前不接知识库系统是合理的，应保留。**
2. **真正该补的是：原文必留、来源解析层、多格式/文件夹导入、拆书后续导向分流。**
3. **拆书后的次级选项是对的，但它应当是“后续导向”或“派生目标”，不应膨胀成新的主项目类型。**
4. **拆书续写与拆书同人必须分开：前者把原作章节接入正文连续体，后者把原作作为来源体系与参考边界。**
5. **`epub`、目录扫描、多格式解析不应做成拆书特例，而应做成共享来源解析层；上层业务编排再按项目类型分流。**
6. **一般项目导入的“智能分析”默认勾选是合理的，但它只属于已有项目导入，并且应提供建议而不是替用户做最终落盘决定。**
7. **智能分析应允许显式选择分析智能体或智能体组，避免偷偷绑定到主写作智能体。**
8. **“所有有效信息都提取出来”应被定义为可稳定提取、可复跑、可补提、可追溯，而不是一次性全提完。**

如果后续要真正开始实现，这一轮最自然的下一步不是直接乱改，而是按下面顺序推进：

1. 共享来源解析层
2. 拆书原文归档统一
3. 拆书后续导向分流
4. continuation / fanfic 的目录与派生合同
5. 多 source document 的正式拆书提取运行时

这条顺序是当前最稳、也最不容易把系统重新做乱的推进方式。
