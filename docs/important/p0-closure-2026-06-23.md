### 1. 诚实标注（commit `9d18d2b`）

检索 executor 不再冒充。`_searchHits` 返回 `_SearchOutcome`（hits + mode），mode 取值：
- `vector`：向量端口正常召回。
- `lexical`：未注入/未解析出向量端口，走关键词匹配。
- `lexical_fallback`：注入了端口但本次嵌入/检索抛错，降级到关键词。

`retrievePassages` 透出 `retrieval_mode`；词法模式的 `display_text` 标"（关键词匹配）"，`warning_notes` 加诚实提示（"当前未注入向量检索端口，结果为关键词匹配（非语义检索）。" / "向量检索不可用，已降级为关键词匹配（非语义检索）。" / "已启用向量检索但未召回命中，可能语料尚未生成嵌入。"）。3 个回归测试覆盖三模式。

### 2. 端到端接线（commit `d8eb66e`，按可选配置门控）

- **`SettingsBackedEmbeddingProviderResolver`**（新，adapters）：读默认 provider 凭据（baseUrl/apiKey）+ `AppSettings.extraSettings['embedding_model_id']`，构造 `RemoteOpenAiCompatibleEmbeddingProvider`；未配置 embedding 模型或缺凭据返回 null（调用方诚实降级）。配置放 `extraSettings`，**免改 settings schema/UI**——专用 UI 字段将来写同一键即可。

- **入库**：`RagTxtCorpusIngestionService` 接同一惰性 `embeddingProviderResolver`，`_embedChunks` 入库时解析；app 的 `ProjectRagExtractionExecutionService` 从当前 `_settings` 解析并透传，配置齐全时 chunk 落 `embedding_blob`，否则纯元数据。

**效果**：用户在默认 provider 配 embedding 模型即获端到端语义 RAG（入库生成向量 + 检索向量召回）；否则全程诚实降级到关键词（已如实标注，不再冒充）。

## 剩余深缺口（2026-06-23 续修：三项均已定位并修复/收窄）

> 此前三项曾标注"需真实 LLM/运行时追踪"。深挖后：三项都是**确定的代码/时序 bug，非模型行为**，已修复或收窄。

### kb 会话水合卡死 "正在恢复会话..." — 已修复

**根因（与旧判断不同）**：不在水合状态机本身（水合对 kb 也正常清状态），而在**视图同步层**。`app_shell_listenable_state.dart` 的 `_workbenchConversation` notifier 只在 `nextDestination == workbench` 时同步（`_syncWorkbenchPanes`）；kb 项目开项目时 destination 重定向到 `projectAssets`（`usesProjectAssetsAsPrimaryWorkspace`），于是 notifier 冻结在离开 workbench 前那一帧——恰好是"正在恢复会话..."。底层 `viewModel.workbench.generationStatus` 之后会清空，但不再传播到 notifier。

**修复**：`_syncConversationPane` 提取为独立方法并**无条件调用**（`_syncWorkbenchPanes` 仅留 resource/canvas/overlay）。会话就绪信号在任意目的地都保持实时。`app_shell_listenable_state_test.dart` 加回归（kb 场景：projectAssets 下 generationStatus 从"正在恢复会话..."演进到空）。

### chaptered_continuation 会话活动超时 — 已收窄（确定性诊断 + 真实流已通）

**根因（与旧判断不同）**：非真实 LLM、非就绪态时序玄学。probe 种入 `chapters/第02章_摸底.md` 后立即 `invokePrimaryAction('session.goal.continue_writing')`，但 guide 投影（`primaryActions`）读 `resourceSnapshotEntries`，可能滞后于资源树，此刻 `continue_writing` 被 `OpeningStarterActionPolicyService` 剥掉（maturity 仍判 fresh/opening）→ `onPrimaryActionRequested` 找不到动作 → 静默 `_announce` 返回 → 无生成活动 → 2 分钟超时。LLM 全程未被调用。

**修复**：
- probe（`real_gui_chaptered_continuation_probe.dart`）：调用前先 `waitUntil(continue_writing 出现在 primaryActions, 20s)`——给 guide 投影追赶时间；若 snapshot 真不刷新则**快速失败 + 诊断**，而非 2 分钟神秘超时。
- `conversation_opening_flow_controller.onPrimaryActionRequested`：动作缺失时点名 actionId + 给就绪提示，避免静默 _announce 被误读成"活动开始"。
- **真实续写流已通**：Phase 2（拆书续写正文落 `chapters/`）直接喂 maturity 的 narrative 计数 → 项目打开时 guide 投影判 continue-ready → `continue_writing` 出现。

**残留**：若某边缘场景 `resourceSnapshotEntries` 真不带 chapters，现在快速失败诊断（不再神秘超时）；snapshot 刷新机制本身已接线（`snapshot.entries → resourceSnapshotEntries` on refresh）。

### 多智能体派发不被推理模型采用 — 已修复（旧"模型行为"判断是错的）

**根因（与旧判断不同）**：工具定义/schema/描述都 OK（旧"工具链已确认启用"只对了一半）。真问题是**派发时 agent_id 解析无归一化**——同类 snake/kebab bug（见 [[agent-skill-expression-audit-conclusions]] 技能 ID）：
- `sub_agent_group_selection_service._groupSupportsRequestedAgent`：原始 `.contains()`，模型 emit `world_builder`/`WorldBuilder` 与存储 `world-builder` 不匹配 → 组选择失败回退。
- `sub_agent_run_package_service._selectChildAgent`：`byId.containsKey(requestedId)` 原始比对 → 显式指定子智能体解析失败 → 退回规则选人 → 若落到单成员/派生组，`supportsChildDelegation` false → 子智能体包构建失败 → 模型见失败"放弃"工具。

**修复**：两处都加归一化比对（`_canonicalAgentId`：小写 + `-`/`_` 等价），不改存储/路径用的 `safeAgentId`。`sub_agent_group_selection_service_test.dart` 新增 kebab/snake/大小写命中回归。

**残留（产品决策，非 bug）**：内置多智能体组（`optional_editorial_room`/`optional_review_room`）默认 `enabled:false`，故默认配置下 `call_sub_agent` 被 capability 闸门从工具列表剥离（模型看不到）——多智能体是 opt-in。要默认启用是产品取舍，未单方面改默认。
