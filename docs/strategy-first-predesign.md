# 策略优先与底层设计预案

## 目的

这份文档是项目进入正式实施前的桥接文档。

它解决两个问题：

1. 上层虽然以策略模式为先，但底层不能变成“什么都往里堆”的杂物层
2. `docs/mumuainovel-absorption-analysis.md` 里所有建议吸收的部分，必须在预设计层面都有明确落位

因此，这份文档是：

- `agent.md` 的工程化展开
- `architecture.md` 的策略落地版
- `mumuainovel-absorption-analysis.md` 的实施映射版

## 总原则

### 1. 上层由策略定义工作方式

仍然坚持：

- `project_strategy`
- `mode_strategy`
- `workflow_strategy`

先定义“怎么工作”，再决定“怎么实现”。

### 2. 底层由稳定资产和稳定合同支撑策略

底层不直接决定策略，
但底层必须有自己的设计理念：

- 资产稳定
- 引用稳定
- 状态可恢复
- 上下文可裁剪
- 宿主能力可替换

也就是说，底层不是被动承载，而是主动提供“可复用的稳定构件”。

## 底层设计理念

## 一、资产优先，不以页面为中心

底层优先建的是资产对象，不是页面数据。

例如：

- 风格
- 世界规则
- 角色 / 组织 / 地点 / 物品卡
- 伏笔
- 分析结果
- 模板包
- 模式状态
- 导入导出包

这些对象必须先在 core 中稳定表达，
UI 只是它们的一个视图层。

## 二、稳定 ID 优先，不以显示文本为主键

底层一律优先：

- 稳定 ID
- 显示名
- 别名
- 历史名

绝不允许：

- 人名当主键
- 标题当主键
- 文件名当唯一身份

这条规则适用于：

- 角色
- 组织
- 地点
- 风格
- 模板
- 伏笔
- 模式记录

## 三、关系优先，不以孤立对象建模

底层对象之间应允许稳定关系：

- 角色与组织
- 角色与章节
- 伏笔与章节
- 风格与项目
- 模板与策略
- 分析结果与重写计划

因此底层必须优先支持：

- 引用关系
- 反向查找
- 状态同步
- 关系更新

## 四、阶段记录优先，不以“一次性对话”建模

对复杂流程，底层应优先记录：

- 当前阶段
- 已收集项
- 缺失项
- 最近确认项
- 可恢复检查点

不能把这些信息只寄托在聊天历史里。

## 五、参数化优先，不以硬编码行为建模

底层实现要服务多模式，所以应优先做成参数化规则：

- 字数限制
- 检查点密度
- 自动推进边界
- 风格强度
- 伏笔提醒阈值
- 上下文注入策略

不要把某一模式的默认值写死成唯一逻辑。

## 六、能力解耦优先，不以供应商或宿主做中心

底层必须围绕“能力类型”建模：

- 文本生成
- 结构化分析
- 文件读写
- 资产导入导出
- 图谱构建
- 风格校验

而不是围绕：

- 某个模型厂商
- 某个 provider 参数
- 某个平台页面

## 七、结果对象优先，不暴露传输细节

底层提供给上层的应该是：

- 章节分析结果
- 重写计划
- 风格摘要
- 伏笔状态快照
- 导入预检结果

而不是：

- 原始 response body
- 原始工具分片
- 原始 provider 私有字段

## 预设计层级

建议把预设计拆成五层：

### 1. 策略层

负责：

- 项目策略
- 模式策略
- 工作流策略

位置：

- `packages/novel_agent_core/lib/src/strategy/`

### 2. 资产层

负责：

- 世界规则
- 风格
- 实体卡
- 伏笔
- 模板包
- 分析对象

位置：

- `packages/novel_agent_core/lib/src/assets/`

### 3. 引用与关系层

负责：

- 稳定 ID
- 别名解析
- 实体引用
- 图谱关系

位置：

- `packages/novel_agent_core/lib/src/entity/`
- `packages/novel_agent_core/lib/src/graph/`

### 4. 运行编排层

负责：

- 模式引导状态机
- 长任务调度
- 分析到执行闭环
- 上下文注入裁剪

位置：

- `packages/novel_agent_core/lib/src/modes/`
- `packages/novel_agent_core/lib/src/workflow/`
- `packages/novel_agent_core/lib/src/context/`

### 5. 宿主实现层

负责：

- 文件系统
- SQLite
- 导入导出
- 外部文档解析
- provider 接入

位置：

- `packages/novel_agent_adapters/lib/src/`

## 底层实现的红线

以后落实现时，底层必须避免下面几类坏味道：

### 1. 以 JSON blob 代替结构对象

除非确实是开放扩展字段，否则不要把：

- 风格
- 伏笔
- 分析结果
- 角色关系
- 模式状态

全塞回一个未拆分大 JSON 字段。

### 2. 以文件路径代替领域身份

路径可以变，名字可以变，目录可以改。

因此领域对象必须有独立 ID。

### 3. 以控制器拼接领域规则

任何：

- 阶段推进
- 风格注入
- 伏笔同步
- 导入预检
- 分析到重写转换

都不能主要写在 Flutter 控制器里。

### 4. 以单次 provider 协议塑造模型

领域模型不能围绕某一家模型厂商的字段来长。

### 5. 以页面分类替代策略分类

页面可以改，
但：

- 项目策略
- 模式策略
- 工作流策略

不能跟着页面结构漂。
